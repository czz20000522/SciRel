## 要决定的问题

两个收敛判定的分工，在总纲与实现注释之间**口径冲突**，需要定一次：

- `evaluate_outer_convergence(previous_density_m3, current_density_m3, truncate)`
- `evaluate_neutral_outer_seed_convergence(previous_density_m3, current_density_m3, truncate)`

两者**签名逐字相同**，返回同为"相对变化比 + bool + 理由字符串"，唯一差别是判定阈值：
前者用 `truncate`，后者用 `10*truncate`。

要决定的是：
**A. 合成一族**（一个函数加 `pass_='outer'|'seed'` 或 `threshold_factor=`），
**B. 维持分开**，并在合同里把"为什么 10× 阈值构成分开的理由"写成可引用的规范依据。

维护者已初步裁决"保持分开"；本单是把这条裁决与冲突一起固化成可追溯记录，
并请审核人确认 B 的**理由**要怎么写才不与总纲 §6.4 冲突。

## 仓库内的事实（可直接复现）

1. 两个函数的签名与返回结构逐字相同：

```python
>>> from scirel.neutrals import evaluate_outer_convergence, evaluate_neutral_outer_seed_convergence
>>> import inspect
>>> inspect.signature(evaluate_outer_convergence)
(previous_density_m3, current_density_m3, truncate)
>>> inspect.signature(evaluate_neutral_outer_seed_convergence)
(previous_density_m3, current_density_m3, truncate)
```

2. 两者的相对变化公式相同（都是 `max|prev-cur| / max(cur)`），差别只在阈值：
   - `scirel/neutrals/outer_convergence.py`：注释写明 "re-enters while the relative change is greater than
     ``truncate``"，比较式用 `truncate`；
   - `scirel/neutrals/outer_seed_convergence.py`：`reentry_threshold = 10*truncate`，
     合同 `relation` 原文 "computes seed_error and reentry_threshold (10*truncate)"。

3. **实现里有明确的"有意分开"声明**：`outer_convergence.py` 的模块 docstring 写着

   > "This operator is intentionally separate from the 10*truncate seed relation used inside the
   > neutral transport closures."

4. 两份合同都把差异写在 `model` 字段里：
   - `outer-convergence`：`the top-level outer-pass ratio-of-max relation with truncate threshold ...`
   - `outer-seed-convergence`：`the inner seed-pass ratio-of-max relation with 10*truncate threshold ...`

5. 两份合同都没有写"为什么这个阈值系数使它们不能合成一个函数的两个 `method`"。
   缺的正是这条依据。

## 冲突点（审核人只需要看这一段）

- **总纲 §6.4**：「某个方法专有的**迭代次数、截断阶数或数值容差**可以单独声明；把它传给不使用它的方法时
  应明确拒绝，不能悄悄忽略。」
  → 按这句话，`10*truncate` 属于"方法专有的容差"，**恰恰是允许留在同一函数里的那类参数**，
  不构成"分开写"的理由。
- **实现注释**：声明两者"intentionally separate"，理由就是那个 10× 系数。
  → 按这句话，阈值差异足以构成两个公开函数。

两条依据指向相反结论。§6.3 的判据（"只改 `method`、别的参数一个不动，拿到的是不是同一个物理量"）
在这两个函数上是**成立**的：改一个选择参数即得同一物理量（pass/fail 判定）。
所以按现行总纲字面，答案是 A；按现行实现注释，答案是 B。

## 选项

**A. 合成一族。**
`evaluate_outer_convergence(previous_density_m3, current_density_m3, truncate, *, pass_='outer')`，
`pass_='seed'` 时用 `10*truncate` 并在返回里保留 `reentry_threshold` 字段。
依据：§6.3 判据成立、§6.4 允许方法专有容差；返回结构已经是同一形状，合并后调用方无需改代码。
影响：公开面减少一个名字，两份合同合成一份；旧名需要删除（不留别名），并同步所有消费者与文档。

**B. 维持分开，补写依据。**
在两份合同的 `model` 或 `verification` 里写明：这不是"同一量的两种算法"，而是
**同一物理量在两个不同循环层级上的两次判定**，阈值 10× 是层级语义的一部分（外层 pass vs 内层 seed pass），
不是可替换的数值容差；并说明为什么合并会让"层级"这一物理语义从签名里消失。
影响：公开面不变，零风险；代价是需要在总纲 §6.4 补一句"层级/语义不同的容差不算可替换容差"，
否则下一个人还会问同一个问题。

## 各方意见（为什么需要人工裁决）

支持 A：总纲字面 + §6.4 字面 + 调用方不需要改后续代码，三条都指向合并。
支持 B：两个判定在调用方程序里的位置不同（一个在顶层 outer 循环、一个在 seed 内层重入），
合并后签名里再也看不出"这是内层"，而 §6.2 的 `method` 语义是"选算法"，不是"选循环层级"——
用 `method` 表达层级，会让族语义被滥用。

两边都不是证据不足，而是**规范之间的优先级问题**，只能人工定。

## 不决定的后果（已执行的安全默认）

实现、签名、合同**都不动**，两个函数继续分开存在；本审计文档把该组列为"该合族 + 已裁决保持分开"，
并指向本单。维护者的初步裁决（保持分开）与审核人最终结论一致时，本单可直接转 `decided` 并补写 B 的规范依据。
