## 要决定的问题

`scirel.neutrals.cross-mesh-distribution-interpolation` 的 `failure_semantics` 点名了两个异常类型
`InfeasibleMomentsError` 和 `MomentCorrectionConvergenceError`，并把它们描述为调用者可以区分的失败通道：
前者表示请求矩落在目标节点凸包之外（改迭代预算也没用），后者表示可行但数值上没收敛。但这两个名字
**不在** `scirel.neutrals` 的公开命名空间里。要决定的是：把它们纳入公开导出面（A），还是把合同的承诺改成
"只承诺 ValueError，具体类型名不作为公开契约"（B）。

审核人只读这一页就能决定，下面把事实分层写：仓库内可复现的事实、影响、两个选项的后果。

### 仓库内的事实（可直接复现）

1. 类定义在模块 `scirel/neutrals/cross_mesh_distribution_interpolation.py` 内，是 `ValueError` 的子类。
2. 公开命名空间没有它们：

   ```python
   >>> import scirel.neutrals as N
   >>> N.InfeasibleMomentsError
   AttributeError: module 'scirel.neutrals' has no attribute 'InfeasibleMomentsError'
   >>> from scirel.neutrals.cross_mesh_distribution_interpolation import InfeasibleMomentsError
   >>> issubclass(InfeasibleMomentsError, ValueError)
   True
   ```

3. 合同 `failure_semantics.invalid_input` 写的是"InfeasibleMomentsError, a ValueError subclass, reports an
   unrealizable destination moment ..."，`runtime_failure` 写的是"MomentCorrectionConvergenceError, a
   ValueError subclass, reports ..."。合同没有声明这两个名字属于 `scirel.neutrals`，也没有声明调用者该从
   哪个模块导入——两条信息都缺。
4. `scirel.neutrals.__init__` 的惰性导出表里没有这两个名字；`catalog/examples` 里其它资产的
   `public_api` 都写了 module/symbol，本资产的 `public_api` 只列了主函数，没有列异常类型。
5. 行为本身是可用的：`except ValueError` 能捕获两者，`error.diagnostics` 只在拿到具体类型或直接读属性时
   才用得上。

### 影响

- 按合同字面写代码的调用者会写 `except N.InfeasibleMomentsError`（N 是 `import scirel.neutrals as N`），
  这会在**导入期/属性期**失败，而不是在异常发生时失败，属于最不友好的失败方式。
- 只捕获 `ValueError` 的调用者拿不到"不可行 vs 未收敛"的区分——而这正是合同声称存在的区分，也是
  唯一一条"改迭代预算也没用"的可操作建议的载体。
- 发行包与文档读者无法从公开命名空间发现有这两个类型，只能读源码。

## 选项

**A. 在 `scirel.neutrals` 导出这两个名字（推荐给审核人评估）。**
依据：合同已经在 `failure_semantics` 里把两者写成可区分的失败通道；`ValueError` 子类的语义不变，导出不
改变任何数值或控制流。影响：公开命名空间新增两个名字，属于 API 表面变更，需按 `api-spec` 走 API 评审；
一旦导出就不能再安静地改名。若选 A，还应把两个名字写进本资产的 `public_api`。

**B. 合同改为只承诺 `ValueError`，并写明具体类型的模块路径。**
依据：不改公开面，零风险。影响：调用者失去"不可行 vs 未收敛"的类型级区分，只能靠 `diagnostics` 是否存在
或消息文本判断；合同的 `failure_semantics` 需要改写两条，`known_limitations` 保留"A 尚未执行"的说明。

## 各方意见（为什么现在定不下来）

支持 A 的理由是合同内部一致性与调用者可用性；反对 A 的理由是这会给一个冻结期内的资产新增公开名字，
而维护者已宣布暂停接收新能力。支持 B 的理由是零风险；反对 B 的理由是合同已经写下的可区分性会缩水，
且 `MomentCorrectionConvergenceError` 的诊断信息（未收敛的面/索引）恰恰是需要区分时才用得上。
两边都没有决定性证据，属范围决定。

## 不决定的后果（已执行的安全默认）

实现与公开面**都不动**；合同 `known_limitations` 已记录该缺口并引用本单 `T-2026-0003`；
本批新增的独立证据用模块路径导入该类型来验证不可行分支，并在测试注释里写明为何不能用 `scirel.neutrals`
的命名空间——这本身也是该缺口的一个可执行记录。
