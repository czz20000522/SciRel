## 要决定的问题

有三份资产的返回值是**一个映射**，而映射里有哪些键，合同里没有可枚举的声明。要决定的是：
**合同是否必须能列出返回映射的键集**（A），还是"返回一个映射、由 `description` 说明它关于什么"就算足够（B）。

### 仓库内的事实（可直接复现）

```sh
python3 -c "
import json
for a in ['fluid-case-state','multifluid-frequency-solve']:
    d=json.load(open(f'catalog/examples/scirel.kinetic.{a}.json'))
    print(a, [(o['name'], o.get('dtype')) for o in d['outputs']])"
# fluid-case-state        [('result', 'mapping')]
# multifluid-frequency-solve [('solution', 'dict[str, numeric arrays or structured metadata]')]
```

1. **三份都是"1 个声明输出、`dtype` 是 mapping/dict/类"**，不是"漏列了 30 个输出"。⊗ 我先前的读法有误，已在提交信息里更正。
2. `fluid-case-state` 的 `description` 是 "Complete species scales and source material metadata; EM sets kz=0.1kn."——
   它说明了映射**关于什么**，但列不出键。
3. 外部消费者（C4 收口轮）的实际后果：照合同无法枚举键，只能试；它把这三种记为"硬缺口"。
   原文见 `examples/c4-usage-acceptance/closeout/GAPS.md` B2。
4. 把 31 个键摊成 31 个 `outputs[]` 是**错的**：`outputs` 描述的是返回值，返回值是**一个**映射。

### 各方意见（为什么现在定不下来）

- **支持 A 的一方**：`outputs` 是外部消费者唯一能机读的返回结构声明。映射的键不声明，"合同即接口"在这三份上就不成立——消费者只能猜或试。
- **支持 B 的一方**：另加字段会把 schema 变成"两种返回形状描述法"（多输出用 `outputs[]`，映射用 `mapping_keys`），增加一处必须同步维护的东西；而这三份的键名本身是自由度很高的内部结构（species 名、deck 字段），固定下来可能锁死实现。
- **尚缺的证据**：没有记录过任何外部消费者**实际需要**这三个映射的哪些键。若审核人知道有使用者，这条会直接决定选项。


### 补充实测（2026-11-17，`main` @ `743fd738`）：范围比原先记的大

看得见的债换成若干条看不见的假陈述。

## 选项

- **A**：给合同 schema 加一个可选的 `mapping_keys`（或等价的 `outputs[0].keys`），三份补齐；门禁要求"`dtype` 是 mapping 时必须列键"。
- **B**：明确写下"mapping 型返回的键集不在公开契约内，消费者应通过 `capability-index` 或 `description` 判断适用性"，并把这句写进 `api-spec.md`，让后来的资产不再被要求列键。

## 不决定的后果（已执行的安全默认）

行为不动、合同不动、schema 不动。消费者在这三份上只能记 `cannot establish`。
是否需要门禁，随本单一起决定——**注意**：若选 B，则 `scripts/check_output_channel_declaration.py`
对 `dtype: mapping` 的单输出合同不应要求位置返回措辞；若选 A，则应要求列键。
