# 变异插件无法改写返回 frozen dataclass 的公开函数，这类资产的"变异存活"结论无效

## 要决定的问题

`scripts/scirel_mutation_plugin.py` 的输出变异器只递归 `dict` / `list` / `tuple` / `ndarray` / 数值标量。公开函数若返回 frozen dataclass，变异器走到末尾直接 `return value`，**任何 kind 都不会改变返回值**，`scripts/mutation_check.py` 就把五个 kind 全部记为 `not_exercised`。要决定的是：这一类资产此后怎么取得"证据是否承重"的判定。

## 现象与机制（可核对）

`scirel_mutation_plugin.mutate()` 的递归类型清单只有：

```python
if isinstance(value, dict): ...
if isinstance(value, (list, tuple)): ...
if np ... isinstance(value, np.ndarray): ...
numeric_scalar = isinstance(value, (int, float, complex)) or isinstance(value, np.number)
return value          # 其他一切对象原样返回
```

而 `scirel.equilibrium.compute_equilibrium` 返回 `scirel.equilibrium.equilibrium_state.EquilibriumResult`，它是 `@dataclass(frozen=True)`。`_changed_numeric()` 同样只比较 dict/list/tuple/数值，因此标记文件必然为空，驱动把"未改变返回值"读成 `not_exercised`。

2026-11-17 的实测（c1-eq2 批次，`scripts/mutation_check.py scirel.equilibrium.compute-equilibrium`）：

```text
FAILED  scirel.equilibrium.compute-equilibrium: scale not_exercised, negate not_exercised,
        zero not_exercised, swap not_exercised, constant not_exercised
  control selected 75, executed 75, deselected 0
```

baseline 的 75 条测试**全部执行并通过**，证据测试也在其中，所以这不是"测试没走到"，而是观测装置无法表达这个变异。

仓库里至少还有两处同形态的返回类型（`src/scirel/fvm/cell_variable.py`、`src/scirel/kinetic/dispersion/rational.py` 的 frozen dataclass），凡是把它们作为公开返回值的资产都受同一影响。

## 影响

- 这类资产的"变异存活"读数**一律无效**：`not_exercised` 会被误读成"测试缺口"，`PASSED` 也永远不会出现。
- 按 `scirel-acceptance` skill 的四档判定，正确结论只有 `UNKNOWN`（插桩失败，不作结论）。2026-11-17 的批次即按此处理，并用副本目录手写代码变异替代（符号、2π 因子、边界比较、松弛权交换、clip 失效，5/5 killed，带 `print(scirel.__file__)` 副本探针与未变异副本对照）。
- 手写代码变异不进合同（合同记证据结论，不记工具限制），所以这条限制目前**只存在于本单与批次报告**里。

## 已执行的处置（安全默认）

实现未改，插件未改，合同未加"该资产不适用插件变异"的条款；受影响资产在批次报告里记 `UNKNOWN` 并附手写变异结果。

## 选项

- **A. 插件支持 dataclass**：在 `mutate()` 与 `_changed_numeric()` 里按 `dataclasses.fields()` 递归，frozen 用 `dataclasses.replace`。代价：所有返回 dataclass 的资产的变异判据会**同时变严**，此前恒为 `not_exercised` 的资产会开始出现 `survived`，可能把别的批次的回执变红。
- **B. 只写文档**：在 `skills/development/scirel-acceptance/SKILL.md` 写明"返回 dataclass 的资产必须用手写代码变异，插件结论记为 UNKNOWN"。代价：判据仍在人手里，没有门禁。
- **C. 合同侧标注**：在受影响合同的 `verification` 里写明"该资产的变异证据来自手写代码变异"。代价：合同开始记录工具用法，而合同本应只记证据结论。

## 需要审核人给出的结论

选 A / B / C 中的哪一个，以及若选 A，是否接受"其他批次可能因此转红"这一即时后果。

## 各方意见

- 供给线（c1-eq2 批次，2026-11-17）：受影响资产的变异结论记 `UNKNOWN` 是唯一诚实的读法；手写代码变异（副本 + `print(scirel.__file__)` 探针 + 未变异对照）能承重，但不进合同。倾向 A，其次 C；反对在没有任何门禁的情况下长期依赖 B。
- 未收到其他意见。

## 不决定的后果

- 所有返回 frozen dataclass 的资产在 `scripts/mutation_check.py` 里永远只会得到 `not_exercised`，驱动把它们判为 `FAILED`，于是"这批资产的变异没做"与"这批资产的证据不承重"在回执里长得一样。
- 每个批次的执行者都要各自手写一遍代码变异，判据不进仓库，下一批无法核对上一批到底做了哪几种变异。
- 若将来有人为了"让插件跑通"把公开返回类型从 dataclass 改成 dict，那会是一次未经评审的 API 变更；本单存在正是为了不让那次变更以"修门禁"的名义发生。
