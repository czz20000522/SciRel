## 要决定的问题

公开面上有四个名字，其中两个带 `helper` / `Helper` 前缀：

| 公开名 | 合同资产 | 所在模块 |
| --- | --- | --- |
| `contour_points(contourset)` | `scirel.fieldline.contour-points` | `scirel.geometry.fieldline` |
| `helper_contour_points(contourset)` | `scirel.fieldline.helper-contour-points` | `scirel.geometry.fieldline` |
| `FieldLine(psi, verts, **kwargs)` | `scirel.fieldline.fieldline` | `scirel.geometry.fieldline` |
| `HelperFieldLine(psi, verts)` | `scirel.fieldline.helper-fieldline` | `scirel.geometry.fieldline` |

"helper" 是**实现词汇**，不是用户词汇。它出现在公开名里，等于告诉使用者"这个名字是内部用的"，
同时又要求他为它写 `import`。要决定的是：**从公开面移除、改名，还是维持并写清理由。**

这不是族的判定问题（两组都已按"产出类型/接口不同"判为分开，见
[族规则审计](../../docs/maintainer/family-rule-audit.md) §2.3(b)），而是**命名与公开面范围**问题。

## 仓库内的事实（可直接复现）

1. 两组函数签名相同，但**产出的对象类型不同**：

```python
>>> from scirel.geometry.fieldline import contour_points, helper_contour_points
>>> import inspect
>>> inspect.signature(contour_points)
(contourset)
>>> inspect.signature(helper_contour_points)
(contourset)
```

2. 文档把两者的差异写得很清楚（见 `tools/docs/handbook.json`、`tools/docs/zh/zh_geometry_primitives.json`）：
   - `FieldLine` 构造器另接受 `u`、`s`、`k`、`npts` 拟合参数，`HelperFieldLine` 不接受；
   - `interpolate_onto` 中 `FieldLine` 过滤非有限源场值，`HelperFieldLine` 把全部源场值传给 SciPy；
   - `get_kappa_n` 在 `FieldLine` 返回形状 `(npts, 2)` 的数组，在 `HelperFieldLine` 返回两个 `(npts,)` 数组组成的元组；
   - 只有 `FieldLine` 提供磁通梯度曲率方法 `get_kappa_n_2`。

   也就是说：**同一物理量（曲率、场线几何）在两处有不同接口**，且其中一处以 `Helper` 命名。

3. 这两组已经被**正式文档引用**，不是内部残留：
   `tools/docs/handbook.json`、`tools/docs/handbook.en.json`、`tools/docs/zh/zh_geometry_primitives.json`
   都有专门段落描述 `FieldLine` / `HelperFieldLine` 的构造与返回合同差异，
   并有独立的 `example.expected`（"返回字典含键 0.2，其中有一条包含 1000 个拟合顶点的 HelperFieldLine"）。
   因此**移除会同时改变文档站内容**。

4. 仓库内有专门的清理检查：`tests/architecture/test_public_helper_cleanup.py`。
   本单与该检查的关系需要审核人确认——如果检查只覆盖 `_` 前缀的私有名，那它对 `helper_` 前缀是盲的。

## 影响：移除会影响谁

| 受影响面 | 具体 |
| --- | --- |
| 文档站 | `tools/docs/handbook.json`、`handbook.en.json`、`zh_geometry_primitives.json` 中四个资产条目的段落、`example`、`known_limitations` |
| 合同 | `catalog/examples/scirel.fieldline.{contour-points,helper-contour-points,fieldline,helper-fieldline}.json` 的 `public_api` |
| 测试 | `tests/fieldline/test_contour_composition_evidence.py`（以 `HelperFieldLine` 作工厂套用独立展平 oracle）、`tests/equilibrium/test_analysis_families.py`、`tests/equilibrium/test_fieldline_t7_precision.py` 都显式调用 `HelperFieldLine` |
| 交付面 | 若 C4（独立消费者首轮）/ C5（真实交付包）的用例引用了这两个名字，改名会让那份回执失效——**审核前需先查这两条线是否引用**（本次未查，属待补事实） |

## 选项

**A. 从公开面移除。**
把 `helper_contour_points` / `HelperFieldLine` 降为模块私有（`_helper_...`），公开面只留
`contour_points` / `FieldLine`；内部调用改指私有名。
依据：`helper` 是实现词汇，不该出现在公开 API；公开面有两个名字做同一件事会让人选错。
影响：`energy` 最小但破坏面最大——文档站三段要重写，测试要改导入，且**"两类对象接口不同"这个事实**
会从公开面消失（用户只会看到 `FieldLine`，却可能在内部拿到 `HelperFieldLine` 类型的对象）。

**B. 改名并统一接口。**
保留两类对象，但改成有意义的名字（例如 `FieldLine` / `FieldLineSegment`），
并统一 `get_kappa_n` 的返回形状。
依据：`get_kappa_n` 返回两种形状是真正的接口债；名字只是症状。
影响：公开面改名 + 接口变更，属 API 评审范围；一次改动同时解决命名和接口不一致。

**C. 维持现状，把理由写进合同。**
在两个资产合同的 `known_limitations` 里写明"`helper_` 前缀表示这一实现的返回合同更窄，
两类对象不可互换"，并在 `api-spec` 里承认这是一条例外。
依据：零风险，且当前文档已经把这层差异写清楚了。
影响：`helper` 前缀永久留在公开面上；下一个作者会认为这种做法被批准过。

## 各方意见（为什么需要人工裁决）

A 的理由是公开面整洁；反对方指出文档已经把两类对象当作**独立的公开合同**在写，移除等于删掉一份
有独立证据的合同，与"能力边界冻结"期间的"先还债、不新增也不随意删"相冲突。
B 的理由是接口债才是根因（一个方法两种返回形状）；反对方指出这属于 API 变更，需要走 `api-spec` 评审，
且会同时失效文档站的示例与 C4/C5 可能存在的引用。
C 的理由是"文档已经说清"，反对方认为这会把一个实现词汇固化成规范。

## 不决定的后果（已执行的安全默认）

实现、公开面、合同、文档**都不动**。本审计文档在 §2.3(b) 与 §2.4 记录该归一事实，
并指向本单；族审计按"接口不同 → 分开"处理，不把这两个名字当作合族候选。
