## 要决定的问题

`build_basis` / `BasisMatrix` 的选择器与 `coeffs` 控件有两条失败通道与
[api-spec](../../skills/development/scirel-code-style/references/api-spec.md) 的"无效输入 → `ValueError`、类型错 → `TypeError`"
不一致；第三条（未实现选择器）合同与 api-spec 之间的口径也不统一。要决定的是：**改实现去对齐 api-spec，还是把合同口径正式定为当前实现**。
本单只列事实与方案，不改行为。

## 仓库内的事实（可复现）

以下三条在 `c1-numerics` 分支的实测结果（`PYTHONPATH=src python -m pytest tests/numerics/test_basis_design_evidence.py` 可复现），
合同 `failure_semantics.invalid_input` 的原文列在右侧：

| 调用 | 实测异常 | 合同 `invalid_input` 是否已声明 |
| --- | --- | --- |
| `build_basis('quartic')` | `KeyError` | **已声明**："KeyError for an unregistered selector"，另声明 "NotImplementedError for an unsupported retained selector" |
| `build_basis('poly', poly_deg=2, coeffs=[1.0, 0.0])` | `AttributeError: 'list' object has no attribute 'shape'` | 未声明 |
| `build_basis('poly', poly_deg=2, coeffs=np.array([2.0, 3.0]))` | `IndexError: tuple index out of range`（内部 `coeffs.shape[1]`） | 未声明 |
| `build_basis('foo')`（未知选择器） | `KeyError`，消息只有裸键名，无合法取值清单 | 已声明 KeyError，但未要求消息含合法取值 |

代码位置：`src/scirel/numerics/basis.py` 的选择器分发（`basis_map[...]`）与 `_poly_basis`（`coeffs[:, i]`）。
同仓先例：`QuarticSpline.__init__` 对同一缺口抛 `NotImplementedError("Upstream quartic spline coefficient construction is incomplete")`。

`coeffs` 在 api-spec 中属 array_like，`[1.0, 0.0]` 这种形式**应当被接受**，所以 `AttributeError` 同时是"错的异常类型"和"拒了合法输入形式"。

## 各方意见

- 调用方按 api-spec 写 `except ValueError` 时，上述三条都接不住；`KeyError`/`AttributeError`/`IndexError` 是内部实现泄漏，不是对外承诺。
- `quartic` 走 `KeyError` 与同仓 `NotImplementedError` 先例不一致，同一缺口两种异常类型。
- 未实现的选择器是"能力缺口"而非"输入错误"，把两者都压成 `ValueError` 会让调用方无法区分"我拼错了"与"这个能力还没实现"。
- 若改为 `NotImplementedError`：它继承 `RuntimeError` 而**不是** `ValueError`，`except ValueError` 的调用方会漏接；这会改变对外承诺，必须在此单里定，不能顺手改。

## 选项

- **A（对齐 api-spec，改实现）**：未知/拼错选择器 → `ValueError`，消息列出合法取值；`quartic` 等已识别未实现选择器 → `NotImplementedError`；`coeffs` 先 `np.asarray`，形状/维度不合 → `ValueError`（并接受 1 维 array_like 作为单函数系数）。合同 `invalid_input` 随之改写。
- **B（把合同口径定为当前实现）**：保留 `KeyError` 表达"未注册"、`NotImplementedError` 表达"未实现"，只补 `coeffs` 两条为已声明的 `ValueError`，并在 api-spec 里为"选择器类输入"写例外条款。

上一级评审已表示倾向 **A**（"invalid input raises ValueError，wrong kind 用 TypeError"）；本单据此请两位审核人确认 `NotImplementedError` 的例外是否成立，因为它是 A 里唯一改变异常继承层次的部分。

## 不决定的后果

本 PR 的交付物是 C1 科学证据（测试 + 合同 `verification`），不含行为改动。把失败通道改掉会让同一个 PR 同时改变对外承诺，
无法按 `RULES.md` §1 与 `supply-pipeline.md` §7.2 的证据-评审链逐项核对；而且修实现后必须同步改两处刻意钉住实测类型的测试
（`test_basis_design_evidence.py::test_basis_matrix_rejects_an_unknown_selection`、
`::test_poly_coeff_control_shape_deviations_are_recorded`），这属于实现改动 PR 的范围。

安全默认已生效：实现不动，合同 `verification.known_limitations` 记录"实测类型与 api-spec 不一致，见本单"，测试钉住实测类型并在 docstring 指向本单。
