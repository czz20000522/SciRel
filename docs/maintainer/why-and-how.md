# 我们做什么、为什么、怎么做

这是项目的**完整叙事**。README 是五分钟版，这一页是给要向别人讲解 SciReL 的人用的：
听众可能是物理专家，也可能是软件开发者，所以每个概念先用大白话讲清楚，再给术语。

**本文件只写不会随版本失效的内容。** 现状、进度、规模、领域清单一律在
[状态快照](status.md)；两者怎么分界见 [持久规范与状态](durable-vs-status.md)。

## 1 一句话

**SciRel 是一个面向聚变与等离子体物理的 Python 科学计算库。它的每一个公开函数都附带一份正式的"合同"，
写清楚这个函数用的是什么物理模型、单位是什么、在什么范围内可信、出错时会怎样。**

再通俗一点：

- 它是一个"聚变物理的零件箱"：里面放的是库仑对数、碰撞截面、复合速率、磁场 Green 函数、
  平衡求解器、色散关系这类可以单独拿出来用的物理计算。
- 它不是一个"从输入文件跑到输出结果"的大程序，而是一堆标准零件，用户（人或 agent）自己挑零件、自己组装。
- 与一般代码库不同，**每件工具都贴着一张说明书**，而且这张说明书是机器能读的，不只是给人看的注释。

长期目标是覆盖聚变与等离子体研究的广泛方向，最终能组织上千乃至上万个能力。
因此结构设计要同时回答两件事：今天的一条公式怎样独立复用，以及将来大量不同物理领域的能力
怎样被找到、比较和组合。

## 2 我们想解决什么问题

### 2.1 聚变领域的代码现状

做聚变或等离子体研究的人大多见过这几种情况：

- **同一个公式被反复重写。** 库仑对数、电荷交换截面、Bessel 函数求和，每个课题组、每个程序里都有一份，
  彼此略有不同，没人说得清哪个对。
- **代码和程序绑死。** 一个很好用的截面拟合藏在某个大程序（比如中性粒子输运程序）的深处，
  想单独拿出来用，就得把半个程序都带上。
- **适用范围没人写。** 程序允许接收的数值范围，有时被误当成已经有物理证据支撑的范围；
  使用者因此分不清哪段经过验证、哪段属于近似或外推。
- **出错时静默。** 输入超出范围，代码悄悄截断，然后给一个"看起来正常"的数字。

### 2.2 新的用户：AI agent

越来越多的计算工作会交给 AI agent 来做。agent 有三个和人很不一样的特点：

- **会话之间的记忆不可靠。** 换一个 agent，或上下文被压缩后，不能假定它记得某个函数以前有什么限制。
- **会漏掉隐含的异常信号。** agent 可以提出质疑，但不能把它一定会察觉"这个结果太容易就通过了"作为设计前提。
- **部署环境未必有源码。** 只拿到分发包的使用者，主要依靠函数说明、合同、检索结果和报错来判断下一步。

所以**重要的限制和失败不能只藏在某个人的经验里，必须能从交付物中查到。**
SciRel 把 agent 当成主要用户之一，这决定了合同要机器可读、报错要自带"下一步怎么办"、文档要能分层查找。

## 3 核心思想

### 3.1 每个函数都有一份合同

合同不是注释，是一个结构化记录：模型是什么、输入输出的单位与形状、适用与排除的范围、
失败时会怎样（哪类错误、什么条件下、会不会给部分结果）、以及**它凭什么是正确的**（证据与已知局限）。

合同是**代码的衍生品**：可推导的字段来自实现与 docstring，物理依据与适用范围另由独立证据支撑。
所以合同写错时以代码的实际行为为准改写合同；但"合同和代码一致"**不构成代码正确的证据**。

### 3.2 真值链：证据 → 代码 → 合同 → 文档

代码之所以是对的，只因为**证据**支持它——已发表文献、被拆解项目的实际行为、物理正确性、解析恒等式、
守恒量。三条箭头各有各的失败模式，不要混：

| 现象 | 结论与动作 |
| --- | --- |
| 合同与代码不符 | **合同错了**。按代码实际行为改写合同，不留两个版本。这只解决"合同没写对"，不证明代码对 |
| 代码与证据不符 | **代码错了**。开工单、按安全默认处理（行为不动、`known_limitations` 记录、等人工裁决）；不得把错误行为写进合同让它变成"已声明" |
| 证据拿不到 | 如实记 `cannot establish` 并写清卡点。缺失的证据不能当证据；"测试钉住了当前行为"或"与另一实现一致"都不等于正确性证据 |

自查一句话：**这条合同说法背后，是证据，还是只是代码现在的样子？**

这套做法不是我们自创的标准。OpenFOAM 社区把 exact solution / manufactured solution 当作求解器验证的
标准手段——造一个已知精确解，让求解器把它解回来，判据是"能不能对上那个精确解"。
我们的闭式解、精确有理重算、守恒恒等式、高位 mpmath 对照，是同一套思想。
出处与对照见 [参照项目](reference-projects.md) §2.3。

### 3.3 按物理分层，依赖像水一样只能往下流

函数一多就会遇到两个问题：找不到，以及互相缠绕。做法是按物理分层，规定依赖只能单向。
楼上的人可以下楼借东西，楼下的人不能上楼借。

- **L0 私有基础**：结果类型、输入校验、通用工具（用户看不到）。
- **L1 数学与数值**：插值、拟合、有限体积、文件读写（纯数学，不含物理名词）。
- **L2 局部物理关系**：库仑对数、截面、反应率、介电张量（"一个点上的物理量"）。
- **L3 几何与场**：通量面、场线、真空磁场、线圈。
- **L4 物理子系统**：动理学、中性粒子、磁镜、新经典、闭合。
- **L5 耦合与反演**：平衡求解、诊断、参数反演。

规则只有一条：**依赖只能往下走**。同一层内的领域原则上互不依赖，例外必须写进白名单。
分层的好处是 agent 能推理出该去哪儿找，而且扩展时层数不变——能力增长是在层内增加领域与模型族，不是加层。

这张表**不是**"现在有哪些域"的清单（那是会漂的状态），而是**分层原则**；
具体有哪些域、拆分进行到哪一步，看 [状态快照](status.md) 与 [代码地图](codebase-map.md)。

### 3.4 模型族与 `method=`

物理里经常有这种情况：**同一个物理量，有好几种算法或拟合公式**。这叫一个**模型族**。

同一族的模型合成一个函数，用一个参数选"用哪种算法"：

```python
compute_bootstrap_coefficients(..., method="redl")     # 默认
compute_bootstrap_coefficients(..., method="sauter")   # 旧拟合，用来对照
```

**判断标准就一句话：调用的人只改 `method`、别的参数一个都不动，拿到的是不是同一个物理量？**
是 → 合族；不是 → 分开写。

几个真实的判断（这些是规范，不是现状）：

| 情况 | 结论 | 理由 |
| --- | --- | --- |
| bootstrap 系数的两种拟合 | 合族，默认用更新更准的 | 同一个物理量 |
| 电子–电子与电子–离子的库仑对数 | **分开** | 是不同的碰撞对，不是同一个量的不同算法 |
| 多个平衡求解器 | **分开** | 物理输入差别很大：有的要压力剖面，有的要各向异性闭合，有的要真空场 |
| 读 EQDSK 与读 G-EQDSK | **分开** | 读文件是数据格式问题，不是在选物理模型 |
| 动量转移截面与粘性截面 | **分开** | 两个不同的物理量 |

两种写法各有权衡：`method=` 好找、便于对比模型，但某个模型专有的参数对其他模型没有意义，
容易变成"只在某种 method 下有效"的参数堆；分开写签名精确，但名字多、要靠索引补。
原则是：**同一个物理量、同一组物理输入用 `method=`；物理输入或问题性质不同就分开写。**
方法专有的迭代次数、截断阶数、数值容差可以单独声明；把它传给不使用它的方法时必须明确拒绝，不能悄悄忽略。

默认值的定法：一族里有两个都有文献支持的拟合时，在目标范围内优先选证据更充分、精度与稳定性更合适的，
同时说明计算代价。**发表得更新不自动等于对所有输入都更好。** 改默认值会改变计算结果，
必须附新旧方法在同一组输入上的对比并同步合同。

这条规则当前的执行情况（哪些该合族、哪些判不了）见 [族规则审计](family-rule-audit.md)。

### 3.5 为 agent 设计接口

- **报错自带下一步。** 选错名字时列出全部合法名字；输入越界时说清边界在哪、该怎么办。
- **超出适用范围**不静默截断，要么拒绝，要么明确标注这是外推。
- **迭代不收敛**要区分"预算不够"和"不可行"，因为这两种的下一步完全不同。
- **渐进式披露**：能力多了之后，先从领域与物理问题缩小范围，再看完整合同；索引由权威内容生成，
  搜索相似度不能覆盖物理约束，零命中也不自动代表缺能力。
- **文献引用用 DOI 或 URL 与最小书目信息**，不要用"作者-年份"这类需要私人上下文才能解析的引用。

## 4 能力从哪里来：三条线

供给者提取候选，合并者把候选并入库，消费者用分发包解决问题。

- **拆解线**：把别人的实现变成我们的能力。拆解者手上永远有一份冻结版合同，可以先比对、再取补集；
  新实现在那个版本上运行测试。产物必须是最终形态，并且已经通过与合并线完全相同的检查。
- **合并线**：只消费"拆解包"，只判题、不重写。拆解包的格式是两条线之间唯一的约定。
- **出库线**：通过"缺口信号"影响拆解方向——用户经常需要但库里没有的能力会反馈回去，
  但出库线不直接派任务。分发包里是合同、安装包和使用方法 skill，改进外部 agent 的回答就改这三样。

操作细节（六步流程、校验器、分级格式）见 [供给侧流程](supply-pipeline.md)。

## 5 怎么证明"测试真的有用"

覆盖率只证明代码被执行过，不证明测试能发现错误。办法是**变异测试**：故意把答案弄坏，
看测试能不能发现。发现不了，说明这条测试没在保护任何东西。

变异测试也是"证据测试"与"行为测试"之分能落地的地方：行为测试挡的是回归，
证据测试挡的是"物理算错了"。两者都要有，但不能混报成同一个数字。

## 6 人工审核：分级评审与工单

不是所有事都要人来管。按代价分级：A 级交叉预审、B 级两个独立评审、C 级人工裁决。
证据不足以定论时**先执行安全默认**——行为不动、在合同的 `known_limitations` 里记录、开一张工单，等人工裁决。

工单是给人看的，要求是"审核人只读这一页就能决定"：先把仓库内可复现的事实列清，再列选项与各自影响，
最后写清"不决定的后果"（也就是已经执行的安全默认是什么）。

## 7 刻意不做的事

SciRel 提供科学零件，**也可以提供可复用的组合零件**——多线圈加权叠加、一个有明确输入输出的平衡求解步骤，
只要有自己的合同和直接测试，就可以作为库里的能力。

但**具体研究任务的总体流程仍由用户程序负责**：采用哪些假设、怎样准备装置数据、如何安排整个模拟、
输出什么报告。**SciRel 不要求用户改用另一套配置语言或全局运行框架。**

边界可以这样理解：库负责标准元件与标准组件，用户负责把它们装成自己的研究程序。
不能因为几个元件各自正确，就省掉它们组合之后的单位、坐标、适用假设和失败路径检查。

## 8 工程纪律：为什么有这么多"规矩"

- **可复现的环境**：解释器版本与依赖锁定在仓库内，运行产物不写到项目目录之外，不依赖某台机器的环境。
- **门禁按代价分层**：防的是自己和 agent 的失误，不是攻击者。拦在不可逆之前（凭据、私有路径），
  其余放在合并前的完整检查里。门禁按**改动落在哪个面上**选，不是"跑得越重越保险"。
- **如实报告**：失败和未运行的内容不能写成通过；回执要能对账到具体检查项。
- **不留兼容层**：一条规范只留一份实现，不留别名、不留双读路径。改就改到位，同步消费者。
- **公开仓库自给自足**：代码、测试、门禁和文档构建只依赖仓库内跟踪的文件，
  不写本机路径，也不依赖私人笔记。

## 9 参照项目

**结构参照 scipy，流程参照 OpenFOAM。** 两者是参照，不是依赖，也不是要模仿的完成度。
scipy 管"这个库长什么样"（分层、模块粒度、公开面组织、选择参数的用法），
OpenFOAM 管"能力怎么被造出来、怎么被验收"（准入、验收、族纪律、案例分类、验证方法论）。

两条线一旦混用就会走偏：拿 scipy 的模块数当验收标准，就会为了少文件而强并强删；
拿 OpenFOAM 的平台形态当目标，就会开始造配置语言和运行框架。

完整的对照、以及我们**不采用**哪些做法，见 [参照项目](reference-projects.md)。

## 10 术语

| 术语 | 含义 |
| --- | --- |
| 资产（asset） | 一条可独立验收的物理能力，对应一份实现、一份合同、一个测试入口 |
| 合同（contract） | 描述一个公开函数模型、单位、范围、失败行为与证据的机器可读记录 |
| 真值链 | 证据 → 代码 → 合同 → 文档 的派生关系；每条箭头各有失败模式 |
| 模型族 | 用不同模型或拟合计算**同一个物理量**的一组函数 |
| `method=` | 模型族里选算法/模型的参数 |
| 分级评审 | 按改动代价分级的人工审核（A 交叉预审 / B 两个独立评审 / C 人工裁决） |
| 变异测试 | 故意弄坏实现，检查测试能否发现 |
| 分发包 | 交给外部 agent 的合同目录 + 安装包 + 使用方法 skill |
