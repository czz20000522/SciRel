# 模块粒度：一个能力一个模块

状态：**第 1、5 节是一次性测量与现行规则**；第 5 节的规则是持久的（提议写入
[`scirel-code-style` 的 API 规范](../../skills/development/scirel-code-style/references/api-spec.md)），
第 2~4 节的理由不会随版本变，第 1 节的数字会。观察点：`main` @ `7f1eef8c`，2026-11-17。

## 0 这份文件解决什么

"一个公开能力 = 一个实现模块"这件事，全库都在照做，但**从来没有被写成规定过**。
它既不在 [架构文档](../../ARCHITECTURE.md) 里，也不在 `api-spec` 里，也没有任何检查器。
所以它既不能被引用为理由，也不能在被违反时被发现。

本文件做三件事：把现状量清楚、说明它**是怎么长出来的**（不是谁决定的）、把代价和收益摆出来，
最后给出**一条可执行、可检查的规则**，并说明按实测哪些域最可能违反它。

## 1 现状（一次性测量）

口径：合同的 `public_api.python.module` 为承载模块；复算脚本见
[状态快照](status.md) 附录 A。

| 量 | 值 |
| --- | --- |
| 合同 | 249 |
| 承载这些合同的模块 | 170 |
| 平均每模块合同数 | 1.46 |
| 只承载 1 份合同的模块 | 149（占 170 的 87.6%） |
| 承载 ≥2 份合同的模块 | 21 |
| 这 21 个模块吃下的合同 | 100（占 249 的 40%） |
| 模块文件名与合同 slug 逐字对应 | 124（占 249 的 49.8%） |

### 1.1 这个 1.28 该跟什么比

比的是 scipy 的**合法区间**，不是一个单点。实测（scipy 1.18.1，口径见
[参照项目 §1.1](reference-projects.md)）：不同子包每个模块承载 0.7–5.8 个公开名字，
另一套口径给出 1.2–17.0。落在地板上的子包（`io` 0.7、`cluster` 0.8、`sparse` 0.9）
都是"一模块一格式/一类对象"——**格式与数据结构天然独立，聚合度低合理**；
按子主题组织的子包（`special` 4.6、`stats` 5.6、`ndimage` 5.8）才是"一大类对象 + 若干变体"。

我们 1.28，**落在 scipy 的地板上**。

所以结论不是"我们模块太多"——那是拿文件数当判据。正确的是：

> **1.28 通常意味着把一个子主题摊成了平铺列表。**
> `neutrals` 的 33 份合同近乎严格 1:1，相当于把"物理模型族"当"文件格式"来组织；
> 它本该更像 `special` 或 `signal` 那样，按子主题成组。

粒度是否合适的判据是"这一族该不该在一起"，不是"文件数比别人多多少"。

### 1.2 现状的两个半边

缺一半就会说错：

1. **主导形态确实是 1 合同 : 1 模块。** 149/170 的模块只装一份合同；
   `neutrals` 33 份合同分摊到 32 个模块，其中 31 个模块只装一份（唯一的例外是
   `scirel.neutrals.moment_compensation`，装 2 份）。
2. **但分布是长尾的，不是严格的 1:1。** 21 个模块装下了 40% 的合同，最多的是
   `scirel.geometry.sampling`（14 份）、`scirel.kinetic.dispersion.rational`（9 份）、
   `scirel.kinetic.vlasov_poisson`（9 份）、`scirel.geometry.fieldline`（7 份）。
   也就是说，"一个能力一个模块"是**默认**，不是**铁律**；已经有模块按功能而不是按合同聚合。

域内分布（合同 / 模块 / 单合同模块）见 [状态快照 §3](status.md)。最贴近平铺的是
`field`（14/14/14）、`equilibrium`（12/12/12）、`mirror`（12/12/12）、`closures`（7/7/7）、
`diagnostics`（7/7/7）；最像"一个模块多个能力"的是 `sampling`（14/1/0）、`fieldline`（7/1/0）、
`configurations`（3/1/0）。

## 2 为什么会长成这样（不是谁决定的）

没有任何一次评审决定过"一个函数一个模块"。它是下面这条供给流程的**默认产物**：

```
一个资产 → 一份实现 → 一个模块文件 → 一份合同 → 一个测试文件
```

拆解线的输入单位是"资产"（一篇文献、一段被拆解的源实现），输出单位自然也是"资产"。
[供给侧流程](supply-pipeline.md) 的每一步都按单个资产推进：比对已有合同、为新资产写实现、
写它自己的测试与证据。没有任何一步要求作者去看"同域里已有哪些模块、能不能并进去"。
于是每来一个资产，就多一个模块、一份合同、一个测试文件——**三者同比例增长是这个流程的
必然结果，不是某个人的审美**。

两条机械证据：

- 249 个模块里有 124 个的文件名与合同 slug 逐字对应（`discrete-vector-error-feedback`
  → `discrete_vector_feedback`，`atomic-hydrogen-charge-exchange-rate-coefficient`
  → `atomic_hydrogen_charge_exchange_rate`）。命名是照着资产抄的，不是照着族设计的。
- 引入 `method=` 的成本落在这一步之上：作者必须先把同族的另一个函数读一遍，
  才能知道能不能合。按资产推进的流程不会自动产生这个动作，所以执行率低（实测 9/249，
  见同目录的族规则审计）。这条事实与本节互为解释。

## 3 代价

1. **域内概览难。** `kinetic` 有 62 份合同分摊在 26 个模块上，读目录只能看到 26 个名字，
   看不到 62 个能力之间的族关系。要判断"有没有人已经算过这个量"，必须逐个打开合同。
2. **测试文件数 1.65× 合同数。** 412 个测试文件对 249 份合同。多出来的部分是域级、
   架构级和工具测试，但"一资产一测试文件"仍然让每个小改动都落在一个新文件里，
   跨切面改动（改一个共用校验、改一个返回类型）触点是线性放大的。
3. **跨切面改动触点多。** `Result` 形状、单位约定、错误措辞这类横切面如果按模块落地，
   一次口径调整就要动几十个文件。实测的例子：`evaluate_dielectric_diagnostics` 与
   `evaluate_dielectric_response` 各自维护一份几乎相同的返回字段。

## 4 收益

这些收益是真实的，也是这条约定一直没被推翻的原因：

1. **provenance 隔离。** 一份合同的证据、`known_limitations`、适用范围和它的实现同处一个模块，
   改一个能力不会碰到另一个能力的证据链。真值链要求"证据 → 代码 → 合同"逐条成立，
   1:1 让这条链最短，出错时能直接定位到唯一的一份证据。
2. **变异测试可逐文件定位。** 变异测试按文件跑，1:1 意味着一份合同的变异结果就是那个文件的
   变异结果，不需要从混装模块里分辨"这条测试是为了哪个能力"。
3. **不会误耦合。** 十五个波/色散函数如果并成一个模块，公用一个内部 helper 只是时间问题；
   一旦公用，单改一个模型就会牵动别的模型的结果，而合同上的适用范围是逐条独立的。

**因此本文件不主张大规模合并。** 代价是真实的，收益也是真实的；用"文件数难看"作为合并理由，
会拿第 4 节的三条收益去换一张更短的目录。

## 5 规则（持久，提议写入 api-spec）

把隐含的约定写成显式规则，并把"能不能合"的判断权从"文件数"移到"物理"：

> **同族多算法必须合成一个函数 + `method=`（总纲 §6 的判据），一族一个模块；
> 不同物理问题才分模块。**
>
> 判断顺序是：
> 1. 调用的人只改一个选择参数、别的参数一个不动，拿到的是不是同一个物理量？
>    是 → 合成一族，一族一个模块，用 `method=` 选算法。
> 2. 不是 → 分开写；**分开写的函数可以放在同一个模块里**（同一个物理问题的不同侧面的
>    中间量），也可以各自开模块。
> 3. 一个模块装几个公开函数，不是判据；**一个族装几个模块，才是判据。**

第 3 条是关键补充：现行实践把"一个函数一个模块"当默认，结果把真正该管的东西
（族是不是被拆散了）掩盖了。按这条规则，`scirel.geometry.sampling` 一个模块装 14 个
不同能力是**合规**的（它们不是同族），而 `Numerics` 的四个三次样条类被拆成四个公开类
是**不合规**的（同族、只差边界条件）。

### 5.1 按实测，哪些域最可能违反

判据是可复算的：在同一个域内，把函数名按名词词干聚类，看有多少组 ≥3 个函数共享同一个
物理对象名词。组越大、越集中，越可能本该是一族。实测（`main` @ `7f1eef8c`）：

| 域 | 最大的同名词干簇 | 数量 | 判断 |
| --- | --- | --- | --- |
| `kinetic` | `fluid` | 15 | 最高风险。15 个流体色散相关函数，实测只有 `evaluate_fluid_dispersion` 带 `method=` |
| `collisions` | `hydrogen` / `section` / `elastic` | 11 / 8 / 5 | 高风险，但多数是**不同碰撞对**，按 §6.3 应分开，见族规则审计 |
| `neutrals` | `neutral` / `molecular` / `terminal` | 10 / 7 / 5 | 多数是流水线的不同阶段，不是同族；例外见族规则审计 |
| `equilibrium` | `anisotropic` / `picard` | 6 / 6 | 风险点不在数量，在签名：6 份里有 3 份写成 `(inputs=None, **kwargs)` |
| `mirror` | `mirror` / `egedal` | 6 / 5 | 同上，3 份 `(inputs=None, **kwargs)` |
| `numerics` | `cubic` / `spline` | 4 / 4 | 明确违反：四个三次样条类只差边界条件 |
| `sampling` | `locs_to_vals` | 3 | 明确违反：三个同签名函数只差插值算法 |
| `field` | `field` / `green` | 6 / 5 | 格林函数响应有候选，但物理输入不同，需逐个判 |

### 5.2 为什么现在不做批量合并

两条硬理由，都来自仓库自己的规则：

1. **改物理必须带证据、走分级评审**（[`AGENTS.md`](../../AGENTS.md) 第 2 条）。合族改的是公开签名，
   按 §6.5 会改变默认方法，属于要附新旧对比、走分级评审的改动，不是整理。
2. **候选不宜合族或不宜删除的，必须给出证据，不能强并强删。** 合并的前提是逐条证明
   "同一物理量、同一组物理输入"；证不出来的必须留在原地并写明卡点，而不是按名字相似度并掉。

所以本文件落地的方式只有一条：**先把规则写进 api-spec，让新能力不再制造新族分裂；
已有的候选逐个判定、逐条评审，不设"结构整理"式的批量合并批次。** 逐条判定的结果见同目录的
族规则审计。
