# 总纲与仓库：持久规范 vs 会漂移的状态

状态：**规范 + 迁移清单**。第 1 节的判据是持久规范；第 2 节的迁移清单是一次性盘点，搬完之后可以删。

## 0 这份文件解决什么

维护者的总纲（仓库外的一份讲解文档）要求**一直有效、尽量少改**。它现在混着两类内容：

- 不会随版本失效的**原则**：合同思想、证据链、分层原则、模型族与 `method=`、agent 优先、刻意不做的事、分级评审；
- 每次核对都会变的**状态**：有哪些领域、分发包里有什么、现在做到哪了、上一轮核对了什么。

状态写在总纲里，代价不是"多写了几行"，而是**读者无法判断哪一句还在生效**。§15.1 自己就写着"现状要逐项核验：有的旧问题已经解决，有的只搬了目录或写了规则"——一句需要读者再去核验的话，本身就已经不是规范。

处置办法：**把状态搬进仓库，让仓库承担它的时效性**；总纲只留判据和原则。

## 1 判据（持久，进总纲）

写任何一节之前先问一句：

> **下个版本它还成立吗？**

- 成立 → 持久规范 → 留总纲。
- 不成立 → 状态 → 搬进仓库（本文配套的 [状态快照](status.md) 或所属专题文件）。

三条可直接执行的判别细则：

| 细则 | 判据 | 例子 |
| --- | --- | --- |
| 数字 | 任何写死的计数都是状态 | 合同数、公开函数数、域数、测试文件数、用例数 |
| 名词清单 | 出现具体包名/模块名/文件名的成段清单，默认是状态 | §5.3 的领域清单；§9.3 的分发包内容清单 |
| 时态 | 主语是"已完成 / 正在进行 / 接下来"，或写成"本次核对到" | §15.1、§15.2、§15.3 |

"数字"这条不是本文新提的：仓库已经把它做成检查。
[`test_repository_skeleton.py`](../../tests/architecture/test_repository_skeleton.py)
的 `test_catalog_size_is_not_hand_written_into_documents` 会扫描全部 `.md`，命中
`<三位数> (admitted|public|contracts|assets|exposed|held)` 或 `共 <三位数> 份合同` 就判红。
也就是说"手写规模会漂"在仓库里已经是**被执行的事实**，而总纲作为仓库外的文件不受这道检查约束——
这正是它最容易留下过期数字的原因。

## 2 迁移清单（一次性，搬完可删）

对象是总纲现有的各节。判定为"状态"的部分按"落点"列搬进仓库；判定为"持久"的部分原样留在总纲。

| 总纲节 | 内容 | 判定 | 落点 |
| --- | --- | --- | --- |
| §5.3 现在有哪些领域 | 逐一点名的领域清单 | **状态**：域会拆（`mirror` 已拆出、`neutrals` 在讨论）、会合并、会新增 | [状态快照](status.md) 的领域表 + [代码地图](codebase-map.md) |
| §9.3 分发包里有什么 | "合同目录 / wheel / 三个使用方法 skill" | **混合**：三条箭头（合同由代码派生、索引由合同生成）是持久；具体装了哪几个 skill、包怎么构建是状态 | 持久部分留总纲；清单进 [状态快照](status.md) |
| §9.4 新版本统一交付（表格） | "各部分按什么生成或维护" | **混合**：派生关系是规范；每个生成物的当前实现是状态 | 派生链留总纲；当前生成入口进 [状态快照](status.md) |
| §15.1 当前状态 | 冻结、还债清单、"现状要逐项核验" | **状态**（冻结决定本身是维护者裁决，属于当期的约束，不是永久规范） | [状态快照](status.md)，标注冻结是当期决定 |
| §15.2 正在进行的工作 | 七个方向 × 本次核对到的状态 × 下一步 | **状态**，且已过期 | [状态快照](status.md) 或对应专题文件（如结构债务进本文配套的粒度文件） |
| §15.3 接下来 | 六条排序 | **状态**：排序会随债务清完而变 | [状态快照](status.md) |
| §15.4 为更大目标提前做哪些结构设计 | 五个问题 | **持久**：是设计判据，不是进度 | 留总纲 |
| §10 拆解线六步 | 找骨架 / 比对 / 写代码 / 测试和证据 / 打包 / 自检 | **持久**（流程）；但步骤里点名的具体脚本是状态 | 流程留总纲；脚本名进 [状态快照](status.md) |
| 全文写死的数字 | 合同数、函数数、域数 | **状态** | [状态快照](status.md)，且只以可复算的表格形式记录 |

明确**保留在总纲**、不搬走的部分：

- 核心思想（§3 每人一份合同、§4 证据与真值链、§5 分层原则、§6 模型族与 `method=`、§7 agent 优先、§8 物理正确优先于"忠于原代码"）；
- §5.5 刻意不做的事；
- §11 变异测试方法、§12 分级评审判据与开工单判据；
- §14 工程纪律；
- 参照项目的分工（结构参照 scipy、流程参照 OpenFOAM）。

判定为"持久"与"状态"的界线，就是第 1 节那一问。搬完之后，总纲里剩下的每一节都应该能通过这一问。

## 3 怎么防止总纲再次漂移

"定期回看"不算机制：它依赖人的自觉，而在一个人和一群 bot 轮班改动的仓库里，自觉一定会在某次冲刺里失效。可靠的办法只有一条：

> **总纲里凡是能机械判定的规范，都必须有一个检查器在替它站岗。**

能判定的规范不靠人读，就不会过期；不能判定的规范要**明确承认它是软规则**，而不是假装它被执行了。

现有的检查器（本节即为核对口径）：

| 规范 | 检查器 | 状态 |
| --- | --- | --- |
| 文档不得手写目录规模 | [`test_repository_skeleton.py`](../../tests/architecture/test_repository_skeleton.py) 的 `test_catalog_size_is_not_hand_written_into_documents` | 已有 |
| 文档相对链接必须可解析、不得出现私有机器路径 | 同文件 `test_markdown_relative_links_resolve`、`test_no_private_machine_paths_in_the_tree` | 已有 |
| 领域依赖只能单向、同层白名单、不得成环 | [`test_domain_dependency_conformance.py`](../../tests/architecture/test_domain_dependency_conformance.py)、[`test_domain_import_cycles.py`](../../tests/architecture/test_domain_import_cycles.py) | 已有 |
| 导入领域不得连带加载 NumPy/SciPy | [`test_domain_import_boundaries.py`](../../tests/architecture/test_domain_import_boundaries.py) | 已有 |
| 公开面必须能被文档覆盖 | [`audit_public_export_documents.py`](../../scripts/audit_public_export_documents.py) 与 [`test_public_export_document_census.py`](../../tests/architecture/test_public_export_document_census.py) | 已有 |

已知缺口（**必须在总纲里写成软规则，不能写成"已有检查"**）：

| 规范 | 缺口 |
| --- | --- |
| 合同 ID 的领域段必须等于规范模块域 | 本分支没有检查器；结构理清后由 C2 落地（`scripts/check_catalog_id_domain.py`，另一个分支在建）。在此之前只能人工核对。 |
| 合同必须记录证据来源或明确记为缺口 | [`c1_evidence_coverage.py`](../../scripts/c1_evidence_coverage.py) 只做文本统计，脚本自己写明 "Text match only, not a gate"，它给分母，不判红。 |
| 观测完整性（回执锚点、逐项测试身份） | 本分支无对应脚本，board 上仍是未决项。 |
| 模型族必须收成 `method=` | 没有任何检查器；本仓库当前的执行率见同目录的族规则审计。 |

所以对总纲的要求可以压成两条：

1. **写进去的规范，都要么有检查器，要么带一句"这是软规则，靠评审把关"。** 不写清是哪一种，就等于让人替一个不存在的门禁背书。
2. **状态不写进总纲。** 状态写进仓库文件，并在那个文件的抬头声明"本文件会随版本变"。

这两条本身就是持久的，不会因为下一批合同进来而失效。

### 3.1 反例：规范依赖签名可比，就必须要求签名可比

有一条规范在总纲里存在、却没有检查器，而且**连"能不能判断"都成问题**，值得单独记下来当反例。

总纲 §6.3 的族规则判据是：

> 调用的人只改 `method`、别的参数一个都不动，拿到的是不是同一个物理量？

这条判据**依赖签名可比**：得看得见参数，才能问"改哪个参数"。
但仓库里有 14 份公开签名带 `**kwargs`，其中 **6 份求解器的签名是 `(inputs=None, **kwargs)`** ——
参数表完全不透明，判据在这 6 份上**无法执行**，不是"判出来是分开"，而是"判不了"。

这类失败比"规范没被遵守"更糟：**没被遵守能被发现，不可判定连被发现都不可能。**
一条规范如果只写在总纲里、又落在不可判定的对象上，它就退化成了一句愿望。

所以结论不是"补一个检查器去查族"，而是先补一条**更靠前、更可判的规则**：

> **公开函数不得用 `**kwargs` 吞掉物理参数。**
> 物理输入必须出现在签名里；可变关键字只能用于传递不影响物理语义的装饰性选项，
> 而且必须在该函数的合同 `inputs` 中逐项列出。

这条规则可检查（扫描 `public_api.python.signature` 里是否出现 `**kwargs`），
而且它是族规则的前置条件：**签名不可比的地方，任何以签名为判据的规范都不成立。**
落地建议：交给 C2 的后续批次（先补检查，再逐项收口那 14 份），
不在文档批次里改代码。

一般化的写法，可以直接抄进总纲：

> 一条规范若依赖某种信息可比，就必须同时要求那种信息可比；否则规范退化为不可审计的愿望。
> 判断办法是问一句：**这条规范今天能对几个对象执行？对执行不了的对象，我们是知道的，还是不知道的？**
