# 观测完整性：一类缺陷，不是一串 bug

## 这一页解决什么

基础结项过程中出现了十六个缺陷。逐个修掉之后仍然会复发，因为它们不是十六件事，是**同一件事的十六种表面**：

> 检查的输出对"通过形状"与"失败形状"**没有分辨力**。

损失信息的观测不会报错。它把一个空格交给读者，而读者会用先验去补那一位——补出来的总是往"还好"方向的故事。这份仓库里，补位发生过四次，每次都由我自己做：

| 观测给出的 | 我补的故事 | 真实 |
|---|---|---|
| 变异账为空 | "变异全部存活" | **变异没跑起来**（`verification.tests` 里的 node id 被 `is_file()` 判成缺失） |
| `not_exercised` | "没有覆盖缺口" | **装置改不动返回值**（frozen dataclass） |
| `exit 128` 裸退出码 | "大概是超时" | **本地克隆硬链接拷贝失败**，原因被 `capture_output` 丢掉 |
| `neither` 从 69 变 85 | "合并丢了内容" | 我读的工作树**落后 5 个提交** |

四次都花了额外代价：其中一次误开了 PR #328，一次连跑六轮发布档。

## 缺陷清单与它们共同违反的那一条

| # | 缺陷 | 输出塌陷了哪两个状态 |
|---|---|---|
| 1 | 变异账为空 | 未运行 ↔ 全存活 |
| 2 | `not_exercised` 覆盖装置盲区 | 无缺口 ↔ 看不见 |
| 3 | 子进程失败只报退出码 | 原因 ↔ 无原因 |
| 4 | `neither` 被当作"没有证据" | 文本缺口 ↔ 证据缺失 |
| 5 | 覆盖工具把否定句计入依据 | 声明有依据 ↔ 明确否认依据 |
| 6 | 合同文字被当作代码行为 | 合同说 X ↔ 代码做 Y |
| 7 | 回执在 `.runtime/` | 有证据 ↔ 证据不在交付物里 |
| 8 | 陈旧工作树 | 改动丢了 ↔ 看的是旧树 |
| 9 | 单文件多记录整份取一侧 | 并集 ↔ 静默丢弃另一侧 |
| 10 | 各 zh 文件缩进不同 | 真实 diff ↔ 两千行重排 |
| 11 | 交付包用 extraction kit 校验器 | 包有问题 ↔ 用错命令 |
| 12 | 代理可重写被它判定的 oracle | 独立核对 ↔ 自证 |
| 13 | 代理自述 hash 落在自己的分支 | 已合并 ↔ 空操作 |
| 14 | "超时"修复（实际无效） | 已修 ↔ 只是看起来修了 |
| 15 | 两次消费者报告相反未被裁决 | 已定论 ↔ 未决 |
| 16 | 归因错误（把 A 的问题记给 B） | 记录正确 ↔ 记录错误 |

第 16 条是我自己的：同一条消息里把两件事分别错记给了两个代理，其中一个代理贴出 `diff` 才纠正过来。

## 从根上遏制：三态可判别

规则写在 `AGENTS.md` 第 7 条。核心一句：**每个判定的落点必须是 `pass` / `fail` / `not-observed` 之一，"未观测"要单独命名，永不并入 `pass`。**

这条不是新增教条，仓库里本来零散地做对过几处，现在把它们提升为不变量：

| 已有实例 | 它如何表达"未观测" |
|---|---|
| `dev.py` 退出码 75 | 没拿到锁，这次没有观测 |
| 变异 `UNKNOWN` 档 | 装置无效，不是"测试没走到" |
| 包内 `runtime_status=NOT_RUN` | 运行时未验证 |
| `retrieval.completeness=unknown` | 检索完备性未评估 |
| 回执 `collection_finished` | 收集是否跑完 |

配套的五条推论，各自对应上表中的一类：

1. **失败必须携带原因。** `capture_output=True` 起的子进程，失败要把 `stderr` 带进抛出的错误。机械检查：`scripts/check_observation_integrity.py`。这是第 1–3 类，也是代价最高的一类。
2. **数字必须带出处。** 引用测量时写明它测的是哪棵树、哪个 revision。第 8 类。
3. **证据必须在交付物里。** 落在被忽略目录的回执在结项时不存在。第 7 类。
4. **判据不可由被判定方书写。** 第 12 类。
5. **有损容器按记录合并。** 第 9、10 类。

## ratchet，不是全量整改

`scripts/check_observation_integrity.py` 对已存在的静默点采取 ratchet：它们记在 `tools/docs/observation-baseline.json` 里，每条带理由，**新增的一律拦下，基线只许变小**。

这条分支落地时基线记了 14 处，同轮清到 **2 处**。清掉的是四个共享 helper（`test_dev.py`、`test_check_all.py`、`test_build_extraction_kit.py`、`test_tickets.py` 里的 `_git`，被整批 fixture 复用）和各处一次性探针，改法一律是"失败时把 `stderr` 带进抛出的错误"，返回类型与既有断言不动。它们原来"紧随其后的断言会响亮失败"的说法站不住：`check=True` 时进程一失败就当场抛 `CalledProcessError`，根本轮不到下一句断言——那正是本页第 3 类缺陷本身。

剩下 2 处都在 `scripts/`：`build_catalog.py` 与 `build_pleiades_truth.py` 的 HEAD 探测把 git 失败折进同一个 `None`，与"这不是 git 检出"共用一个返回值。拆开这两种结局会让构建改为中止，属于行为变更，等维护者裁决，所以留在基线里并如实写下理由。

所以 ratchet 现在的用处是"以后新增的一律拦下"，而不是"把这批留着不管"：

- 一个永远红的检查器等于没有检查器，人们会学会忽略它；
- 清理方式写在基线文件本身：删掉一条 = 把该文件的调用点改成携带 stderr。基线数字会随时间变小，这本身就是进度。

## 什么算"修好了"

同一个测试在这条仓库里被"修好"过三次又复发三次（先是"超时"、再是"锁"、再是 `--no-hardlinks`），共同点是**修复都在不产生失败的环境里验证**。静默条件下通过只证明"这次没复现"。"已修复"是需要证据的声明，不是一次提交的自我描述。

声明"已修复"要三件齐全：

1. **一个失败率大于零的可重放装置**，并写明它的形态与条件（例："按 fixture 的真实规模跑 20 轮，失败 5 次"，而不是"多跑几次也过了"）；
2. **一段能被装置预测的机制陈述**，不是相关性。机制对不上就先别改——没解释失败形状的改动只是在赌下一次；
3. **在同一装置上连续 N 次通过**，且 N 满足 `(1−p)^N < 1%`（p 是修前失败率；p=0.25 时 N≥16）。

**首选证据是留在仓库里的一条检查，不是次数统计。** 次数统计会随时间失效：装置没了就复现不了，下次复发得从头再来。而"去掉修法必然红、带上就绿"的确定性检查不会失效。样板是 `tests/tooling/test_validate_extraction_package.py::test_the_clone_source_still_holds_loose_objects_after_the_fixture`——它钉的是**根因**（克隆期间松散对象还在），不是症状（克隆偶发失败）：带上修法 3/3 绿，把 `GIT_ENV` 里那两行配置拿掉 3/3 红。

判定落点和其余判定一样是三态，不得合并：

| 状态 | 含义 |
|---|---|
| `fixed-verified` | 三件齐全，且那条钉根因的检查已在仓库里 |
| `fixed-unverified` | 改了，但没在失败条件下验过；**不得写成"已修复"** |
| `not-fixed` | 未定因。必须写明已排除的假设、当初的复现条件、下次该从哪查 |

两条硬规矩：

- **"缓解"不得记作"修复"。** 加重试、加大超时、换 `--no-hardlinks` 都可能是对的方向，但它们不是定因；记成"缓解，未定因"，并把原因留在记录里。
- **先让失败携带原因，再谈修复。** stderr 还看不见时加的防御性改动会同时拿走诊断线索。`--no-hardlinks` 就是例子：它没修好，还让下一个读者看不出为什么没修好——真正的根因（`git commit` 留下的后台维护在克隆拷对象时把松散对象删掉）因此多藏了两轮。

## 怎么用

```sh
python3 scripts/check_observation_integrity.py .   # 新违规 → 非零退出
```

三个退出码就是三态：`0` 没有新增静默点、`1` 有新增（ratchet 只许变小）、`2` **什么都没观测到**——给出的根目录下没有 `scripts/`、`tests/` 或 `src/` 中的任何一个。最后一种以前会打印和"干净通过"一模一样的成功行，现在它有自己的名字。

判定新代码是否违反第 7 条，先问一句：**这次失败如果发生，读者能只凭输出说出"发生了什么"吗？** 说不出来，就是这一类。

## 第六类：判据本身写错

前五类缺陷都发生在**观测装置**上：子进程丢了 stderr、容器整份取一侧、把空账读成全存活。它们有一个共同点——装置是好的，是装置**丢掉的那一位**被人用先验补上了。

这一节记的是另一类：**装置运转正常，判据本身错了**。它更难发现，因为输出不像故障，像一份认真的报告。

### 实例（C4 第二轮，八条"阻塞缺口"里六条是判据错）

外部消费者只拿分发包跑 73 条冻结任务，报出 8 类阻塞缺口。维护者按真值链去复现，**6 类不成立**，错因各不相同：

| 它报的 | 实际 | 判据错在哪 |
|---|---|---|
| `matrix_size` 返回 1，与 40×40 不符 | 返回 40，与 `M.shape` 一致 | 用 `np.size(标量)` 当字段值 |
| 电荷交换速率在钳位之上偏 78% | 钳位点与之上三点同值，且带 `ApplicabilityWarning` | 比较区间选错，比在无钳位区 |
| 超导权重×2 场只放大 1.25 倍 | 逐分量正好 2 倍，偏差 `0.0` | `rel_dev(a, 2b)` 因子写反 + 张量转置 |
| 非法 `method` 应抛 TypeError | 抛 `ValueError` | `*fields` 签名重复传关键字，测的不是那条路径 |
| 缺 mesh 应在构造时抛 | 构造合法，求值时才抛 | 把"缺 mesh"绑到了错误的调用点 |
| 形状不匹配应抛 | stimulus 本身同形，正常返回 | 冻结 stimulus 无效 |
| flux→Picard 网格不兼容 | 通过，`B_R/B_Z` 与有限差分偏差 `0.0` | 一维 flux 交给二维入口 |
| `roots` 应是合法观测通道 | 合同只声明 `flux_loops/thomson/...` | 凭空发明了一个接口 |

修订后的数字：`package_sufficient` 43/30 → **47/26**，判据 191/77/5 → **196/66/7**，跨域 0/6 → **1/6**。

### 由此确立的规矩

1. **"外部消费者报了缺陷"不是缺陷成立的证据。** 维护者的第一动作是**用对方记录的最小参数复现**，不是开工单。工单的前提是事实成立；给审核人一张基于误报的工单，比不开单更糟。
2. **报告必须自带可粘贴的最小复现调用。** 含全部字面参数、不依赖报告者内部状态。做不到这一点的判定，只能算线索，不能算缺口。
3. **判据错了要留痕，不许静默删改。** 原判定保留，紧接复核结论与错因分类。删掉误报等于让下一个读者重犯同一遍。
4. **区分"库错了"与"我看错了"要靠第三方复现，不靠报告者的自信。** 这次六条误报，报告者当时的措辞都很确定。
5. **降级不是消灭。** 复核后仍成立的三条（合同声明命名输出而入口返回裸值、44 个声明字段只回 9 个、3-D 笛卡尔与 2-D 网格无适配）都保留，只是严重度按"能不能只用合同拿到值"重排。

一句话：**损失信息的观测不会报错，写错判据的观测会报错——报的是假错。** 两者都要靠同一条防线拦：任何人报出的缺陷，都要能在别人手里复现。
