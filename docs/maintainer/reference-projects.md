# 参照项目：scipy 是结构参照，OpenFOAM 是流程参照

状态：**持久规范**。本文件说明两个外部项目各自约束我们的哪一部分、哪些做法**不采用**。
它不随版本失效，因此可以放心引用；具体进度和规模一律指向 [状态快照](status.md)。

## 0 一句话

> **结构参照 scipy，流程参照 OpenFOAM。**

这两个词常被当成口号，落不到具体决定上。本文件把它们拆成可对照的条目：
scipy 管"这个库长什么样"，OpenFOAM 管"能力怎么被造出来、怎么被验收"。

**边界先说清楚：** 两者都是**参照**，不是依赖，也不是要模仿的完成度。

- 不是依赖：运行依赖里没有它们的位置，它们出现在这里只是因为我们要向读者解释设计来由。
- 不是完成度目标：scipy 有二十年的模块划分和社区规模，OpenFOAM 有完整的求解器平台；
  我们既不打算、也不需要变成它们那样。参照的是**决定**，不是**体量**。
- 不是兼容目标：我们不实现 scipy 的 API，也不读 OpenFOAM 的算例格式。

## 1 scipy 作为结构参照

### 1.1 scipy 的实际形态（实测，不是印象）

口径定义（本文件所有 scipy 数字都按此口径，可逐条复算）：

- **模块**：子包目录下递归的、文件名不以 `_` 开头的 `.py` / `.pyx`；
- **公开名字**：`[n for n in dir(subpackage) if not n.startswith('_')]`；
- 版本：scipy 1.18.1（仓库开发环境里已安装的那份）。

| 子包 | 模块 | 公开名字 | 名字/模块 |
| --- | --- | --- | --- |
| `ndimage` | 14 | 81 | 5.8 |
| `stats` | 56 | 316 | 5.6 |
| `signal` | 33 | 170 | 5.2 |
| `special` | 79 | 366 | 4.6 |
| `fft` | 12 | 42 | 3.5 |
| `interpolate` | 21 | 65 | 3.1 |
| `linalg` | 40 | 114 | 2.9 |
| `integrate` | 23 | 39 | 1.7 |
| `spatial` | 17 | 24 | 1.4 |
| `optimize` | 76 | 84 | 1.1 |
| `sparse` | 78 | 70 | 0.9 |
| `cluster` | 4 | 3 | 0.8 |
| `io` | 33 | 22 | 0.7 |
| **合计** | **486** | **1396** | **2.9** |

另一套口径（把私有的 `_*.py` 也算进模块，只数模块顶层 `def`）会得到 **539 模块 / 1674 个顶层公开名字 ≈ 3.1**；
两套口径的合计数一致（2.9 ≈ 3.1），差别只在分母含不含内部实现文件。
引用时必须带口径，否则同一份 scipy 会被数成两倍差异。

**两套口径的差异来源（第三个人据此判断该信哪个）：**

- 本文件这套数的是"**用户可能看到的公开面**"：`dir(pkg)` 里的非下划线名字 ÷ 该子包内非下划线的 `.py/.pyx` 文件。
  分子是用户真能 `import` 到的名字，分母是"一定程度上可被直接阅读"的实现文件；
  私有实现文件（`_basic.py`、`_impl.py`）不计入分母，因为用户不会去那里找东西。
- 交叉口径把 `_` 开头的实现文件也算进分母，并且只数模块顶层 `def`（不含通过 `__init__` 重新导出的名字）。
  分母变大、分子变小，所以除 `special` 这类两者恰好同值的子包外，交叉口径的比值普遍更低。
- 逐子包差距最大的是 `cluster`（0.8 vs 17.0）：这类子包由极少数公开模块 + 大量私有实现组成，
  两套口径对"分母"的理解在这里分岔最严重。
- **该信哪个**：讨论"模块粒度是否合理"时用本文件这套，因为问题问的是**用户看到的公开面怎么组织**；
  讨论"实现文件有多少"时用交叉口径。两者都不该被当成"scipy 的模块数"这种唯一事实。

**三条可用的结论：**

1. **合法区间宽，不是单点。** 实测每个模块承载 0.7–5.8 个公开名字；另一套口径给出 1.2–17.0。
   无论哪套，"一个模块装几个函数"在 scipy 里本来就是一个**跨一个数量级的区间**，
   不存在"标准答案"这种值。
2. **落在地板上的子包，都是"一模块一格式/一对象"。** `io`（0.7）一个模块一种文件格式；
   `cluster`（0.8）、`sparse`（0.9）也是一模块一类对象。文件格式和数据结构天然独立，
   所以聚合度低**合理**。
3. **按子主题组织的子包，聚合度高。** `special`（4.6）、`stats`（5.6）、`ndimage`（5.8）
   都是"一大类数学对象 + 若干变体"，一个模块装一族。**这正是总纲 §6 想让我们长成的样子。**

我们的对应数字是 **1.28 个合同/模块**（口径见 [状态快照](status.md)）。
这个值**落在 scipy 的地板上**，不是"明显超标"。所以正确的结论不是"我们模块太多"，
而是：**1.28 通常意味着把一个子主题摊成了平铺列表**——`neutrals` 33 份合同近乎严格 1:1，
等于把"物理模型族"当成了"文件格式"来组织；它本该更像 `special` 或 `signal` 那样按子主题成组。

> 判断粒度是否合适，问的永远是"这一族该不该在一起"，不是"文件数是不是比别人多"。
> 详细的代价、收益和落地规则见 [模块粒度](module-granularity.md)。

### 1.2 scipy 里 `method=` / `kind=` 的实际用法

这是一种**很窄但很硬**的约定：一个函数能在同一组输入上换算法时，用参数选，而不是换函数名。

| 调用 | 选择参数 | 合法值（实测） | 默认 |
| --- | --- | --- | --- |
| `scipy.integrate.solve_ivp(..., method=...)` | `method` | `RK45` `RK23` `DOP853` `Radau` `BDF` `LSODA` | `RK45` |
| `scipy.interpolate.CubicSpline(x, y, bc_type=...)` | `bc_type` | `not-a-knot` / `natural` / `clamped` / `periodic` / 指定导数 | `not-a-knot` |
| `scipy.interpolate.interp1d(x, y, kind=...)` | `kind` | `linear` `nearest` `zero` `slinear` `quadratic` `cubic` … | `linear` |

三条可观察的规律：

1. **选择参数的名字随"选择的是什么"而变。** 选算法叫 `method`，选插值阶数叫 `kind`，
   选边界条件叫 `bc_type`。不是所有地方都叫 `method`——名字要说明被选的东西是什么。
2. **换算法不换返回值形状。** `solve_ivp` 换 `method` 之后结果对象的字段不变；
   `CubicSpline` 换 `bc_type` 之后仍是同一个"可调用的分段三次多项式"。
   这就是"同一个物理量"的软件版本。
3. **默认值是设计决定，不是随便挑的。** `RK45` 做默认、`not-a-knot` 做默认，文档都要能说出为什么。

### 1.3 逐条对照我们的做法

| scipy 的做法 | 我们现在的做法 | 一致还是不一致 |
| --- | --- | --- |
| 按数学领域分子包，单向依赖 | 按物理领域分 L0–L5 六层，依赖只能往下走，且有导入方向检查 | **一致**（分层更细，因为物理领域比数学领域多） |
| 一个模块装一组相关名字（2.9 个/模块） | 1.28 个合同/模块，即 scipy 的地板层 | **不一致**，见 [模块粒度](module-granularity.md) |
| 公开面是扁平命名空间，用户不必知道文件布局 | 合同 ID 承诺"按 ID 能推测模块位置"，但 `scirel.sampling.*` 等 ID 实际在 `scirel.geometry` 下 | **不一致**，是已知结构债务（C2） |
| 同族换算法用参数选，不换函数名 | 有做得对的样板（等离子体色散函数一个函数带四种算法、介电响应一个函数带三种算法），但整体执行率低 | **部分一致**，逐条判定见同目录的族规则审计 |
| 选择参数名随语义变（`method` / `kind` / `bc_type`） | 有 `method=`、`model=`、`family=`、`selector=`、`jcase=`、`*_mode=` 等多种写法并存 | **不一致**，应先统一语义命名再谈收族 |
| 默认值是设计决定，文档说得出理由 | 合同要求写清默认方法的依据与代价（总纲 §6.5） | **一致**，而且比 scipy 更严：我们要求逐条给证据 |

### 1.4 测试密度：比模块粒度偏离更大，但**不能照 scipy 对齐**

| 指标 | scipy 1.18.1 | 我们 |
| --- | --- | --- |
| 测试文件数 | 338 | 412 |
| 测试文件 / 模块 | 338 / 486 ≈ **0.70** | 412 / 230 ≈ **1.79** |

我们的测试密度是 scipy 的 2.5–2.8 倍。但**这个差距是对齐不了的，也不该对齐**，原因不是"我们的测试太多"：

- **scipy 的测试是行为回归。** 它证明"改完之后没有变"，正确性主要靠文献与长期社区使用。
- **我们的测试里有一半承担的是独立证据。** 闭式解对照、精确有理重算、高位 mpmath 对照、
  守恒恒等式、变异测试——这些不是回归，是**真值链的第一环**。删掉它们，
  合同就只剩"代码现在是这样"。

所以结论是**记账方式要改**，不是数量要改：报告测试规模时必须把"证据测试"和"行为测试"分开计数，
混在一起的那个总数既吓人又没有信息量。分类口径见 [状态快照](status.md)。

### 1.5 索引结构：比模块粒度更值得改的一处（待改进项，不改代码）

scipy 的公开面是**少模块、多名字**：`special` 用 79 个模块导出 366 个公开名字，
`stats` 用 56 个模块导出 316 个。用户在 `scipy.special` 这一层看到的是一个**扁平命名空间**，
层级全部留在内部——他要找的东西由**名字**提示，而不是由**目录**提示。

我们是**多模块、少名字**：合同分摊到各域，平均每个域只有十几个合同。
用户看到的不是一个命名空间，而是一张需要检索的表。

差别落在检索上：

| | scipy | 我们 |
| --- | --- | --- |
| 用户靠什么缩小范围 | 命名空间层级 + 名字（`special.jv`、`stats.t`） | 合同检索 + `capability-index` |
| 检索质量 | 不需要检索（名字本身就是索引） | 取决于索引结构 |

C5 的独立消费者刚做过一轮实测，我们的检索是 **`lexical-and`，`completeness: unknown`**：
只会按词面 AND 命中，给不出"这一族还有哪些变体"，也无法声明结果是否完整。

**待改进项（记录，不在本次改代码）：** 问题不在"模块太多"，而在
**索引里缺少 scipy 那种"按子主题聚合"的一层**。因为缺这一层，一个子主题被摊成平铺列表，
检索只能退回词面匹配。要改的是索引结构（让每个域内部先有子主题，再由子主题挂合同），
不是文件数。这条与 [模块粒度](module-granularity.md) 是同一个问题的两面：
**族的划分既是代码结构问题，也是检索结构问题。**

### 1.6 我们**不**向 scipy 学的地方

- **不学它的公开面规模。** `special` 有数百个公开名字，那是几十年、几十个贡献者的积累。
  我们的约束是每条能力都有合同、证据和适用范围，规模必须让证据链跟得上。
- **不学它的版本兼容策略。** scipy 要对外部用户保持兼容；我们的规矩是一条规范只留一份实现，
  不留别名、不留双读路径。改就改到位，同步消费者。
- **不学"函数即文档"的省略。** scipy 靠 docstring；我们的 docstring 只是合同的投影，
  合同的物理依据、适用范围、失败行为是独立的、可被门禁检查的产物。
- **不把它的测试密度当目标。** 见 §1.4。

## 2 OpenFOAM 作为流程参照

### 2.1 OpenFOAM 是什么，"流程参照"指什么

OpenFOAM 是一个**求解器平台**：用户写算例（字典文件 + 网格），选一个求解器，平台把它跑完。
它曾经遇到的工程问题和我们很像——**独立求解器越来越多，彼此重复**。

它的解法分三层：

1. 物理模型做成**分层库**；
2. 同一族模型共用**一个基类接口**，按名字在**运行时选择**；
3. 一个**通用算法骨架**调度可插拔的物理模块。

外加一条容易被忽略的工程细节：**选错模型名时，报错会列出全部合法名字。**

### 2.2 我们借用它的哪一部分：准入、验收、回归

OpenFOAM 真正值得借的不是它的代码结构，而是它**怎么防止能力变多之后失控**这套工程流程。
它的源码树把职责分得很清楚：`src`（库）/ `applications`（求解器与工具）/
`tutorials`（给人看的演示案例）/ `test`（**验证单个模型**的案例）/ `etc` / `bin` / `doc`。

对应到我们的三条线（拆解 → 合并 → 出库）：

| OpenFOAM 的工程做法 | 我们的对应 | 说明 |
| --- | --- | --- |
| 同族模型共用接口，按名字选择 | 模型族约定 + `method=`（总纲 §6） | 借的是"不留一族多入口"这条纪律 |
| 选错名字报错列出全部合法名字 | agent 优先报错规范（总纲 §7.1） | 借，且是硬要求：报错必须带合法值清单 |
| 构建系统列出可选模型 | 由合同生成的族索引与检索入口 | 借"索引从权威内容生成"，不另维护一份函数清单 |
| **`tutorials` 与 `test` 分开** | 我们的 `examples/` 需要分两类 | **待改进项**：现在 `examples/` 混着两种东西——`c4-usage-acceptance`、`c5-delivery-acceptance` 是验收测试；`negative-demo-*` 是给人看的演示。用途不同，验收标准也不同：前者要可复跑、有回执，后者要能读懂 |
| **案例即回归资产** | `examples/c5-delivery-acceptance/` | 已经是这个方向：记录 sha256 与复跑命令，案例**可执行**，不是文档。这是我们的做法，值得在 README 里写清 |
| **MMS / 制造解作为验证手段** | 真值链的"证据"一环 | **方法论出处**，见 §2.3 |

### 2.3 MMS 与我们的真值链是同构的

OpenFOAM 社区把 exact solution / manufactured solution 当作求解器验证的标准手段：
先造一个已知的精确解，代进方程得到源项，再让求解器把这个精确解解回来。
**判据不是"结果看起来对"，而是"结果能不能对上那个已知的精确解"。**

这与我们的真值链是同一套思想，只是我们没把它写成方法论：

| MMS 的做法 | 我们的对应 |
| --- | --- |
| 造一个已知精确解 | 闭式解、解析恒等式、守恒量 |
| 用它生成源项/边界 | 构造能让恒等式成立的输入 |
| 解回来比对 | 精确有理重算、高位 mpmath 对照、容差有依据的数值比较 |
| 判据是"对上精确解" | 判据是"合同说法背后是证据"（真值链第一环） |

**所以"证据测试"不是我们发明的洁癖，而是一个成熟工程社区对"求解器可信"的标准答案。**
这一点应该写进 README 的证据一节，作为方法论的出处，而不是当作内部规范。

落到具体的门槛上，就是 [`supply-pipeline.md`](supply-pipeline.md) 的分级评审与
`tickets/` 的人工裁决流程：**新能力不是"写完了"就进库，而是"能被独立验收"才进库。**

### 2.4 我们**不**采用它的哪一部分

这一段是本节的重点，因为最容易走偏：

| OpenFOAM 的做法 | 我们的决定 | 理由 |
| --- | --- | --- |
| 用户写字典文件、选求解器、由平台跑完 | **不采用**：不要求用户改用另一套配置语言 | 总纲 §5.5 明确：研究任务的总体流程由用户程序负责 |
| 全局时间循环调度一切 | **不采用**：不提供全局运行框架 | 提供零件，不组装整道题 |
| 应用框架（`applications`）为交付单位 | **不采用**：交付单位是库 + 合同 + 分发包 | 装进去的是一个可 `import` 的库 |
| 求解器 = 可执行文件 | **不采用**：一个能力是一个可调用函数 | 用户在自己的程序里调用，不启动我们的进程 |
| `tutorials` 里的算例直接当产品示例发布 | **部分采用**：演示与验收分开维护 | 见 §2.2 的待改进项 |

一句话概括边界：**OpenFOAM 是应用框架，我们是函数库。**
借它的工程纪律，不借它的运行方式。

### 2.5 哪些"组合零件"仍然可以进库

总纲 §5.5 留了一个口子，这里要说清口径，否则"不建框架"会被误读成"不许组合"：

- **可以进库**：有明确输入输出、有自己的合同与直接测试的可复用组合零件
  （例如多线圈加权叠加、一个有明确输入输出的平衡求解步骤）。
- **不进库**：装配整道研究题的部分——采用哪些假设、怎样准备装置数据、如何安排整个模拟、
  输出什么报告。这些属于用户程序。
- **判断口径**：这个组合是"用户会重复用到的标准组件"，还是"某个具体研究题的编排"？
  前者进库，后者留在用户程序。组合进库时，**必须补上元件之间新增的单位、坐标、
  适用假设和失败路径检查**——几个元件各自正确，不构成它们组合之后正确。

## 3 两条参照线互不越界

| | scipy 参照 | OpenFOAM 参照 |
| --- | --- | --- |
| 管什么 | 库的**形状**：分层、模块粒度、公开面组织、选择参数的用法、索引层级 | 能力的**生产流程**：准入、验收、族纪律、案例分类、验证方法论 |
| 不管什么 | 不规定我们怎么造能力、怎么验收 | 不规定我们的代码怎么分层、模块怎么分 |
| 一旦混用会怎样 | 拿 scipy 的模块数当验收标准 → 为了少文件而强并强删 | 拿 OpenFOAM 的平台形态当目标 → 开始造配置语言和运行框架 |

混用这两条线是本项目最容易犯的错，也是最难自察的错：两者都会伪装成"向优秀项目看齐"。
判断办法只有一条：**这条建议改变的是库的形状（scipy 域），还是能力的生产流程（OpenFOAM 域）？**
改错域的建议，一律不接。

## 4 怎么用这两条参照线：先查上游，再定标准

第 1、2 节是**结论**（scipy 的结构、OpenFOAM 的流程）。这一节是**动作**：遇到约定问题时怎么走，
以及依据要长什么样。规则本身写在 `AGENTS.md` 第 8 条。

### 4.1 哪些问题必须先查上游

| 问题 | 先看谁 | 看什么 |
| --- | --- | --- |
| 角度、频率、波数等**单位** | `scipy.spatial.transform`、`numpy` | 默认单位是什么；要另一种单位靠开关还是靠参数名 |
| 参数**开关**形状（`degrees=`、`method=`、`kind=`） | scipy | 布尔开关 vs 字符串枚举，默认值取哪个 |
| **返回形状**（裸值 / 元组 / `Result` / 映射） | scipy 的同类函数 | 单值就返回单值，多值才打包 |
| **异常类型**（`ValueError` vs 自定义） | scipy、numpy | 无效输入用什么；自定义异常是否进入公开命名空间 |
| **命名**（`*_deg`、`helper` 前缀） | scipy、numpy | 有没有一致的前后缀习惯 |
| **数值**方法的容差与收敛判据 | scipy、OpenFOAM | 默认容差量级、按什么量判收敛 |

### 4.2 怎么测（必须真跑，不看印象）

在项目解释器里跑，不要在脑内推断：

```sh
python3 scripts/dev.py run python -B -c "
import scipy, inspect
from scipy.spatial.transform import Rotation
print(scipy.__version__)
print(inspect.signature(Rotation.as_euler))"
```

### 4.3 依据要长什么样

引用块里必须同时有**版本**和**输出**：

```
scipy 1.18.1  from_euler(seq, angles, degrees: bool = False)
              as_euler(seq, degrees: bool = False)
numpy         np.deg2rad / np.rad2deg —— 弧度是默认单位
```

一段真实的走法（2026-11-18，角度单位）：

- 第一次调用写错了 `seq`（只有单个轴），scipy 抛 `ValueError: Expected 3 axes, got z`；
- **如果停在这里，结论会是"scipy 没有约定"**——而实际是参数用错了；
- 改成三轴再跑，才拿到 `degrees: bool = False` 这个默认值。

**所以：一次跑失败不等于上游没有约定。** 先确认自己调对了，再下结论。这一条与
[观测完整性](observation-integrity.md) 是同一条原则在"查上游"上的实例。

### 4.4 上游没有约定时

不要发明。按 `AGENTS.md` 第 8 条：**先不暴露**，并把"为什么没暴露"写进 `known_limitations`
或工单（若属于需要人判断危害的那两类）。
