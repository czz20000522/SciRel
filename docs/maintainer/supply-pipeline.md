# 三线闭环：拆解工具包、拆解包格式与本地人工工单（设计提案）

状态：**已采纳**（issue #158，维护者 2026-11-11 决定，见第 11 节）。

采纳后，规则会拆到真正被执行的地方：

- 拆解方法 → 精简后的拆解 skill；
- 拆解包格式和工单格式 → 校验脚本；
- 本文只保留"为什么这样设计"。

分层、模型族和接口规范见 [physical-modularity.md](physical-modularity.md)，本文不重复。

## 1. 问题：三条线彼此割裂

拆解线产出后就归档了，合并线可能隔很久才消费。合并线发现不合格时已经找不到生产者，只能自己重写。现在要还的债就是这种割裂留下的：

- **来源的形状被原样带进库里。** 例如 `Device(mesh=None, **kwargs)`、`get_gpsi(R, Z)`、`compute_greens(rzw, rz_pts)`。
- **同一个物理关系有两份合同。** `electromagnetism.circular-filament-green` 和 `field.circular-filament-green`。
- **装置数据被当成了能力。** 例如 `WHAM()`、`BRB()`。
- **物理问题在入库之后才被发现。** 见 #10。

还有两个结构性原因：

- **拆解包不是最终形态。** 原来的 D0–D3 阶段包、`contracts/admission` 的 FINAL 绑定都在证明"字节没被改过"，没有证明"内容能直接用"。
- **人工审核挡在主路上。** 早期规定入库就要人工审核，人的带宽却远远跟不上。

## 2. 主线与可选增强

```text
主线：    来源材料 ─▶ 拆解线 ─拆解包─▶ 合并线 ─▶ 分发包 ─▶ 出库线
可选增强： 题库（定向拆解、额外的隐藏测试）；出库线的缺口信号（影响拆解方向）
旁路：    人工工单（异步裁决，不阻塞主线）
```

- **合并线只消费拆解包。** 拆解包的格式（第 5 节）是两条线之间唯一的约定。
- **题库是独立资产，不是主线上的一环。** 可能来不及出题，也可能只需要某个项目里的一项能力，所以拆解线必须能在没有题库时独立完成。有题库时，拆解线优先拆有题的能力，并把题目的隐藏测试当作额外的验收依据。
- **出库线通过"缺口信号"影响拆解方向**，不直接给拆解线派任务。

## 3. 拆解工具包：冻结版 SciReL 随 skill 分发

拆解在独立工作目录中进行，来源材料与库代码分开保存。工作目录中放一份**拆解工具包**，它随拆解 skill 一起分发：

| 内容 | 作用 | 复用现有的 |
| --- | --- | --- |
| 冻结版 SciReL（某个 commit 的 git 副本，含源码、catalog 和查询工具） | 拆解者手上**总有一份合同**，可以先比对、再取补集；新实现在这个版本上运行测试 | `scripts/build_extraction_kit.py` |
| 规范文档（api-spec、分层与模型族、本文第 4、5 节） | 拆解者按 SciReL 的最终形态写代码 | `skills/development/scirel-code-style/` |
| 拆解包校验器 | **与合并线使用同一套检查**：结构、api-spec、合同 schema、测试、变异测试 | `scripts/validate_extraction_package.py`（已替代原 FINAL 准入校验） |

工具包里的冻结版本**不是为了直接开 PR**，而是为了让拆解者的产物格式不出错，并且手上永远有合同可以比对。

**校验器不通过，拆解包就不能归档。** 合并线的验收前移到了生产者还在的时候，相当于出厂检验。

## 4. 找骨架

拆解不是来源里有什么就拆什么。

**要的：** 能脱离来源程序独立复用的物理关系。它要有明确的模型假设、单位和适用边界，能放进 L1–L5 的某一层，并且换一个装置依然成立。

**不要的：**

| 类别 | 处置 |
| --- | --- |
| 画图、文件路径、命令行、来源的流程编排（驱动循环） | 不拆 |
| 包装类、来源特有的组织方式 | 不拆，只拆它包住的物理关系 |
| 与物理无关的工具 | SciPy 已有的直接用 SciPy；确实需要的放进 `numerics` |
| 装置数据 | 作为参考数据（第 8 节），不算能力 |
| 冻结版合同里已有的关系 | 不重复拆；实现有差异时，记一条物理疑点（走工单或 #10 那类审查） |

**方法：**

1. 从来源的入口、示例和配套论文出发，沿着主计算路径往下追。主路径上的物理关系链就是**骨架**。例如 Pleiades 的骨架是：细环 Green 函数 → 线圈场叠加 → Grad–Shafranov 平衡的 Picard 迭代。
2. 只需要某一项能力时，从这项能力出发，往下追它的依赖链，只拆这条链。
3. 主路径以外的关系，只有在能独立复用时才拆。
4. 每个关系都要和冻结版合同比对，结论只能是四种之一：**已有**、**某族的新 method**、**全新**、**不收**。
5. 来源中每一个没拆的部分，都在 `disposition.md` 里写一行：属于哪一类，理由是什么。这样"有意不拆"和"漏拆"可以区分开。

## 5. 拆解包格式

拆解包是基于冻结版 SciReL 的补丁，加上说明材料：

```text
<拆解包>/
  PACKAGE.md          任务、冻结版本（commit）、范围、完成状态、未完成项（续拆的入口）
  patch/              基于冻结 commit 的 git format-patch 或 git bundle：
                      src/、tests/、catalog/ 都已按 api-spec 写成最终形态
  manifest.md         每项能力：合同 ID、领域、层、族、比对结论（第 4 节第 4 步的四类之一）
  evidence/<能力>.md   每条测试预期值的来源：解析 / 文献 / 守恒 / 来源输出；
                      只有来源输出作为依据的，必须显式标出
  disposition.md      来源中每个没拆的部分：分类和理由
  tickets/            需要人工裁决的工单（第 7 节）
  private/            来源身份、源码对照、许可证（不进入公开仓库，见 RULES.md）
```

要求：

- **能续拆。** `PACKAGE.md` 加上整个拆解包，必须足以让一个从没见过这个任务的 agent 接着干下去。
- **只装需要的东西。** 不装 D0–D3 阶段的过程材料、自引用的字节计数或多层摘要绑定。真正需要的身份信息只有一个冻结 commit 和补丁本身。
- **证据带分母。** `manifest.md` 统计"拆了几项、不收几项、有疑点几项"，和 `disposition.md` 的行数对得上。

## 6. 合并线：只判题和评审，打回就续拆

1. 把补丁 rebase 到最新的 main。机械冲突（路径或名字已经变了）由合并 agent 处理。
2. 跑校验器和完整检查。有题库对应题目的，加跑隐藏测试。
3. 独立评审，按第 7 节分级。
4. **不合格就打回，不代为重写。** 打回的方式是：把归档的拆解包和缺陷清单交给一个新的拆解工作目录，由新的 agent 续拆。所有 agent 本来就是短命的，所以不需要去找原来的拆解者。

## 7. 人工审核：分级，并且异步

### 7.1 分级

| 级别 | 情形 | 谁审 | 是否阻塞 |
| --- | --- | --- | --- |
| A 机械 | 改名、移动、文档、工具 | agent 交叉预审，再由 reviewer 终审 | 否 |
| B 有证据 | 新增，或改变数值结果，并且有独立证据（文献、推导、解析极限），隐藏测试和变异测试都通过 | 两个独立的 agent 评审，结论一致 | 否 |
| C 人工裁决 | ① agent 之间有分歧，而且双方都拿不出决定性证据；② 有多种合法约定，需要选定一种；③ 范围决定（收不收、删不删、冻结或解冻）；④ 只有"与来源一致"一种证据，而且影响面大 | 物理专业的审核人 | **否**：先执行安全默认，再排队 |

**安全默认：** 按 [RULES.md](../../RULES.md) §6 的三级阶梯执行，不另立一套——① 不改数值，收窄声明范围并加域外告警（`ApplicabilityWarning`）；② 范围也界不清，就在合同 `known_limitations` 里标 UNKNOWN、保留现行行为；③ 越界会给出错误结果又无法告警，就拒绝该输入。新增能力一律先不合并。

### 7.2 工单格式

一张工单是一个 md 文件，存放在本仓库的 `tickets/<kind>/<id>.md`，按工单类型分目录存放。这样合并者可以直接起草工单，Git 提供历史记录和并发合并。维护者定期把待审工单导入本地平台，交给物理审核人，平台再把裁决写回文件。

- **状态只写在 frontmatter 里。** 状态变化时不移动文件，避免目录和字段出现两份互相矛盾的状态。列出待审工单用工单脚本（M3），不靠目录。
- **本仓库是公开的。** 工单不能写来源项目的身份、私有路径或未公开的材料。需要对照来源时，写"见拆解包 `<包名>` 的 `private/`"，由审核人在平台侧取得。工单脚本和 pre-commit 扫描会检查这一条。

```markdown
---
id: T-YYYY-NNNN
kind: physics-dispute          # physics-dispute | convention | scope | evidence-gap
status: open                   # open → decided → applied → closed
assets: [<合同 ID>]
default_applied: <已执行的安全默认，一句话>
options: [A, B, C]
reviewers_required: 2
decisions: []                  # 平台写入：[{reviewer, option, rationale, date}]
resolution: null               # 平台写入：最终选项
applied: null                  # agent 写入：{by, ref, date}
---

## 要决定的问题
## 选项（每个选项写清依据和影响）
## 各方意见（为什么现有证据说服不了对方）
## 不决定的后果（即已执行的安全默认）
```

正文必须做到：**审核人只读这一页就能做出决定，不需要打开任何其他文件。**

### 7.3 状态与读写权限

| 状态 | 写入方 | 写入的字段 |
| --- | --- | --- |
| `open` | agent（创建时同时执行安全默认） | 正文、`options`、`default_applied` |
| `decided` | 平台（`reviewers_required` 个审核人意见一致后） | `decisions`、`resolution` |
| `applied` | agent（执行完裁决结果后） | `applied` |
| `closed` | agent（核对无误后） | — |

- 每个字段只有一方能写。平台只写裁决字段，agent 只写其余字段。
- 审核人意见不一致时，工单保持 `open`，由平台标记为"人工分歧"，安全默认继续生效。agent 不能从分歧的意见里挑一个来执行。
- 校验脚本检查 frontmatter 的结构和状态流转。非法流转（例如跳过 `decided` 直接 `applied`，或 agent 写了裁决字段）一律判红。

### 7.4 裁决怎样回到 agent

1. **开工第一步是查工单。** AGENTS.md 的路由里写明：开工先列出 `decided` 状态的工单，先处理它们。
2. **工单自带全部上下文。** agent 只读这一张工单就能执行，不依赖任何会话记录。
3. **会重复用到的裁决要沉淀成规则。** 例如某种约定的选择，执行裁决时一并写进 api-spec 或合同。之后同类问题直接按规则处理，不再开工单。
4. **平台可以更换，协议不变。** 真正的约定是这个文件格式和状态机。

## 8. 装置数据

- 物理函数只接收显式的几何输入（例如一组线圈的 `r, z, 电流, 匝数`），不认识任何具体装置。
- 常用装置作为**参考数据**随包提供，做成可以修改的默认配置，例如 `scirel.datasets.load_device("wham")`。返回的是普通数据，用户可以复制后修改，也可以完全使用自己的数据。每份数据都标注来源和版本。
- 参考数据不算能力，不做物理审查，只核对来源是否属实。
- 现有的 `WHAM()`、`BRB()`、`TREXCoil` 等类迁移成这种形式。

## 9. 规则放在哪里

| 规则 | 位置 | 执行方式 |
| --- | --- | --- |
| 拆解包结构、manifest 与 disposition 的分母对账 | 拆解包校验器 | 检查 |
| 补丁内容符合 api-spec、合同 schema、测试通过 | 同一个校验器，复用仓库现有的检查 | 检查 |
| 变异测试 | 校验器 | 检查 |
| 工单格式与状态流转 | 工单校验脚本 | 检查 |
| 找骨架、比对的四类结论、处置分类 | 精简后的拆解 skill | skill |
| 审核分级、安全默认 | `RULES.md` §6（正文），合并线 skill 只引用 | 规则 |

## 11. 维护者决定（2026-11-11）

- **工单存放：** 放在本仓库的 `tickets/` 下，按类型分目录；维护者定期上传给审核人。不另开仓库。
- **参考数据：** 使用 `scirel.datasets` 命名空间。
- **冻结版 SciReL 随 skill 分发：** 拆解者手上总有一份合同，所以"只有源码、没有合同"的情形不再出现。冻结版本的作用是保证拆解产物的格式正确，不是为了直接开 PR。
