# 物理模块化、领域分层与 agent 优先接口（设计提案）

状态：**已采纳**（维护者 2026-11-11 决定，见第 10 节），issue #145。本文给出目标结构、理由和迁移顺序。

采纳后，规则会搬到真正被读、被执行的地方：

1. 能由机器判定的，做成 `tests/architecture/` 下的检查。
2. 判定不了的，写进做这件事时必然会读到的 [`scirel-code-style` skill](../../skills/development/scirel-code-style/references/api-spec.md)。

同一条规则不在两处各写一份。规则搬走之后，本文只保留"为什么这样分"，具体规则以检查和 skill 为准。

## 1. 定位

SciReL 是独立的 SciPy 式科学库，不附属于任何求解系统或 agent 平台。

| 要做 | 不做 |
| --- | --- |
| 按物理划分的领域子包，依赖方向清楚 | 求解框架、配置语言或运行时驱动 |
| 每个公开函数的行为、单位、适用范围和失败方式都写进合同 | 替用户把整道题组装好 |
| 让只有上下文记忆、生命周期很短的 agent，仅凭安装好的包就能找到、用对函数，并看懂报错 | 依赖聊天记录、私人笔记或"维护者都知道"的隐性知识 |

组装整道题由用户或 agent 自己写程序完成（见 [ARCHITECTURE.md](../../ARCHITECTURE.md) 的 outbound line）。库要做的，是让零件拼得起来，而且拼错时一定会报错。

## 2. 参考 OpenFOAM：借什么，不借什么

OpenFOAM 曾经出现独立求解器越来越多、彼此重复的问题。它的解法分三层：

- 物理模型做成分层库；
- 同一族模型共用一个基类接口，按名字在运行时选择；
- 一个通用算法骨架（`foamRun`）调度可插拔的物理模块（`fluid`、`solid` 等）。

另外，选错模型名时，报错会列出全部合法名字。

| OpenFOAM 做法 | SciReL 对应 | 是否借用 |
| --- | --- | --- |
| 库按物理分层，依赖单向 | 领域分层表 + 导入方向检查（第 4 节） | 借 |
| 同族模型共用接口、按名字选择 | 模型族约定，SciPy 的 `method=` 风格（第 5 节） | 借 |
| 报错列出合法选项 | agent 优先报错规范（第 7 节） | 借 |
| `foamToC` 列出可选模型 | 由合同生成的族索引和 `describe`/`search`（第 7.4 节） | 借 |
| 配置文件语言、全局时间循环 `foamRun` | 属于用户程序 | **不借**：库只提供零件 |

## 3. 现状中的结构问题

下面这些问题都能从仓库直接复算。数字不抄进本文，只写问题的性质和复算方法。本提案 PR 的描述里附有 `e7fa1bba` 当时的快照。

1. **`closures` 和 `kinetic` 互相依赖。** 两个方向的导入都写在函数体内，所以绕过了模块顶层的导入检查：
   - `closures/mirror_quasineutral_closure.py` 导入 `kinetic.mirror_*`；
   - `kinetic/grid_mirror_kinetic_closure.py` 导入 `closures.mirror_*`。

   这两条边牵涉的都是磁镜物理。把磁镜代码拆进 `mirror` 领域后，环会自然消失。
2. **"两个领域不得相互依赖"这条规则没有执行。** 它只写在 api-spec 里。`test_domain_import_boundaries.py` 只检查导入领域时是否会加载 NumPy 或 SciPy，不检查领域之间的依赖方向。
3. **`kinetic` 是大杂烩。** 它同时装了波与色散、中性粒子输运、磁镜约束、Saha 平衡等，合同数接近全库一半。
4. **`geometry` 是第二个大杂烩。** 除了等离子体几何（通量面、场线、网格映射），它还装着与物理无关的数值工具：插值、基函数、非均匀差分、多项式拟合、截断 SVD 逆。
5. **合同 ID 的领域和包路径对不上。** `scirel.sampling.*`、`scirel.fieldline.*`、`scirel.basis.*`、部分 `scirel.numerics.*` 实际都在 `scirel.geometry` 下；部分 `scirel.electromagnetism.*` 实际在 `scirel.configurations` 下。agent 按 ID 推测模块位置会找不到。
6. **有些根级私有模块带着物理含义。** `_mirror_numerics` 被 `closures` 和 `kinetic` 共用，它实际属于磁镜领域。`_framework_compositions` 不属于任何领域。
7. **测试大量导入私有模块。** 判据：如果只改一个私有实现，就得同时改测试，说明测试依赖了实现而不是合同，边界在漏。测试应该通过公开 API 断言合同上的行为。

复算方法：用 AST 遍历 `src/scirel/**/*.py` 的全部 `import` 和 `from ... import`，包括函数体内的，按 `scirel.<第一段>` 归到领域。这件事要做成第 9 节 P0 的检查脚本，**脚本目前还不存在**。

## 4. 领域分层

### 4.1 分层表（提案）

| 层 | 领域 | 职责 | 不允许出现 |
| --- | --- | --- | --- |
| L0 私有基础 | `_result` `_validation` `_numerics` `_optional` | Result 类型、输入校验、通用数值工具 | 任何物理名词 |
| L1 数学与数值 | `numerics`（物理无关工具的唯一共享位置，按数学主题分子包，见 D3） `fvm` `io` | 插值、基函数、差分、拟合、线性代数、有限体积、文件格式 | 等离子体物理量 |
| L2 局部物理关系 | `physics` `collisions` `fusion` `dielectric` `plasma` | 点态物理量：特征尺度、库仑对数、截面、反应率、介电张量 | 场分布、输运求解 |
| L3 几何与场 | `geometry` `electromagnetism` `field` `configurations` | 通量面、场线、网格映射、真空磁场、线圈、器件数据 | 动理学或输运 |
| L4 物理子系统 | `kinetic` `neutrals`（新） `mirror`（新） `neoclassical` `closures` `source` | 一类物理现象自己的模型 | 跨子系统的耦合迭代 |
| L5 耦合与反演 | `equilibrium` `diagnostics` `inference` | 跨子系统组合、残差、参数估计 | 被更低层引用 |

### 4.2 依赖规则

1. 领域只能依赖比自己更低的层。
2. 同一层内的依赖必须在下面的白名单中显式列出，并且不能成环。没列出的就算违规。
3. 统计依赖时，函数体内的导入和模块顶层的导入一样算。
4. 根级私有模块只能放与物理无关的工具。带物理含义的私有代码放进所属领域，写成 `<domain>/_*.py`。
5. 跨领域只能引用对方的公开名字（对方 `__all__` 里的名字），不能引用对方的私有模块。

同层白名单（提案，迁移时按实测结果修订）：

| 层 | 允许的同层依赖 |
| --- | --- |
| L3 | `field → electromagnetism`，`configurations → electromagnetism`，`electromagnetism → geometry` |
| L4 | `mirror → closures`，`mirror → kinetic`（若实测需要） |
| L5 | `equilibrium → diagnostics`，`inference → diagnostics` |

### 4.3 为什么这样分

- **有一张单向的分层表，agent 才能推理出该去哪里找。** 例如，要算一个截面，只需要去 L2 找。
- **单向依赖让正确性可以分层建立。** 下层验证通过后，上层只需要验证自己新增的那部分关系。这对应 [ARCHITECTURE.md](../../ARCHITECTURE.md) 里"组合只有在节点合同都成立时才可公开"的要求。
- **拆分的依据是物理，不是文件数**（api-spec 已有这条）。`neutrals` 和 `mirror` 之所以要拆出来，是因为它们各自有完整的假设集合，和 `kinetic` 的假设集合不同：`neutrals` 是中性粒子在电离和电荷交换下的输运，`mirror` 是磁镜中的不变量分布、端损失和双极电势。

## 5. 模型族

### 5.1 定义

**模型族**是用不同模型或拟合计算同一个物理关系的一组函数。例如：H 的电荷交换截面有多种拟合；同一类波的色散关系有冷等离子体、热等离子体、广义几种模型；压力闭合有几种不同假设。

这相当于 OpenFOAM 中"同一基类下的不同运行时可选模型"。

### 5.2 约定（提案）

1. **一族一个入口。** 用 `method=` 关键字选择模型，和 `scipy.optimize.minimize`、`scipy.integrate.solve_ivp` 一致。`method` 的取值是封闭集合，默认值在合同里写明并说明理由。
2. **物理输入的签名一致。** 同一族的函数使用相同的物理参数名、单位和轴序。某个模型独有的参数是 keyword-only，传给不支持它的模型时报 `TypeError`。
3. **Result 键一致。** 同一族返回同一组键。某个模型不提供的量不出现在 Result 里，也不填 `nan`。
4. **适用范围按模型分别声明。** 每个 `method` 在合同里有自己的适用范围。超出范围时的行为（报错或警告）按第 7 节执行。
5. **族归属由人决定，写进合同。** 合同新增一个 `family` 字段，记录族名和 `method` 名。族索引由合同生成，不提交进 Git。

族归属是人做的判断，属于需要提交的事实；族索引是机器算出来的结果，每次构建时重新生成。

### 5.3 什么时候不该合成一族

如果两个模型的物理输入不同（例如一个需要温度，一个需要完整的分布函数），说明它们回答的不是同一个问题，应该保持为两个函数，在 See Also 里互相引用。不要为了凑成一族，引入"有的模型用、有的模型不用"的物理参数。

## 6. 组合

- **公开组合属于它所在的最高层领域。** 例如磁镜 Hall 平衡属于 `equilibrium`。`_framework_compositions` 应当解散。
- **组合也必须遵守显式参数规则（#3）。** `_composition.compose` 目前把输入当作 mapping 传递。它可以作为私有的连线工具保留，但不能把 mapping 暴露到公开签名上。
- **从来源图提升为公开组合，沿用 [ARCHITECTURE.md](../../ARCHITECTURE.md) 的五条提升条件，本文不重复。**

## 7. agent 优先的接口规范

agent 没有人类工程师那样的旁路能力：它记不住意图，不会打开 IDE 追代码，看到"太容易就绿了"也不会起疑。**库给出的反馈中，凡是需要靠人类旁路能力才能读懂的，到了 agent 手里都会悄悄失效。**

### 7.1 报错

报错消息要让 agent 不翻源码就知道下一步该做什么。必须包含：

1. **哪个参数**：参数名。
2. **违反了什么条件**：例如有限、正值、形状 `(n_r, n_z)`、单位为 eV。
3. **实际收到的是什么**：形状、dtype、取值范围或违约元素的数目。不要打印整个数组。
4. **合法的是什么**：封闭选项集要列出全部合法值，数值约束要给出范围。
5. **去哪里查**：合同的 asset ID。

例子：

```text
ValueError: method='lindsay' is not a charge-exchange fit; valid methods are
'janev', 'lindsay-stebbings', 'barnett'. See contract
scirel.collisions.atomic-hydrogen-charge-exchange-cross-section.
```

（例子里的方法名只是示意，不代表实际实现。）

异常类型沿用 api-spec：`ValueError`、`TypeError`、`FloatingPointError`，以及各领域已有的子类。规则是：**库内不允许捕获异常后换成默认值继续运行。**

### 7.2 超出适用范围

- **结果会错得没有任何迹象时**，报错。
- **结果仍有一定意义、但精度下降时**，发出警告。警告使用统一的 `scirel.ApplicabilityWarning`（`UserWarning` 的子类，新增）。这样 agent 和用户可以用 `warnings.filterwarnings("error", category=...)` 把它升级成错误。目前警告用的是裸 `UserWarning`，无法和其他来源的警告区分。
- **警告消息必须说明**：哪个量、合法范围、实际取值、对结果的影响（偏高还是偏低，有多严重），以及合同 ID。
- **静默截断或静默外推一律禁止。** 每次截断都要么报错，要么警告。

### 7.3 不收敛与状态

迭代求解器的返回值带 `success`、`status`、`message`，和 SciPy 的 `OptimizeResult` 一致。不收敛的结果不能看起来像收敛了。具体是报错还是带状态返回，由合同的 `failure_semantics.nonconvergence` 决定。

### 7.4 自描述

agent 应当只靠安装好的包和分发包，就能从问题一路找到函数：

| 问题 | 入口 |
| --- | --- |
| 有哪些领域、各管什么物理 | `scirel` 根模块的 docstring：分层表，由本文第 4 节生成 |
| 这个领域有哪些模型族和函数 | 各领域 `__init__` 的 docstring，由合同生成，不手写 |
| 某个函数的完整合同 | `describe`/`search`/`get`（[PURE_CONSUMPTION.md](../../tools/docs/PURE_CONSUMPTION.md)） |
| 报错时该查哪份合同 | 报错消息里的合同 ID（7.1） |

能从合同生成的内容不手写；手写的内容不写可以从仓库算出来的数字。

### 7.5 规模：函数上千之后 agent 怎么找

目标是覆盖聚变领域除量子以外的几乎所有方向，公开函数会增长到数千甚至上万。到那时，平铺的清单和全文搜索对 agent 都不可用：上下文装不下，近似命中又会把不适用的函数当成可用。这是从一开始就要按 OpenFOAM 的方式分层的根本原因。

检索按层级逐步收窄，每一层的候选数量都有上限：

```text
领域（L0–L5 分层表）→ 子领域 / 模型族 → 族内 method → 完整合同
```

1. **每层规模有上限。** 一个领域的直接子项（子领域、族和独立函数之和）超过上限时，必须按物理拆分出子领域，不能继续平铺。上限是多少待定，见 D6。这条规则做成检查。
2. **每层都能单独列出。** 列出一个领域，只返回它的子领域和族的一行摘要，不返回函数全文。这和 `browse` 的卡片预算是同一个思路。
3. **搜索结果带路径。** 每个命中都给出 `领域 → 族 → method` 的完整路径，agent 能从路径回到上一层，看看同族里还有哪些选项。
4. **族是主要的检索单元。** agent 先找到"要算的是哪个物理关系"（族），再根据适用范围选模型（method）。上千个函数会收敛成数量少得多的族。

### 7.6 合同 ID 与包路径一一对应

合同 ID `scirel.<domain>.<name>` 中的 `<domain>`，必须等于该函数的规范模块所在的领域。由检查强制执行。这样 agent 看到 ID 就能直接定位到模块，反过来也一样。

## 8. 规则放在哪里

| 规则 | 放在哪 | 执行方式 |
| --- | --- | --- |
| 分层表、同层白名单、不能成环、函数体内导入也算 | `tests/architecture/` 新检查 + api-spec 的领域表 | 检查失败就判红 |
| 根级私有模块不得带物理含义；跨领域只能引用公开名字 | 同上 | 检查 |

| 测试不导入私有模块（例外须写明原因） | 检查，附例外清单 | 检查 |

## 9. 迁移顺序

先定结构，再统一接口，最后补文档。如果反过来做，#3、#2、#1 在旧位置做完之后，一拆分又得重做一遍。

| 阶段 | 内容 | 对应 issue | 完成判据 |
| --- | --- | --- | --- |
| P0 | 写领域依赖检查，先只报告不判红，输出当前违规清单；维护者确认分层表 | 新开 | 检查在完整检查路径上实际运行，输出列出全部边 |
| P1 | 拆出 `mirror`：磁镜代码从 `kinetic` 和 `closures` 移入；`_mirror_numerics` 移入 `mirror` | #8 | `closures ↔ kinetic` 的环消失 |
| P2 | 拆出 `neutrals` | #8 | `kinetic` 只剩波与动理学理论 |
| P3 | 把 `geometry` 中与物理无关的工具移入 `numerics`（见 D3）；对齐合同 ID（见 D2） | 新开 | 7.6 的检查通过 |
| P4 | 依赖检查从"只报告"改为判红 | 新开 | 违规清单为空 |
| P5 | 按族划分；然后按族逐个推进显式参数、命名 Result 和 numpydoc | #3 #2 #1 | 每做完一族，该族的合同、签名、Result 键一致 |
| P6 | 报错与警告规范按族推进；新增 `ApplicabilityWarning` | 新开 | 族内所有报错都满足五要素 |

每个阶段都是一个或多个独立 PR，接口工作不改变数值结果（#9 的规则）。如果迁移中发现结果疑似有误，停下来在 #10 记录，不要顺手修。

## 10. 维护者决定（2026-11-11）

- **D1 分层：采用。** 六层够用，因为扩展发生在层内，而不是靠增加层数：能力增长时，在层内增加领域、子领域和模型族，层数不变。关键是依赖像水流一样只往下走。将来如果出现跨越整个装置的集成建模（例如全装置的输运加平衡耦合），可以在 L5 之上加一层，但不能打破"只往下"这条规则。`closures/discrete_vector_feedback` 是控制律而不是物理闭合，迁移时移出 `closures`；它的去处在拆分 PR 里按实测依赖决定。
- **D2 合同 ID：由代码决定。** 代码是唯一锚点，合同由代码派生，所以合同 ID 的领域段必须等于函数规范模块所在的领域。发布前直接改 ID，不留别名，也不维护 ID 到模块的映射表。由 7.6 的检查强制执行。
- **D3 物理无关工具：集中放进一个共享位置。** 所有与物理无关的数值工具（插值、基函数、差分、拟合、线性代数）统一放进 `scirel.numerics`，供所有领域使用。为了避免它变成新的大杂烩，内部按数学主题分子包（例如 `numerics.interpolate`、`numerics.basis`、`numerics.differentiate`、`numerics.linalg`），子包结构在迁移时按实测确定。SciPy 已有等价功能的，直接调用 SciPy，不再包装一个公开函数，除非 SciReL 的版本在合同上确实有不同的约定。
- **D4 模型族：一个入口加 `method=`**，与 SciPy 一致。现有的布尔选择器（例如电荷交换截面的 `freeman=`）也迁移成 `method=`。
- **D5 `ApplicabilityWarning`：新增。** 按 7.2 的规则执行。
- **D6 渐进式披露是原则，上限是手段。** agent 从不一次读完所有能力，而是按"领域 → 子领域或族 → method → 完整合同"逐层读取，每层只读当前需要的那一支。每层的规模上限只是为了保证"一层能一次读完"，具体数值先实测再定，测出来之前不做强制检查。

## 11. 方向：把 SciReL 当作一门科学语言的标准库

SciReL 加上 Python，可以看作一门科学计算语言：公开函数相当于标准库，合同相当于类型签名（端口、单位、形状、适用范围、失败行为），用户或 agent 写的程序相当于用这门语言写的代码。[ARCHITECTURE.md](../../ARCHITECTURE.md) 的 "From Python package toward a scientific language" 一节已经预留了这个方向：将来可以有一个"编译器"或静态检查器，在运行前检查用户程序的单位、形状和适用范围是否匹配。

现在不做这个检查器（能力边界冻结，先还债），但它反过来约束当前的设计：

1. **约定一致就是语法。** 命名动词、参数顺序、Result 键、`method=` 这些规则越一致，这门"语言"越好学。agent 学会一族，就会用整族。
2. **合同要逐步变成机器可读的类型。** 现在合同里的 `shape`、`constraints` 是自由文本（例如 `"any (scalar or array)"`）。检查器需要结构化的形状和约束。新写或重写合同时，优先写成可以解析的形式。具体的 schema 改动等检查器真正立项时再定，现在不预先设计。
3. **少量正交、可组合的原语，胜过大量相似的函数。** 这和模型族、渐进式披露是同一个方向。
