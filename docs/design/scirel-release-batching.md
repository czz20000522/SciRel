# SciRel 发行批次策略

SciRel 的工作树持续演进，发行物按批次切出。一次函数修复、一次性能优化或一次失败语义加固都先进入 Git 历史，默认不立即构建 wheel、重做文档快照或更新 `release/CURRENT.json`。这样可以把一段时间内相互关联的改进作为一个候选统一验收。

“大版本”在这里指公开 `major.minor` 发行线的变化。只有下面的情况才需要进入新的发行线：

- 能力闭包发生大量新增或删减，改变 SciRel 面向用户的主要科学范围；
- 公共 API、TaskGraph 组合、输入输出或失败合同出现不能保持兼容的变化；
- 核心依赖基线、Python/ABI 支持线、平台承诺或分发形态发生整体变化；
- schema、catalog 身份或许可边界发生需要重新解释历史资产的变化。

同一 `major.minor` 发行线内，累计的实现修复、数值稳定性修正、性能优化、边界失败修复和少量向后兼容能力可以合并成一次 `patch/post/dev` 候选。版本号在候选切出时只推进一次；不会因为每个函数改动而单独发布。

候选切出前，工作树的状态是 **post-candidate development**：`release/CURRENT.json`、外部 wheel、文档快照和平台回执继续指向上一个已绑定提交，Git 中的后继提交只表示待收批次。开发期可以运行受影响测试和局部 API/依赖审计，但不得把工作树代码描述成当前已发布 wheel 的内容。

当维护者决定切候选时，按一次批次完成以下动作：冻结确切 Git 提交；根据累计改动选择下一个 `patch/post/dev` 版本；批量更新受影响 exact documents 和 selection；从同一提交构建 wheel、文档快照和平台回执；运行发行对齐、clean-venv、公共 API 和 capability gates；最后一次性更新 `release/CURRENT.json`。候选未通过时继续在 Git 中修正，仍不覆盖旧外部产物。

纯文案、导航、翻译或示例排版可以只推进同一发行线的 `documentation.version`。它不能增加能力；如果改动触及科学定义、公共 API、默认值、失败语义、依赖或任务图，就并入下一实现候选批次。

需要立即切候选的例外只有会影响现有用户安全使用或结果可信度的高风险修复，例如已证实的错误结果、数据损坏、严重依赖漏洞或必须尽快撤回的公开合同。普通小修继续积累，直到达到批次边界。
