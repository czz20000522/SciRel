# SciRel 发行批次策略

SciRel 的工作树持续演进，发行物按批次切出。函数修复、性能优化或失败语义加固先进入 Git，
不因为一次提交就构建 wheel、重做文档快照或更新 `release/CURRENT.json`。维护者在一批改动达到
可交付边界后，再统一冻结、验证和发布。

日常只判断两层版本：

| 变更类型 | 版本处理 | 何时做完整发行 |
| --- | --- | --- |
| 大范围新增/删减科学能力或 TaskGraph；不兼容的公共 API、输入输出或失败合同；核心依赖、Python/平台/分发边界整体变化；schema、catalog 或许可边界需要重新解释 | 推进新的能力线 `major.minor` | 立即按新能力线冻结一次候选 |
| 兼容的实现修复、数值修正、性能优化、内部重构、边界失败修复，以及少量向后兼容能力 | 留在同一能力线，累计为一次维护批次（`patch` 或 `dev`） | 达到批次边界时一次性发布 |

第一行必须同时满足“属于列出的变化”且影响公共能力或兼容边界；修改一个函数本身不会触发新的
能力线。Git 提交数量也不决定版本号，`devN` 只在切出候选时推进一次。PEP 440 的 `post` 仅用于
同一已发布版本的打包或元数据修正，不作为日常科学改动的发布等级。

同一能力线内，维护批次可以包含任意数量的兼容改动。批次切出时，wheel、文档 selection、平台
回执和 `release/CURRENT.json` 从同一确切提交统一生成；wheel 与文档必须绑定相同的能力 ID、数量
和实现版本。这样既不会为每个函数重复完整门禁，也不会让文档声明超出实际 wheel 闭包。

候选切出前，工作树的状态是 **post-candidate development**：`release/CURRENT.json`、外部 wheel、
文档快照和平台回执继续指向上一个已绑定提交，Git 中的后继提交只表示待收批次。开发期可以运行
受影响测试和局部 API/依赖审计，但不得把工作树代码描述成当前已发布 wheel 的内容。

当维护者决定切候选时，按一次批次完成以下动作：冻结确切 Git 提交；根据累计改动选择下一个维护
版本；批量更新受影响 exact documents 和 selection；从同一提交构建 wheel、文档快照和平台回执；
运行发行对齐、clean-venv、公共 API 和 capability gates；最后一次性更新 `release/CURRENT.json`。
候选未通过时继续在 Git 中修正，仍不覆盖旧外部产物。

纯文案、导航、翻译或示例排版可以只推进同一能力线的 `documentation.version`。它不能增加能力；
如果改动触及科学定义、公共 API、默认值、失败语义、适用域、依赖或任务图，就并入下一维护批次，
并和新的 wheel 候选一起发布。

需要立即切候选的例外只有会影响现有用户安全使用或结果可信度的高风险修复，例如已证实的错误结果、
数据损坏、严重依赖漏洞或必须尽快撤回的公开合同。普通小修继续积累，直到达到批次边界。
