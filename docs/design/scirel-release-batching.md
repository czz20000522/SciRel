# SciRel 发行批次策略

SciRel 的工作树持续演进，发行物按批次切出。函数修复、性能优化或失败语义加固先进入 Git，
不因为一次提交就构建 wheel、重做文档快照或更新 `release/CURRENT.json`。内部开发没有自动的
“批次边界”；只有 owner 明确要求外部交付、候选切出或公开发布时，才进入统一冻结、验证和发布。

日常只判断两层版本：

| 变更类型 | 版本处理 | 何时做完整发行 |
| --- | --- | --- |
| 大范围新增/删减科学能力或 TaskGraph；不兼容的公共 API、输入输出或失败合同；核心依赖、Python/平台/分发边界整体变化；schema、catalog 或许可边界需要重新解释 | 下一次切候选时推进新的能力线 `major.minor` | 决定对外切出该批次时，按新能力线冻结候选 |
| 兼容的实现修复、数值修正、性能优化、内部重构、边界失败修复，以及少量向后兼容能力 | 留在同一能力线，累计为一次维护批次（`patch` 或 `dev`） | owner 明确切出该批次时一次性发布 |

第一行必须同时满足“属于列出的变化”且影响公共能力或兼容边界；“大范围”按公共能力闭包和兼容
边界判断，不按文件数、代码行数或 Git 提交数判断。修改一个函数本身不会触发新的能力线。Git
提交数量也不决定版本号，`devN` 只在切出候选时推进一次。PEP 440 的 `post` 仅用于
同一已发布版本的打包或元数据修正，不作为日常科学改动的发布等级。

同一能力线内，维护批次可以包含任意数量的兼容改动。只有进入
`release_freeze`，wheel、文档 selection、平台回执和 `release/CURRENT.json` 才从同一确切提交
统一生成；它们绑定同一冻结 manifest 的成员关系和派生计数。计数属于该 revision，不是项目永久
不变量。这样既不会为每个函数重复完整门禁，也不会让文档声明超出实际 wheel 闭包。

验证强度按变更影响选择，不把每个小改动都升级为完整发行门禁：

- 日常 Git 提交只运行受影响的单元、算子和 TaskGraph 测试；不构建 wheel，也不更新当前候选回执。
- owner 明确切出维护批次时，统一运行受影响测试、发布对齐、安装包公共 API 和主验证平台的 clean-venv 检查，
  然后一次生成 wheel、文档 selection 和绑定记录。
- 只有改变核心依赖、Python/平台边界、分发资源、公共能力闭包或跨平台行为时，才扩大到完整平台矩阵、
  依赖闭包和相应的 native capability 门禁。

这些层次只决定验证范围。wheel 与文档的同源、闭包和计数绑定只在候选/发布工件实际生成时适用；
开发期的当前目录和文档计数随 Git 工作树变化。

候选切出前，工作树的状态是 **development**：`release/CURRENT.json`、外部 wheel、
文档快照和平台回执继续指向上一个已绑定提交，Git 中的后继提交只表示待收批次。开发期可以运行
受影响测试和局部 API/依赖审计，但不得把工作树代码描述成当前已发布 wheel 的内容。

当维护者决定切候选时，按一次批次完成以下动作：冻结确切 Git 提交；根据累计改动选择下一个维护
版本；批量更新受影响 exact documents 和 selection；从同一提交构建 wheel、文档快照和平台回执；
运行发行对齐、clean-venv、公共 API 和 capability gates；最后一次性更新 `release/CURRENT.json`。
候选未通过时继续在 Git 中修正，仍不覆盖旧外部产物。

纯文案、导航、翻译或示例排版可以只推进同一能力线的 `documentation.version`。它不能增加能力。
如果文档改动触及科学定义、公共 API、默认值、失败语义、适用域、依赖或任务图，先判断兼容性：
兼容的合同或实现变化并入下一维护批次并和新的 wheel 候选一起发布；不兼容或导致能力闭包大范围
变化的内容，在下一次切候选时推进新的 `major.minor` 能力线。

上述编辑改动也按批次处理：单次文字修订不单独生成文档 receipt、不触发 wheel 构建或平台门禁。
只有 `release_freeze` 才推进 `documentation.version`、生成文档 receipt 并更新
`release/CURRENT.json`；只要科学合同和能力闭包没有变化，候选可以复用相同 wheel 字节。

需要立即切候选的例外只有会影响现有用户安全使用或结果可信度的高风险修复，例如已证实的错误结果、
数据损坏、严重依赖漏洞或必须尽快撤回的公开合同。普通小修继续积累，直到 owner 明确切出候选。
