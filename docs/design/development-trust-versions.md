# 开发、待审与可信版本

本文规定开发、最终待审与可信版本的边界。普通 Python 开发包不以人工批准为前置条件；workflow 管理最终审核与发行绑定，不管理每次开发提交。阶段方法见 [开发流程](../development-process.md)。

这些状态属于项目开发与治理层；用户安装的科学包不加载审核状态或来源快照。
不同版本在隔离分支/worktree 构建，发行身份绑定确切提交、所选内容、运行依赖和实际 wheel 摘要，
不由分支名、路径或单独的版本字符串决定。主线可以是开发基线，只有确切发行满足可信/发布门禁。
项目与包、历史归档及工作树规则见 [开发项目与科学包交付](project-and-distribution.md)。

## 内容去向与版本边界

首先区分尚未合入的拆解/修正产物、内部待审科学包、已发布稳定包。拆解产物可以忠实保留上游错误、
试验实现及未决科学问题，供 D2 调查；这些材料不能因为位于开发分支或标记 `.dev` 就自动进入科学包。
内部包也只纳入当前证据支持其声明合同准确的内容；最终人工审核和稳定发行仍是独立决策。
以下开发、冻结待审与可信状态描述合格内容的版本演进，不给未解决错误开设入包例外。

- **开发版**：Agent 可以在隔离分支中对照保存的 L1、上一可信版本及全部未发布候选，完成科学比较、去重、变体判断、代码与 TaskGraph 整合、exact document、测试和内部 wheel 验证。进入科学包的内容须满足下述准入规则；被隔离的实验材料可以单独复现。开发版不因能运行而获得专家认可或公开发行资格。
- **冻结待审版**：从某个确定的开发提交形成专家实际审阅的代码、文档、测试与证据快照。进入审核后，实质变更另成待审版本；不能在专家审阅的内容背后改写同一版本。
- **可信版**：专家根据上一可信版到待审版的累积科学差异、适用域和证据作出认可后，记录该认可所绑定的精确版本。发布还须满足许可证、依赖、完整资产文档和发行验证；认可不等于自动发布。

## 准入与人工注意力分开决定

按确切资产版本及其公开合同范围裁决，不给整项目一张通行证，也不把算法复杂度或模型自报信心
当作正确率。D1 源码一致性回答“是否忠实”，D2 独立依据回答“声明是否成立”，二者不能互相替代。
对未解决的正确性疑点按不可信处理，但不把没有证据的部分描述为已经证实错误。

下表约束入包时机，不削减 D2 修复职责。确认错误后由 Agent 调用科学实现、验证和独立审查 skill
完成修正；隔离是修复期间的状态，不能作为可修复问题的默认终点。只有必要调查后仍无法理解行为
或形成有依据且可验证的修正时才科学暂缓；临时执行故障保持待续，不等同科学不可修复。
人工正常审核的是修正后的确切实现，并看到原表现、判错依据、改动和最终验证结果，负责拍板而非代为实现。

| 证据状态 | 内部待审包准入 | 人工审核重点 |
| --- | --- | --- |
| 声明范围有适用的依据与验证，多轮 AI 审核无未决正确性冲突 | 可纳入；仍保留待人工审核身份 | 简洁呈现合同、依据与改动，可显式批量确认确切条目 |
| 保留范围有支持，扩展边界或完整性覆盖不足，未发现推翻保留范围的证据 | 可限定范围纳入；docstring/注释及使用合同显著声明限制 | 对应算子/图审查文档突出未覆盖项、影响及需拍板问题 |
| 已知或有证据支持的疑似错误、数值对照冲突、关键依据缺失而无法支持声明，或 AI 对正确性分歧未解决 | 隔离在未合入产物；阻止同范围依赖链入包 | 先由 AI 补证/修正；仍需领域判断的争点优先交人工 |

“限定范围”须有科学或计算意义上的独立支持，不能只挑通过的样例、放宽容差或把失败输入改名为
不支持来消除反证。须在实现、导出、依赖、正式合同和安装包上确认错误分支不会作为合格功能被调用；
能可靠检查的前提由接口拒绝越界输入，其余条件显式给出。无法安全分离时整个受影响资产暂不纳入。
仅添加警告、保留 xfail 或改成私有名字不足以放行。兼容旧错误的复现实现留在拆解/研究材料中。

人工注意力按后果严重性、证据独立性及覆盖缺口、数值敏感性、模型假设、变更幅度和依赖传播范围
分配。高影响但证据充分的内容可以准入，同时仍需重点审核；简单算法若存在反例也必须隔离。
不以单一加权分数或 AI 多数票抵消正确性阻断。TaskGraph 除继承所用范围的依赖限制，还审查单位、
连接、状态/顺序和组合产生的新风险。聚合按共同科学争点或依赖根因进行，逐项版本绑定不能丢失。

送人前由作者完成自检，再由独立 AI 挑战合同、实现及证据；有发现则修正/补证并按受影响范围复核。
记录每轮目标版本、角色、依据、分歧与处置，避免同一依据的重复赞同冒充独立验证。
审核深度随风险调整，达到有依据的稳定结论后停止；仍有正确性争点则隔离并提交明确问题，
不无限循环，也不把人类当日常调试员。方法见[基于证据的审核注意力](../../skills/extraction/scientific-operator-review/references/evidence_based_review_attention.md)。

每个最终保留的新增/改变候选都要有人工最终决定，低注意力不等于免审。批量确认须明确列出
所覆盖资产、版本和限制；未受影响且已获批内容可引用既有决定。批准、拒绝或要求补证都保留绑定。
人工意见本身不能抹去反例或补造测试：调整合同或实现后形成 successor，验证相关变化再准入。
稳定发行仅选择获批、依赖闭合且完成发行检查的确切内容。

### 遗留失败与待决事项先由 AI 分流

“与基线具有相同失败项”只证明没有增加这些回归，不证明失败已修复、科学合同成立或整库可发行。
送人前，接收 owner 将每个失败（可按同一根因分组并列出全部成员）绑定到确切实现、测试与环境，
形成有证据的处置及下一责任方：

- 缺少测试工具或依赖：补齐开发验证环境，保留原失败，用原断言重跑；不能记成科学错误或要求人工判断。
- 科学结果、合同或测试相互冲突：AI 先调查并做独立计算。实现有误走科学修正；若测试仍描述已被科学修正取代的旧行为，须引用已接受的修正依据，保留旧测试与失败，在后继中提供独立科学依据和审查，不能仅改期望值消除红灯。
- 候选范围外的失败：以实际 wheel、导出和传递依赖证明不受影响，为原范围登记修复 owner、下一动作与重查条件；允许无关的合格开发增量继续，但整库失败仍未关闭。
- 无法在现有证据下解决的科学争点：列明已做调查、缺失事实、影响、备选结论与 AI 建议，再提出具体人工裁决问题。

许可也先形成 AI 的证据审查：绑定来源版本、实际随包代码/数据/依赖和许可原文，分别说明内部使用、
再分发所需条件、已满足条件、缺口及建议。泛称“许可待人审”不是这项工作的完成标志；AI 分析和用户
科学认可都不能替代权利人的授权。许可缺口只阻断对应使用或分发范围，不自动阻断无关的科学验证。

只有上述调查、可完成修正和独立复核完成后，才把准确限定的候选与剩余问题送给人工最终拍板。
人工待审、候选技术完成、接收方验收、canonical 合入和公开发行应分别记录，不能相互代替。

## 统一发布索引

该索引按不可变条目累积已登记的开发快照，不保证覆盖每个新候选；当前候选自身以 `release/CURRENT.json` 绑定。
SciRel 的单一开发期索引位于 `provenance/release-index.dev.json`，按不可变的确切版本记录
未发布开发快照、待审候选及最终发布结果。`development` 条目绑定实际 catalog/wheel 字节、
来源资格、证据和 D3 去向；完整文档闭包不表示来源合格。候选条目
指向冻结的 Git、拟发行资产及依赖闭包、exact documents、初始待审版本和有效证据；后续审核
revision 逐项关联到该候选，发布条目再绑定实际
catalog、wheel、许可决定与发行验证。返工产生关联的 successor，不改写前一个条目或批准记录。
对同一候选后来取得的宿主开发验收使用 `evidence` 追加条目，绑定原候选和本地精确证据记录；
它不产生新候选、审核 revision 或批准状态，也不把单项目导出扩张为全部未发布候选盘点。
候选的 `initial_revision` 是初始待审 artifact 摘要；后续逐项 successor 和当前审核状态须从工作台
实际 artifact/投影核对。r43 的候选去向是工作台审核，不能把较早 dev5 wheel 的 D3 manifest
当作其审核去向。`pending_unapproved` 只表示未批准；`mixed_unverified` 不蕴含 D1 合格。
r43 的 `bounded_d1` 仅属于 13 个保留 item，不外推到同轮 132 项混合来源开发快照。
历史 52 项快照不回填、不重审，也不成为索引门禁。
发布条目前须从逐项批准 revision 验证候选代码、测试和实际结果确实对应固化的 Git 与 wheel；
仅把这些材料显示在审核投影中不足以证明发行内容同一。
索引只选择和绑定版本，不复制资产的科学字段；科学合同仍以 exact document 为准，catalog 是所选
内容的发现投影，单次 release manifest 是构建绑定。CodeFusion 只读取 SciRel 给出的状态，不自行
从 wheel 文件名、catalog 覆盖率或 Git 标签推断发布。

开发期 `pending_unapproved` 快照可供 D3 运行，但不因构建成功自动成为已批准候选或已发布版本。
公开版本指针只在确切候选的批准闭包、许可、依赖、构建和发行检查通过后更新。当前没有已批准的
公开基线，也没有真实批准的发布条目。现有 `.dev` 索引注册器可冻结待审 item 版本，但还没有把
真实候选登记为可信或发布事实；其字段可随首条真实闭环调整，正式发布前连同相关版本和合同冻结为 `v1`。

索引由 D2 集成 owner 单写。D2 负责候选身份、逐项处置、来源资格、冻结 Git/artifact 和
科学验证证据；出库 owner 提供确切 wheel/catalog 消费绑定、D3 manifest 与去向证据，由 D2
核对摘要后追加到同一索引。新快照用 `scripts/release_index.py --snapshot-id` 登记，
最终待审项用 `--item-artifact` 登记；两者均以当前索引作 `--existing-index` 输出新文件，
核验旧条目逐字未变后再更新仓库索引。后续证据或返工形成新版本/投影，不回写旧条目。
宿主开发验收用 `--review-host-evidence` 和 `--candidate-entry-id` 追加，不把宿主项目字段写入资产科学合同。

当前 r81/dev58 与 r43/dev5 是两个混合来源开发快照，不等同于 r43 的 13 项待审增量。
已知但未达到候选登记资格的 D1 输入、精确证据和去向见
`docs/evaluations/2026-09-29-release-index-intake-boundary.md`；合格的有界 D1 批次仅在明确约定的
局部试点/部分接收中可先进入 D2，默认仍按项目交付，不自动逐资产启动下游。

## 开发快照的来源资格

冻结开发快照只表示固定了一组代码、文档与证据的版本，不证明输入通过 D1。`pending_unapproved`
只表达尚未批准，不能把“来源尚未核验”简写成“科学工作已完成，只等人工拍板”。交接引用已有 provenance
和源验证证据，说明输入来自合格 D1 范围、历史 provisional 候选，还是维护过程中形成的修正/组合。
无需为此复制一套账本；wheel 能运行、文档覆盖 complete、D2 测试或 Agent 审查通过都不能代替缺少的源对照。

默认完成来源项目的 D1 并保存独立项目交付，再由后续 owner 接收 D2；阶段可异步相隔数周。
没有全项目 D1 full_freeze 不等于该项目没有可用输入：科学范围明确、实现与数值源对照已通过的有界批次，
在明确约定的局部试点/部分接收中可以先进入 D2。其资格不自动触发下游，不声称完整项目已完成，
也不把逐算子流水线变成默认方式。尚未满足这些条件的历史候选只能用于明确授权的开发
比较和内部联调；不能把这种实验计作“从合格 D1 完成入库”，也不能凭最终人类批准补造源验证事实。

开发快照可以保存未决项以便接续。形成最终待审增量前，应补齐保留资产所需的科学证据，或明确排除未完成
部分；不能将本应由 Agent 调查的来源缺口交给人类日常调试。历史 manifest/版本标签保持原样，当前交接解释
其实际证据上限，不回写旧冻结记录。

审核基线是**上一可信版**，不是上一个开发提交。跳过若干开发版时，待审版仍呈现相对可信版的累积差异。未变且未被依赖变化影响的资产可复用先前证据；新增或改变的 Operator、TaskGraph 及其反向依赖按实际影响复核。排版、路径或统一版本号变化本身不触发全库科学重审，但仍要保留可核对的工程差异。科学行为、模型条件、依赖绑定、默认值和失败语义的变化必须显式呈现，不能被重命名或重排掩盖。

待审快照至少绑定确切 Git tree/提交、参与审核的 exact documents 集合、受影响依赖闭包和验证证据；若候选 wheel/catalog 已构建，也绑定其摘要。证据复用前须核实实现、科学合同、依赖和适用环境均未改变。机械版本号或文案调整可以不做科学重审，但工程构建和发行绑定仍需重新验证。专家只认可部分科学增量时，不得把仍含未认可内容的同一快照标为可信版；应在隔离开发版剔除或返工，重跑受影响验证，形成新的冻结 successor 供确认。

Agent 的比较结论是提案，不是专家裁决。比较时保留关系类型（复用、重复、重叠、变体、合并、待定等）与行动建议的区别，并记录所对照的版本、条件、端口映射、来源和证据。专家可按领域能力和适用域审视冻结版本，不要求对未受影响资产重复逐项批准；证据不足处仍可要求补证、返工或排除。

领域能力入口见[领域页](../domains/README.md)。它帮助专家从问题找到能力、组合、证据和缺口，不取代 `scirel.asset-document.v1` 的唯一精确科学合同，也不以资产数量推断领域覆盖。

## 实现与边界

D2 统筹、各专业 skill、L1 转换器和 standardization submission 使用此边界。
L1 从实现和图定义发现资产，无须正式 Markdown；输入仍只读，D1 科学证据由来源与数值门禁承担。
正式文档在保留代码稳定后生成；来源路径、重复吸收和内部实现说明可存在本阶段代码注释/docstring 中。
混合批次仅把保留增量送审；纯复用 input_dispositions 经完整记账后形成 no_changes，不产生新审核项。
它不授予目标资产批准，也不能通过 release 的 approved 门禁。

开发版和冻结待审版通过 Git 与现有 artifact 管理，不新增数据库或每次提交的工作流状态。
现有 workflow/plugin release API 仍是单 draft fixture。`scripts/release_index.py` 已能登记精确
待审 artifact 与 Git 候选，`scripts/finalize_release.py` 的命令入口已按逐项批准 revision 核对
提交前版本、代码/测试文件、实际重跑结果、文档、catalog 与 wheel，并追加新的索引副本。
首发准备器已可从逐项批准投影装配只含选中资产及绑定支持模块的 wheel；增量发行仍缺
上一可信基线资产、文档和支持模块的可验证继承输入。
审核宿主的身份认证与发行授权也不能由本地 JSON 摘要证明。完整可信版本增量
投影及消费者切换仍需真实获批输入与对应实现验证，不能以开发 fixture 代替。
发布批准始终绑定最终科学内容；既有未批准维护代码不因某一个 draft 获批而整体获批。

CodeFusion 是中性宿主，不拥有这些科学版本的判断。需要宿主联调时，SciRel 作为普通用户访问 Spark 上的 CodeFusion 局域网服务；Spark 侧构建、部署、访问控制和通用工作台由 CodeFusion 维护者负责，SciRel 不在本机启动或改造该服务。
