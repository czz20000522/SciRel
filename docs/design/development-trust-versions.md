# 开发、待审与可信版本

本文记录 SciRel 下一轮流程调整的目标语义。现有 workflow fixture、整合 skill 和 release 门禁仍包含“逐资产批准后才写入维护包”的旧约束；在相应实现与文档完成调整前，不能把本文件当成已经交付的功能。

## 三条边界

- **开发版**：Agent 可以在隔离分支中对照保存的 L1、上一可信版本及全部未发布候选，完成科学比较、去重、变体判断、代码与 TaskGraph 整合、exact document、测试和内部 wheel 验证。开发版允许执行，但不因能运行而获得专家认可或公开发行资格。
- **冻结待审版**：从某个确定的开发提交形成专家实际审阅的代码、文档、测试与证据快照。进入审核后，实质变更另成待审版本；不能在专家审阅的内容背后改写同一版本。
- **可信版**：专家根据上一可信版到待审版的累积科学差异、适用域和证据作出认可后，记录该认可所绑定的精确版本。发布还须满足许可证、依赖、完整资产文档和发行验证；认可不等于自动发布。

审核基线是**上一可信版**，不是上一个开发提交。跳过若干开发版时，待审版仍呈现相对可信版的累积差异。未变且未被依赖变化影响的资产可复用先前证据；新增或改变的 Operator、TaskGraph 及其反向依赖按实际影响复核。排版、路径或统一版本号变化本身不触发全库科学重审，但仍要保留可核对的工程差异。科学行为、模型条件、依赖绑定、默认值和失败语义的变化必须显式呈现，不能被重命名或重排掩盖。

待审快照至少绑定确切 Git tree/提交、参与审核的 exact documents 集合、受影响依赖闭包和验证证据；若候选 wheel/catalog 已构建，也绑定其摘要。证据复用前须核实实现、科学合同、依赖和适用环境均未改变。机械版本号或文案调整可以不做科学重审，但工程构建和发行绑定仍需重新验证。专家只认可部分科学增量时，不得把仍含未认可内容的同一快照标为可信版；应在隔离开发版剔除或返工，重跑受影响验证，形成新的冻结 successor 供确认。

Agent 的比较结论是提案，不是专家裁决。比较时保留关系类型（复用、重复、重叠、变体、合并、待定等）与行动建议的区别，并记录所对照的版本、条件、端口映射、来源和证据。专家可按领域能力和适用域审视冻结版本，不要求对未受影响资产重复逐项批准；证据不足处仍可要求补证、返工或排除。

领域能力入口见[领域页](../domains/README.md)。它帮助专家从问题找到能力、组合、证据和缺口，不取代 `scirel.asset-document.v1` 的唯一精确科学合同，也不以资产数量推断领域覆盖。

## 现有文档与实现的最小调整切片

1. **需求**：在 [Workflow 需求](../requirements/scirel-workflow.md) 中区分“写入隔离开发包”与“进入可信/发行基线”；将逐资产批准前禁止公共 import/wheel 的要求缩到可信发行边界。保留逐项审核工作台作为专家分工能力，不把它强制为每次开发集成的前置步骤。
2. **设计**：在 [Workflow 设计](scirel-workflow.md) 中增加开发提交、冻结待审提交和可信版本的绑定及可信版增量影响计算；重新定义旧“批准后固化器”为认可版本的确认与发布准备。保留精确版本、来源和审核事件；不为开发版引入发布身份。
3. **方法**：在 [开发流程](../development-process.md) 和 [整合 skill](../../skills/integration/scirel-integration/SKILL.md) 中允许隔离分支直接组装、修错、构建和测试，同时要求报告科学比较及证据上限。旧“只准备 patch、批准后才可写入 `src/scirel`”和“未审核代码不得进入任何 wheel”需收窄；公开发行仍须经过可信版与发行门禁。
4. **验证**：复用 `affected` 精确测试、直接科学测试、TaskGraph 反向依赖和 source-free wheel 检查；补针对版本跳跃、未变资产证据复用、实质变更触发重审及开发版不得冒充可信版的回归。现有 workflow/release 接口的调用方和兼容影响在实际改动前单独列出。

CodeFusion 是中性宿主，不拥有这些科学版本的判断。需要宿主联调时，SciRel 作为普通用户访问 Spark 上的 CodeFusion 局域网服务；Spark 侧构建、部署、访问控制和通用工作台由 CodeFusion 维护者负责，SciRel 不在本机启动或改造该服务。
