# SciRel 开发项目与科学包交付

SciRel 项目维护科学库的完整生产过程；面向用户的核心交付是某个确切版本的 `scirel` Python 包。
项目包含科学整合、审核、文档、skill 和平台接入；外部项目源码及拆解运行材料独立存放，不作为本仓库的归档内容。
普通用户可由平台使用该包取得结果；直接使用 Python 的调用方只需安装包及其声明的运行依赖。

## 项目、库与发行物

| 层次 | 内容 | 交付边界 |
| --- | --- | --- |
| 外部项目资产 | 原项目源码及独立拆解的最终产物 | 存放于仓库外；拆解无需访问 SciRel，最终产物不声明 SciRel 合入或发行状态 |
| 开发项目 | skill、科学测试、exact documents、整合及审核记录、构建工具及宿主适配 | 用于生产、验证和维护库；只保留所消费产物的必要摘要和绑定 |
| 科学库 | `src/scirel/` 中按科学领域组织的 Operator、TaskGraph 与必要内部实现 | 形成科学包的运行代码，保持公共科学合同与兼容要求 |
| 科学发行物 | `scirel` wheel、声明依赖、必要本地组件/数据、版本与许可证等分发元数据 | 在满足该版本声明的平台、Python/ABI 与 capability-specific 外部运行时条件时，可在没有项目 checkout、审核服务或源项目环境的条件下安装调用 |

科学实现来自有来源绑定的拆解交付，经 D2 比较、去重、科学判断和必要修正后维护于库中。
官方上游到 D0 的整理差异，以及 D1 保真实现到 D2 有意修正的差异分别保持可核对；
D1 的行为对照与完整性范围绑定冻结 D0，不隐含覆盖已剔除的上游功能。
预处理索引、探针和缓存不进入科学 wheel；不能让 workflow、skill 或胶水代码代替缺少的科学能力。
项目源码属于开发材料，其中用于运行的实现必须随包交付；包内原语言组件的构建、ABI、依赖和许可
仍须满足 [架构合同](../architecture.md)。开发目录的源码并不天然全部具有公开发行资格。

API 使用说明、单位、适用条件和失败行为是用户需要的使用合同。它们可以随包或作为绑定发行版本的
文档提供。Agent 的 catalog 是 exact documents 的只读发现投影，可以由平台单独安装；
它与 wheel 必须绑定同一发行内容。运行不加载审核队列、完整来源快照或开发状态账本。
唯一 exact document 与审核依据仍在项目层维护，用户文档/catalog 不成为第二套科学真值。

## 外部资产的保留与状态边界

每个外部项目长期保留源码和一份当前最终产物，分别位于 `source/` 与
`decomposition/FINAL/`。同项目的新最终产物在校验后覆盖旧产物，不按运行次数累积备份。
`decomposition/WORK/` 与 `INBOX/` 仅供仍在执行或需要接续的拆解使用；完成后将最终产物确需的
实现、合同、科学验证证据和许可材料收进 FINAL，再清理重复副本、失效状态、调度记录与缓存。
曾经属于某次运行不构成长期保留理由。尚未证明已被 FINAL 覆盖的科学材料不能混同于可删日志。

`project.json` 和外部项目目录索引只定位源码与 FINAL，不复制阶段进度、接收、合并或发行状态。
FINAL 描述外部产物本身的能力、范围、验证与许可条件；`canonical_merge`、SciRel root 接收、
SciRel 人审和发行状态属于 SciRel 的整合及版本记录，不得成为外部拆解完成的前提。
已合入的能力由领域包继续维护，不因旧阶段收据的 pending/false 或重新整理外部归档而重新排队。

冻结科学证据在仍被引用时保持原字节，并限定在证据中的对象、阶段和候选范围内；它不充当当前进度入口。
已经失效的进度副本应删除，不靠再添加一个状态文件覆盖旧状态。

## 三类依赖与独立环境

依赖按实际消费者归属，不按上游清单、安装所在机器或工具名称归属。三类清单分别维护，
共用版本政策不等于安装三者的并集。

| 依赖集合 | 由什么决定 | 安装与验收边界 |
| --- | --- | --- |
| 来源运行依赖 | D0 保留的核心科学入口、分支，以及本次确需执行的源码对照 | 从上游声明中筛选必要的直接、传递和本地组件依赖；只供来源运行和对照，不直接复制到 wheel |
| 科学 wheel 运行依赖 | 最终所选实现实际调用的 Python/本地组件、数据及传递依赖闭包 | 写入包元数据及必要的本地运行合同；在声明平台和 capability-specific 外部运行时条件满足时，无来源 checkout、开发环境和网络也能执行对应核心任务 |
| SciRel 项目开发依赖 | 当前构建、科学测试、独立参考计算、文档、版本控制或发行任务 | 按开发任务安装；构建依赖与测试/文档依赖分别声明，不进入用户科学运行环境 |

D0 先用可读取的源码完成或复用初始索引，再依据真实证据确定保留、剔除和修正范围。
准备源码环境时按当前保留入口逐步补齐依赖，不以安装全部上游 `requirements`、所有可选组件或完整构建
作为索引和范围判断的前提。剔除分支独占的依赖不必安装；仍被核心入口直接或间接使用的依赖必须保留。
缺少依赖或安装困难不能成为剔除核心能力的理由；必要对照不能运行时明确记录证据缺口。

同一个工具可能属于不同集合，必须有调用依据。例如，Octave 若只用于原实现对照，属于来源运行环境；
若最终 wheel 的科学入口仍调用它，就是需要单独声明和验证的本地运行依赖。Git、PowerShell、Sphinx、
pytest 在当前项目承担开发工作，不因开发检查调用它们就成为 wheel 的用户安装要求。
绘图工具只用于非核心展示时可以不进入核心运行集合，但绘图库提供的等值线、几何或插值若被求解器使用，
必须先分离或替换该数值能力、验证科学等价后才能移除；不能只凭包名删依赖。

在既有环境定义和阶段交付中分别记录三类清单/锁文件引用、用途与消费者、版本/平台、重建命令和实际验证。
不要求再建一套台账。新增依赖先说明哪个保留入口或开发任务需要它；不从 `pip freeze`、成功启动的大镜像
或开发环境全量清单反推 wheel 要求。统一版本规则见[科学运行依赖基线](scientific-runtime-baseline.md)。

安装包验收仅给目标运行进程提供所声明的 wheel 运行闭包；来源运行和开发检查分别执行。
测试框架可以作为只读验收驱动另行提供，但其安装/挂载须显式记录，不能让目标借用它的库、可执行程序、
源码或参考答案。需要证明最小依赖时，增加仅安装运行闭包的直接调用检查；完整开发镜像中的测试不能替代它。
验证结果分别报告：来源对照、安装包科学任务、开发工具/文档/构建。缺 Git 或 PowerShell 是对应开发检查
的环境缺口，不是算法数值失败；缺最终实现确实调用的本地求解器则是 wheel 运行闭包缺口。
必要开发门禁仍须修复并复跑，但不使无关科学结果失效，也不要求重算未变科学任务。

准备安装验收时，先明确本次检查是开发测试驱动还是用户运行任务。前者可以复用有来源绑定的
测试环境；后者须在不继承系统或开发 `site-packages` 的环境中，只安装所选 wheel 的直接及
传递运行依赖。记录实际导入路径、可执行程序搜索路径和必要本地运行组件；仅新建了虚拟环境，
或测试全部通过，并不能证明没有通过 `--system-site-packages`、`.pth` 或环境变量借用开发依赖。
同一科学字节的有效测试可以复用，干净用户环境直接执行核心任务即可，不要求复制整套开发门禁。

准备依赖工件前，先检查当前登记交付的 manifest 是否已有版本、平台/ABI、字节摘要一致的可复用
wheel 或本地组件。只补齐实际缺少的运行闭包；不扫描全部历史目录，也不因为大镜像中已经安装
了某个工具就将它带入用户环境。离线安装失败须保留原失败并区分下载缺失、平台不匹配、挂载执行
权限和科学实现错误；环境修正另产后继证据，不改写原验收结果。

历史冻结物保持原字节。依赖精简、统一或替换另产后继，重建并验证受影响的安装闭包、公共科学任务和文档；
不能只改 `Requires-Dist` 就宣称依赖已移除或继承旧 wheel 资格。

## 构建边界与适配工具

根 `pyproject.toml` 的普通构建只发现 `scirel` 与 `scirel.*` 包。
`scirel_workflow`、`scirel_plugin`、`scirel_adapter` 属于开发或消费适配层，不能被科学 wheel 自动收集。
必要运行数据、本地程序和扩展须显式声明并验证实际 wheel；包名过滤不替代组件及依赖闭包验证。

开发者在源码 checkout 中通过项目脚本、测试入口或显式的 `PYTHONPATH=src` 使用开发模块。
仅安装 `scirel` wheel 或 editable 科学包不提供上述开发模块。已有脚本自行绑定 checkout 的 `src`，
测试入口也显式提供源码路径。宿主若需要审核服务或 MCP 适配器，须另外部署对应工具与 skill/catalog，
固定其代码版本及兼容的科学包版本；插件 registration 描述这种平台集成，不改变用户科学包的边界。
当前没有独立开发工具包的发行入口，不声称科学 wheel 已提供这些服务。

普通构建会收集该工作树中全部 `scirel` 模块，包发现配置本身不执行科学准入。
后续内部待审包也须按[内容准入规则](development-trust-versions.md#准入与人工注意力分开决定)
选取当前证据支持的内容；未解决正确性疑点、未核验来源及实验实现留在未合入材料，不能仅贴开发标签入包。
历史混合开发快照保持原样，只作其原授权范围的研究证据，不作为新的合格内部包。
正式发行从确切获批内容及必要依赖闭包准备独立源码树，再构建科学 wheel；不能以包名前缀过滤
冒充逐资产发行选择。现有首发准备器见 `scripts/prepare_reviewed_distribution.py`，
增量发行及宿主认证的实现限制见 [开发流程](../development-process.md)。
改变构建配置只影响之后的新构建；已冻结 wheel、索引、审核记录和宿主注册的摘要保持原样，
平台后续更新需绑定新产物，不从同一开发版本字符串推断字节一致。

## 历史样本与正式主线

旧迁移样本、历史 admitted 账本、早期 pilot 与联调记录用于研究、回放和解释设计演进。
它们不定义后续完整主线的资产数量、公开 API、构建输入或永久验收门槛。
后续主线由接收的 D1 项目交付、D2 科学整合及实际发行版本构成；历史输入只能按明确范围参与比较。

历史实现要继续进入正式库，必须明确复用处置、来源资格、科学合同、必要验证和最终发行绑定；
不能因其已在 `src/scirel/`、旧 wheel 或旧测试中存在而自动获得资格。
历史测试若仍验证保留能力的有效合同，应继续维护；只复现旧试验的测试可以退出主线默认门禁。
这与删除断言、放宽容差或静默破坏已发布 API 不同。

历史试验可通过不可变 Git 标签、历史分支或带摘要的独立归档保存，主线保留必要定位。
仍被正式能力、许可证义务或审核证据引用的材料必须可取得。实际移除或迁移前先核对引用、
列出精确 dry run，再在所属线路更新引用和验证；本设计不自动移动或删除现有冻结记录。
当前普通开发树仍保留历史实现与测试，本次包边界调整不声称已完成历史资产迁出。

## 分支、worktree 与多版本构建

一个 Git 仓库维护连续历史；不同工作路线采用隔离 worktree，而非复制并永久维护多套 SciRel 项目。

| 工作路线 | 基线与写入范围 | 产出 |
| --- | --- | --- |
| 主线 | 已整合的开发基线；可以尚未获批 | 下一版本的持续维护，明确其开发身份 |
| D2 整合分支 | 固定接收的 D1 交付、Git base 与候选池；在私有 worktree 整合 | 可验证的科学增量及开发 wheel |
| 发行候选分支 | 明确所选内容和依赖闭包；冻结待审版本 | exact documents、审核绑定及确切候选构建 |
| 已发布版本维护分支 | 从该版本冻结提交/标签开始 | 有兼容说明和独立验证的维护发行 |

分支是演进路线，worktree 是工作目录；二者都不授予科学批准。
每次构建固定确切提交、包版本、依赖/工具链与支持平台，输出到本工作树内全新的运行目录，
记录实际 wheel 摘要及相应证据。一个分支可以产生多个版本；一个版本无需永久保留 worktree。
正式构建输入不得含未绑定的工作区改动；开发试验若使用未提交变更，须记录差异，不能冒充冻结发行。

创建前检查现有 worktree、分支与未提交修改，优先复用适合且写权明确的工作区。
新分支默认使用 `codex/` 前缀，可采用 `codex/integrate-<batch>`、`codex/release-<version>`、
`codex/maintain-<version>`；已有主线名称沿用仓库实际配置，不为本设计强制改名。
各 worktree 使用自己的 Python 环境、暂存树与构建输出；并行开发按文件/科学依赖划分写权，
主线合并和发行索引由明确 owner 串行协调。合并时对照当前基线保留其他贡献者修改，
不以整批覆盖导入或较新时间戳处理科学冲突。

合并、重新构建或 cherry-pick 后核对实际影响；新内容不继承旧候选的批准和构建摘要。
按 [版本边界](development-trust-versions.md)复用仍有效证据，变化部分执行受影响验证。
发行前从实际 wheel 安装并验证公共 API、所选科学测试和文档示例，运行不使用源码路径。
worktree 的归档或删除按精确范围、引用与未提交成果核对后进行，不改写已发布标签或冻结记录。
