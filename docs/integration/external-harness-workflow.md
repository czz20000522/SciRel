# 外部 Agent 整合方法

Claude Code、Codex、CodeFusion 或其他具备代码读取、修改和执行能力的 harness，都可以驱动保存的
L1 产物进入 SciRel。harness 只是承载模型工作的工具；SciRel 的方法由
`skills/integration/scirel-integration/SKILL.md` 定义，科学结论最终由专家审核。

## 输入

一次整合需要三个逻辑输入：

- 一个或多个只读的保存 L1 项目目录；
- 冻结且只读的 SciRel 基线，包括实现、公共 API、科学测试、TaskGraph、资产文档和历史来源证据。
- 当前全部未发布候选的可检索视图，包括开放、审核中和已批准待固化候选。

L1 的预期目录形态由第一阶段 extraction skill 定义，但第三阶段不能假设每个产物都完整无误。模型应检查
缺文件、直接测试、依赖引用、端口、科学合同和证据，并区分结构缺陷、可修复问题、科学不确定性和真实新能力。

当前 `catalog/examples/` 只是部分投影，不能单独代表 SciRel 已有能力。模型必须从相关源码、测试、图绑定、
资产文档和 provenance 逐步建立现有能力视图。为了完成去重和合并判断，不应把当前 SciRel 基线从模型上下文
中隔离。

## 执行边界

加载 `scirel-integration` skill 后，模型自行选择适合当前项目的检索、比较、探针、临时脚本和测试。项目不规定
统一的 task manifest、target projection、finalize 命令、executor receipt 或运行目录。固定这些形式既不能证明
科学等价，也容易把模型限制在预设答案中。

现有仓库脚本可以作为工具或参考实现使用。例如 L1 inventory 能帮助快速发现结构和引用缺口，affected-test
选择器能保护已确认的反向依赖，资产文档 validator 能检查稳定文档合同。但这些工具不替代模型对关系、单位、
坐标、模型、边界、状态、离散、适用域和证据上限的理解。某次任务需要的额外脚本由模型按问题编写；只有经过
重复使用证明为稳定项目需求时才考虑长期维护。

模型应同时比较 L1 批次内部、当前 SciRel 和未发布候选池：识别已有身份、完全重复、等价提案、包含与重叠、参数化变体、
无损适配、组合、新能力、冲突和未决关系。重新处理同一个 Pleiades 应优先发现已有实现而不是再生成一份；
处理具有部分重叠的 PleiadesB 时，应保留每项差异和来源，不能用名称或相似输出直接合并。

## 输出与审核

实际输出是冻结基线之外、可由专家审查的候选三件套：候选文档、候选代码和候选测试。文档是主入口，解释
每项关系判定、科学差异、拟议身份/API、影响、证据、来源、限制和需要专家决定的问题；代码和测试用于核对
文档主张。精确文件布局由当前任务决定，不建立统一 candidate schema。

候选可以放在隔离 worktree、patch 或本次输出目录中，但不得提前写入维护中的 SciRel 基线。处于候选队列但尚未被专家打开的内容仍可被合并、替换或撤回，以便把一个科学决策尽量收敛为一次专家审核；工作台首次打开完整详情时进入 `review_in_progress` 并冻结三件套，之后的修改只能通过返工或关联新候选。若结论是完全
重复或直接复用、无需运行时代码改动，文档必须明确说明，测试或实验仍要支撑该判断，不为形式完整制造空实现。

交接至少要让人能够回答：

- 每个 L1 资产被复用、吸收、保留为变体、组合、新增、冲突还是暂时未决；
- 关联的是哪个现有或新 SciRel 科学身份，依据和材料差异是什么；
- 候选将改哪些文件、运行了哪些检查、哪些结论仍受证据上限约束；
- 是否存在需要专家裁决、补证据或返回第一阶段修复的问题。

这些内容可以用最适合批次的表格、任务记录或审查说明表达，不建立新的治理数据库。模型完成、测试通过或构建
成功都不会自动产生专家批准；只有批准后，另一个执行步骤才把接受的候选应用到 SciRel 并进入 release 门禁。

外部 harness 在候选提交后结束，不等待人工回复。候选需记录本次比较使用的 SciRel Git base。批准后由新的固化任务对照当前基线应用候选；若队列中较早候选已经改变同一科学身份、依赖闭包、TaskGraph 或 patch hunk，则停止应用并基于最新基线生成关联的新候选重新审核。旧批准不能传递给实质变化后的候选。

候选可以长期堆积在隔离 artifact、branch 或 worktree 中，但不能进入 `scirel` 公共导入、catalog 或 wheel。把未审核代码放进可执行包再定期审查，会使候选事实与资产事实混合，不作为主流程。

## Harness 对照

比较 Claude Code 与 CodeFusion 时，应给它们相同的 L1 输入、相同的 SciRel 基线、相同的未发布候选池快照、相同的 skill 和同一目标。
为复核实验，可记录输入路径/内容摘要、Git base、模型与 harness 版本、候选 diff、实际测试和执行时间；这些是
实验事实，不是 SciRel 运行合同，也不应成为模型必须填写的流程表。

对照重点是科学关系判定质量、重复和变体识别、实际库改动、验证充分性、未决问题诚实度和完成效率。旧 gseq
运行、固定时长、调用次数或通过测试数量只能作为历史样本，不能成为新 harness 的通过阈值。
