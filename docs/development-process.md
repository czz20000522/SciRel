# SciRel 开发与增量整合流程

本流程将来源拆解、科学库整合与用户应用作为完整链路；各阶段交接可核对的事实，不重复生产同一份信息。

开发项目包含方法、来源、测试、审核和平台工具，面向用户的核心产物是独立可安装的 `scirel` 包。
普通构建只收集科学库命名空间；正式发行另按确切所选内容准备源码树。历史试验不自动进入发行或成为
永久门禁。不同整合批次、候选和维护版本使用隔离分支/worktree、环境与新输出目录；
以实际提交和工件摘要定义版本。具体规则见 [开发项目与科学包交付](design/project-and-distribution.md)。
领域需求见 [workflow](requirements/scirel-workflow.md)，信任边界见 [版本设计](design/development-trust-versions.md)。

整个流程的黑盒边界固定为**来源码及其声明依赖输入 → 可安装、可调用的 SciRel 包产出**。
内部阶段分别负责行为保真、科学判断与库整合、实际应用验证；阶段调整不丢弃仍有效的实现和证据。

## 阶段职责与入口

| 阶段 | 负责的结果 | 统筹入口 | 不重复承担的工作 |
| --- | --- | --- | --- |
| D1 来源拆解 | 全来源现有功能覆盖、Operator/有序 TaskGraph、忠实实现或原实现封装、源码行为对照、疑似错误及复现依据 | [来源拆解](../skills/extraction/scientific-computation-asset-extraction/SKILL.md) | 不要求科学正确性证明，不修正来源科学行为，不做跨项目去重或正式文档 |
| D2 科学判断与库整合 | 消费 D1 错误记录，科学/数值验证、必要修正及来源差异，基线比较、去重、组装和开发包 | [库整合](../skills/integration/scirel-integration/SKILL.md) | 不重做仍有效的源对照，不回写 D1，不给吸收项生成重复文档或审核项 |
| D3 用户应用 | 真实需求、追加输入、坏数据、恢复、独立复跑及科学解释 | [用户项目](../skills/usage/scientific-project-implementation/SKILL.md) | 不重复拆源，不用单个案例证明整个库 |
| 最终审核与发行准备 | 汇集稳定代码、唯一正式科学文档、累积差异和证据，交最终拍板 | [最终待审准备](../skills/integration/scirel-review-preparation/SKILL.md) | 不把人工作为日常开发调度器，不把开发验证当批准 |

统筹 skill 只维护目标、条件路由、交接和停止条件；专业方法按需加载。
默认先尽量完成一个来源项目的 D1，再统一交付 D2；不按单个算子/TaskGraph 启动整条流水线。
阶段逻辑有先后，但人员和时间独立：D1 交付可以封存排队，D2、D3 可由新的 Agent 在数周后接续。
项目内可按科学家族并行；不同项目可处于不同阶段，无须让每个项目同夜走完全部阶段。
明确约定的局部试点/部分接收可使用合格有界批次，其科学资格不等于调度指令，
也不得称完整项目 full_freeze。D2 开发 wheel 可供 D3 使用；D3 按用户目标与影响选场景，
不为每个库变更发明新用户项目。交付要求见 [项目接续合同](requirements/scirel-workflow.md#项目交付与异步接续)。

D1/D2/D3 skill 是跨学科、跨库名、跨 Agent 与执行平台的通用方法。本文描述 SciRel 对方法的一次集成；
本机路径、包名、harness、模型、子代理类型与资源预算由运行配置提供，不写为通用 skill 的前提。
当前部分 skill 发现名称保留兼容性，不要求目标库采用 SciRel 包名；仓库脚本/API 属于实现适配。

协调者先交付可实际运行的依赖环境、确切只读源码目录、独占结果目录、适用 skill 和项目目标。
环境交付包含可复用的构建定义、依赖/镜像身份和启动命令，并实际检查源码只读、结果持久化及必要依赖。
已选容器后不能以安装了 CLI 代替运行验证；用户明确改变隔离要求时，先保存 checkpoint，再在指定容器接续；按平台影响验证，不机械重跑已有科学证据。
项目 owner 自主选择前沿、拆解粒度和本阶段验证，维护既有项目 checkpoint，持续执行到交付或真实阻塞。
D1 修复自己引入的抽取、封装和比较缺陷；来源自身的科学/数值疑似错误记录后交 D2。
不同项目独立并行；同一项目的科学队列和集成仍由其唯一 owner 负责。

外层协调者按阶段记录定期抽查方法、方向、证据真实性、资源和写权，不逐算子派步骤，
不把每个局部增量回报都变成一次接收、哈希复核、总结或确认，不另建重复状态报告。
只有方法/范围偏离、持续无进展、无法自行解决的阻塞、资源或写权冲突，以及阶段交付需要介入。
owner 空闲但项目未完成时，沿用持久 checkpoint 恢复其自主执行，不必替它排下一组科学步骤。
真实范围选择、超出授权的行动或外部依赖裁决才交用户决定；人工批准与发布仍单独授权。

## D1：完整性与源码行为保真

D1 的验收对照是确切源码已有行为，包括默认值、分支、精度、索引、状态变化、调用顺序和失败。
忠实复现来源的错误结果或可复现失败可以通过对应的行为对照；这不证明科学正确或适合应用。
源码未定义行为不能臆造稳定期望，无法取得的运行条件仍是明确验证缺口。
原实现可直接抽取或封装，内部允许 Python、C/C++、Fortran 及混合语言，不要求统一改写算法。
`source-free` 指不依赖原 checkout、外部源码环境或在线服务；包内合法保留并绑定来源的实现、
本地二进制和声明依赖可以使用。保存构建配方、许可、ABI/平台限制、状态初始化与隔离约定。
整体封装可以先打通对照，但仍须交付来源支持的可复用局部能力及其组合，不能只包住原入口就称拆解完整。

测试使用原样例和自行构建的来源可接受输入，同时运行原实现与抽取实现，比较输出、状态与异常。
按重要分支、边界和生命周期补案例；复用有效原始结果，不要求额外解析解、物理残差、实验校准、
收敛证明或独立科学 oracle。保留原有比较容差，缺少判据时根据原实现精度和运行条件先定比较规则。
源码已知行为可以作为期望；禁止复制答案到实现中或根据候选误差放宽规则。
每次失败先区分抽取不一致、来源原有失败、比较器错误和运行依赖失败，不把它们合成科学失败。

疑似来源错误在已有注释/证据记录中保存：确切来源位置、触发输入/状态、观察结果、影响范围和
复现证据；区分已复现事实与待确认推测，注明供 D2 判断。无须先推导修正方案或新增正式报告。
已有科学修正版另存后续候选及其证据，不能覆盖忠实版本或使已有有效工作失效。

盘清源项目的科学能力、实现、调用顺序、状态/反馈及边界。交付可执行算子、机器可读图和必要 glue，
来源位置/版本、输入输出映射、源实现对照、数值证据与明确缺口。不能以文件数、字段数或文档数量替代完整性。

局部算子完成只推进本项目的 D1 进度。项目交付汇集全来源覆盖、资产/依赖与处置、有效验证和
剩余缺口；有阻塞时保存可恢复快照与重开条件，不能靠送出一个已完成算子宣告项目完成。
在既有 bundle/证据记录上给出简短接续入口及可取得的工件、依赖和复跑方法，使新 owner 不必
阅读原聊天或恢复原临时环境。科学证据单独封存，callable 包仍保持 source-free；不重复写正式资产文档。

代码、YAML、签名、docstring、测试或已有记录能唯一表达的信息直接引用。
不能可靠恢复的单位、约定、假设、分支选择或证据局限补在一个最小科学记录中。
缺少正式 operator.md、task_graph.md 或根报告不构成科学不合格；缺少科学含义、来源映射、
源对照或真实结果仍是相应科学缺口。D2 结构转换成功不自动确认 D1 科学合格。

断言写错时按当前阶段确认期望和判据：D1 对照原实现，D2 科学修正使用独立科学依据；再重放已有原始输出或最小验证；
不能从输出反推期望、调容差或改科学含义。脚本位置、展示格式、文档路径或包装摘要问题，
能确认原实现、输入、环境和结果归属时修复引用、检查新包装并复用数值证据。
不能证明归属、原始输出不足或科学行为变化时，只补必要证据；不伪造旧 receipt 或回写冻结记录。

## D2：整合后生成正式文档

接收 D1 的来源错误/疑点记录，逐项给出修正、保留明确兼容变体、排除或未决的处置及依据。
科学和数值正确性验证在本阶段按保留能力的主张开展；来源对照通过不自动关闭这些门槛。
修正先保留失败回归，说明相对来源的有意差异，再验证改变的合同和受影响依赖。
不能确定修正时记录影响和限制，继续其他工作；不得把忠实行为当作已获科学认可。

上一阶段交付只读。接收已保存的项目级 D1 输入，核对工件、科学资格与缺口，固定接收时的
比较基线及未发布候选池，在独立分支开发，按科学家族并行、私有产物、单写者整合。
项目内逐项比较和依赖闭合属于 D2 内循环，不要求为每项新建一条跨阶段任务。
本阶段的重复判定、来源参考、修正理由和实现约定写在本阶段派生代码的注释、docstring、函数/模块说明
或已有接续记录中。它们不是面向人的正式审查文档，不要求另写一份 Markdown，也不回写上游资产。
上一可信版不可被开发进展改写；开发分支可修改 src/scirel、公开 callable、内部 catalog 和 wheel，
明确 pending_unapproved。没有可信版本不阻断开发，也不得虚构批准基线。

先比较关系、方向、假设、单位/轴、边界、状态、数值方法和失败语义，再比较代码。
哈希、名称和相似度只筛选对象；相同样例不独立证明等价。逐输入记录一次处置与证据：
复用、重复吸收、明确覆盖、新增、变体、适配、组合或未决。子图包含和局部重叠不自动消除独立能力。
Agent 调查并解决有依据的中间分歧，不必交人类逐次裁决；不能判等时保持分离，继续独立工作。

源直接测试在 API 映射后可作对照；入口不匹配只证明不能直接替换，不直接证明科学冲突。
真实科学修改先有失败回归，验证改变资产和受影响反向依赖。未知源码归属沿用 affected 的全套回落。
代码和身份稳定后，仅为保留的新/变公共资产生成或更新唯一 scirel.asset-document.v1。
复用既有文档；重复/吸收项保留来源与处置依据。人读页面、摘要、catalog 均为同一正式文档的投影，
不再同时维护 relation page、operator.md、task_graph.md 和全文审核副本。
审核说明只解释差异并引用 exact document。进入 catalog 前仍验证依赖、签名与示例。
文档可按最终科学家族并行；过程草稿留 run 内，根报告在完成或冻结时汇总。

## D3：用户价值与反馈

固定实际消费的 wheel/catalog/代码版本及信任状态。完成需求澄清、输入检查、实现运行和独立复跑，
验证安装后的 Python 入口及实际使用的本地组件/依赖，不挂原 checkout 或使用开发环境隐式依赖。
报告解释边界以及 Agent 自修、独立 Agent 纠错、用户救援的区别。评审建议的替代答案仍须独立核实。
缺库能力回 D2 比较；缺来源语义或实验回 D1 指定分支；不以重跑整链代替定位问题。

## 最终审核

以**上一可信版本**为基线呈现累积科学增量，不逐开发提交审批。独立 Agent 审查记录真实身份、
模型版本与发现，可走通开发链路，不能冒充人类认可。保留增量完整可评估后送审；
未解决科学缺口补证或明确排除，不强迫人类接手日常调试。

待审快照绑定 Git、exact documents、代码/测试、比较处置和有效证据；已有 wheel/catalog 同时绑定。
SciRel 将稳定待审快照登记为统一发布索引中的候选版本；返工另建关联版本。索引是最终发布版本的
选择入口，catalog、wheel 和单次 manifest 只绑定该版本的实际内容，不自行授予发布状态。
review_units 只包括保留新增/改变项；input_dispositions 完整记录无改变的复用、重复或覆盖。
纯无变化批次终结为 no_changes，不产生新 draft、审核项、批准或 release。复用不提升目标信任状态。
上传后不静默覆盖；返工另建 successor，保留原版及审查记录。人工最终可要求返工或排除；
批准只覆盖确切版本及依赖，科学实质变化须重新确认。

## 验证、提交与发行

```powershell
pwsh ./scripts/check.ps1 -Mode affected -ChangedPath src/scirel/<domain>/<asset>.py
pwsh ./scripts/check.ps1 -Mode affected -BaseRef <merge-base-or-release-ref>
pwsh ./scripts/check.ps1 -Mode focused -TestPath tests/<affected-test>.py
pwsh ./scripts/check.ps1 -Mode full
python scripts/release_index.py --item-artifact <review-pending-workflow.json> --git-revision <frozen-git-sha> --output <candidate-index.json>
pwsh ./scripts/check.ps1 -Mode release -ReleaseIndex <candidate-index.json> -CandidateEntryId <candidate-entry-id> -ApprovedResults <completed-results.json> -ReviewArtifactsDir <exact-review-artifacts> -ReleaseId <release-id> -OutputRoot build/verification/<new-run>
```

内循环按影响选检查并复用有效证据；纯文档验证结构、链接、signature 与相关示例，不重跑源数值。
共享合并前运行适当工作流/科学测试，发行再运行 release 门禁。
交付实际文件、SHA、检查和未验证边界；按 owner 聚焦提交并合并，保护冻结记录及其他贡献者的成果。

安排验证前先定位改变的事实与其影响范围；沿用已有 run 记录，不新增逐项审批表。

| 改变或缺口 | 最小必要动作 |
| --- | --- |
| 路径、包装、报告或文档呈现变化，科学代码/输入/运行条件仍可核对 | 修引用或新绑定；验证结构及受影响文档示例，复用数值结果 |
| 比较器或断言错误，原始输出足够且正确期望有独立依据 | 保留原失败；修比较器并重放原始输出，不调容差或倒推答案 |
| 科学实现、源输入、依赖或数值相关运行条件改变 | 先建立适当回归，再验证受影响科学闭包和反向依赖 |
| 原始结果不足、来源归属不明或独立依据缺失 | 保持该项缺口，补最小缺失证据；不重跑无关项目或整个链路 |

换阶段、换 Agent 或回执格式升级本身不使有效计算失效。独立审查可由获授权的独立可见线程完成，
记录真实身份、模型/工具版本、范围与发现；实现者不能自审，角色字符串也不能证明独立性。
协调者默认按项目保存和接收 D1 交付；内部科学前沿不自动触发下游。
只有确切开发包与实际用户任务出现后才调度 D3，接续可延后且无需原 D1 Agent 在线。发布索引与最终固化
始终由一个明确的 D2 owner 串行写入，流程/工具维护与来源/资产实现使用互不重叠的写入范围。

## 当前主线与发行边界

当前 `0.2.0.dev0` 是无科学资产的包骨架，开发测试只验证骨架和通用工具。
历史实现、科学回归、pilot 与批次记录已迁往 [历史开发测试线](history.md)。
新主线候选/版本入口为 `provenance/mainline-release-index.dev.json`，当前为空；
不继承旧 wheel、候选、回执或批准。实际资产文档进入 `catalog/assets/`，
受影响选择器只读取这里的文档、直接测试和源码 import 关系，不加载旧账本。

后续先接收独立 D1 项目交付，在隔离 D2 worktree 对照接收时基线整合科学源码、相关测试与必要依赖。
开发 wheel 不要求最终批准。保留代码稳定后生成 exact documents，再冻结待审内容。
正式发行另需确切批准、许可证/依赖、宿主认证与授权、文档/catalog/wheel 绑定及实际安装验证。
没有科学资产的骨架和合成审核 fixture 都不能登记为科学库已发布。

现有首发准备器从逐项审核材料装配所选科学模块、支持模块和过滤后的包初始化文件，
历史账本不参与门禁。增量发行仍缺上一可信基线文档/支持模块的可验证继承输入。
本地审核 artifact 摘要核对也不能认证真实专家身份；selection 绑定工具不代替发行前的真实授权与状态复核。
这些工具机制仍在主线维护，测试使用合成材料；旧 r43/52/132 批次的具体接线与验收属于历史线。

平台相关 PowerShell 检查在具备 `pwsh` 的环境执行；缺少时明确 NOT_RUN/skip，不能计作通过。
发行环境必须安装实际声明的依赖，不通过挂载科学源码补足。当前开发检查的 `.pth` 方式只用于已声明
依赖与测试工具，仍不证明完整离线 wheelhouse/工具链隔离；正式发行须完成该边界的实际验证。
