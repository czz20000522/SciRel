# SciRel 开发与增量整合流程

本流程将来源预处理、拆解、科学库整合与用户应用作为完整链路；各阶段交接可核对的事实，不重复生产同一份信息。
本文是全阶段参考；日常任务先按 `skills/development/` 选择 lifecycle mode，普通 development 不自动进入完整链路、发行门禁或平台矩阵。

开发项目包含方法、来源、测试、审核和平台工具，面向用户的核心产物是独立可安装的 `scirel` 包。
普通构建只收集科学库命名空间；正式发行另按确切所选内容准备源码树。历史试验不自动进入发行或成为
永久门禁。不同整合批次、候选和维护版本使用隔离分支/worktree、环境与新输出目录；
以实际提交和工件摘要定义版本。具体规则见 [开发项目与科学包交付](design/project-and-distribution.md)。
领域需求见 [workflow](requirements/scirel-workflow.md)，信任边界见 [版本设计](design/development-trust-versions.md)。

整个流程的黑盒边界固定为**来源码及按保留科学范围选取的必要依赖输入 → 可安装、可调用的 SciRel 包产出**。
内部阶段分别负责 D0 来源整理、D1 对冻结 D0 的行为保真、D2 科学判断与库整合、D3 实际应用验证。
其中 `skills/extraction/` 是可单独交给外部 Agent 的 D0-D3 拆解包，输出合并所需的原材料；
`skills/development/` 是独立的开发包，负责消费这些材料、修改/合并/验收和项目交付。两套包可以重复合同，
但 skill 正文不互相引用。
上游→D0 的变化与 D0→库的变化分别可追溯；阶段转换不把旧证据绑定到新版本。

## 阶段职责与入口

| 阶段 | 负责的结果 | 统筹入口 | 不重复承担的工作 |
| --- | --- | --- | --- |
| D0 来源预处理 | 在可编辑分支/副本整理完整项目，记录上游差异与保留范围，完成 AOCI/CodeGraph 预处理并交付固定 D0 | [来源预处理入口](../skills/extraction/scientific-computation-asset-extraction/references/material_access_and_preprocessing.md#d0-source-preparation) | 不修改官方来源，不宣称科学正确性，不逐项申请已授权的整理批准 |
| D1 来源拆解 | 冻结 D0 全范围现有功能覆盖、Operator/有序 TaskGraph、忠实实现或原实现封装、源码行为对照、疑似错误及复现依据 | [来源拆解](../skills/extraction/scientific-computation-asset-extraction/SKILL.md) | 不重做 D0 裁决，不要求科学正确性证明，不修正 D0 科学行为，不做跨项目去重或正式文档 |
| D2 拆解观察 | 从 exact D1 交付拆出独立科学 claim、修正候选、oracle 需求和证据缺口，形成开发原材料 | [D2 拆解](../skills/extraction/scientific-d2-decomposition/SKILL.md) | 不修正候选，不合并开发库，不替人审或发行 |
| D3 拆解观察 | 在 exact D2 候选上采集有界用户应用、坏输入、恢复与重复性观察，形成开发原材料 | [D3 拆解](../skills/extraction/scientific-d3-decomposition/SKILL.md) | 不写用户项目，不批准资产，不宣称库或发行完成 |
| D2 科学判断与库整合 | 消费 D1 错误记录，科学/数值验证、必要修正及来源差异，基线比较、去重、组装和开发包 | [库整合](../skills/development/integration/scirel-integration/SKILL.md) | 不重做仍有效的源对照，不回写 D1，不给吸收项生成重复文档或审核项 |
| D3 用户应用 | 真实需求、追加输入、坏数据、恢复、独立复跑及科学解释 | [用户项目](../skills/development/usage/scientific-project-implementation/SKILL.md) | 不重复拆源，不用单个案例证明整个库 |
| 最终审核与发行准备 | 汇集稳定代码、唯一正式科学文档、累积差异和证据，交最终拍板 | [最终待审准备](../skills/development/integration/scirel-review-preparation/SKILL.md) | 不把人工作为日常开发调度器，不把开发验证当批准 |

统筹 skill 只维护目标、条件路由、交接和停止条件；专业方法按需加载。
默认先尽量完成一个来源项目的 D1，再统一交付 D2；不按单个算子/TaskGraph 启动整条流水线。
阶段逻辑有先后，但人员和时间独立：D1 交付可封存并由新的 Agent 接续；这是恢复能力，不是默认等待。
已授权整项目交付时，按[连续交付](requirements/scirel-workflow.md#已授权整项目目标的连续交付)提前准备接收，
以全部核心能力及必要组合的无源码安装应用为终点，新冻结优先验收并连续完成包合入和文档同步。
项目内可按科学家族并行；不同项目可处于不同阶段，无须让每个项目同夜走完全部阶段。
明确约定的局部试点/部分接收可使用合格有界批次，其科学资格不等于调度指令，
也不得称完整项目 full_freeze。D2 开发 wheel 可供 D3 使用；D3 按用户目标与影响选场景，
不为每个库变更发明新用户项目。交付要求见 [项目接续合同](requirements/scirel-workflow.md#项目交付与异步接续)。

D0/D1/D2/D3 skill 方法跨学科、跨库名、跨 Agent 与执行平台。本文描述 SciRel 对方法的一次集成；
本机路径、包名、harness、模型、子代理类型与资源预算由运行配置提供，不写为通用 skill 的前提。
当前部分 skill 发现名称保留兼容性，不要求目标库采用 SciRel 包名；仓库脚本/API 属于实现适配。

协调者先交付项目隔离边界、可读取的确切官方来源、独占结果目录、适用 skill 和项目目标。
来源运行依赖在 D0 范围判断后，按保留入口和必要对照逐步准备；不预装全部上游依赖来换取“环境就绪”。
科学 wheel 运行与项目开发的依赖分别选择和验证，按[三类依赖边界](design/project-and-distribution.md#三类依赖与独立环境)
在既有环境合同中记录用途、清单和证据；就绪结论必须说明对应入口与用途。
官方来源始终只读；D0 的工作分支/副本可编辑，冻结交给 D1 后只读。源码、依赖/工具、探针、缓存、证据与产物分别存放，
工具与依赖须能从环境定义重建，不能只存在于待清容器的可写层。worker 复用固定 D0、索引和准备环境。
环境交付包含可复用的构建定义、依赖/镜像身份和启动命令，并实际检查官方源只读、阶段写权、结果持久化及必要依赖。
已选容器后不能以安装了 CLI 代替运行验证；用户明确改变隔离要求时，先保存 checkpoint，再在指定容器接续；按平台影响验证，不机械重跑已有科学证据。
项目 owner 自主选择前沿、拆解粒度和本阶段验证，维护既有项目 checkpoint，持续执行到交付或真实阻塞。
D1 修复自己引入的抽取、封装和比较缺陷；来源自身的科学/数值疑似错误记录后交 D2。
不同项目独立并行；同一项目的科学队列和集成仍由其唯一 owner 负责。

外层协调者按阶段记录定期抽查方法、方向、证据真实性、资源和写权，不逐算子派步骤，
不把每个局部增量回报都变成一次接收、哈希复核、总结或确认，不另建重复状态报告。
只有方法/范围偏离、持续无进展、无法自行解决的阻塞、资源或写权冲突，以及阶段交付需要介入。
owner 空闲但项目未完成时，沿用持久 checkpoint 恢复其自主执行，不必替它排下一组科学步骤。
真实范围选择、超出授权的行动或外部依赖裁决才交用户决定；人工批准与发布仍单独授权。

## D0：整理来源并固定交付

从已核定的官方版本建立可编辑 Git 分支或副本，复用有效来源身份与回执。D0 内部按以下顺序推进，
在既有 checkpoint 分别记录首次索引、源码整理、增量维护和必要纠错；它们不是四次项目启动或额外审批：

1. **先建立完整初始索引。** 固定初始来源身份、工作根和受管理范围，接好工具后按 AOCI 当前 Guide
   完成首次语义索引，取得实际覆盖、校验及未决事项。已有有效完整索引时直接复用。初始索引描述当前
   源码及其已知限制，不要求先完成全部清理、科学修正或 D1；不能用占位、模板或明知错误的条目凑齐数量。
   首建期间保持所绑定源码稳定；发现不阻塞索引的清理项先保存位置与证据，留到下一步处理。
2. **再整理源码。** 用已建立的 AOCI 和结构视图定位项目、核对真实源码，完成下述有依据的 D0 清理。
   CodeGraph 可在初始来源上准备，保留其语言覆盖限制；不把完整构建或科学运行成功当作读取源码建索引的前提。
3. **稳定后增量维护。** 对实际增删改、重命名及受影响关系，按实时 Guide/Maintain 取得当前完整批次，
   更新 AOCI 并按工具能力更新受影响的结构索引。没有变化且已对齐时跳过维护；不为每次编辑或每个文件
   重开全仓流程。工具内部全仓指纹检查与模型重新阅读、创作全部语义条目是不同成本。
4. **对齐后冻结 D0。** 把最终源码、索引、环境及必要验证绑定到同一交付，按原合同完成阶段验收。
   初始索引完成、后续维护完成和整个 D0 完成分别报告；机器条目数不代表语义或科学资格。

必要的访问、安全或无法读取来源问题先有界解决；必须在首建中改源时走当前失效绑定/恢复协议，保留
仍有效的工作。首次建立的真实失败也按 Guide 修复，不能冒称完成后推迟处理。首建完成不自动触发
全量 `cognition_optimization` 或第二轮逐条重审；局部语义问题沿当前工具允许的定向修正路线处理，
只有已证实的影响范围需要全量复核时才采用全量计划。已经启动的可选优化不因剩余数非零而自动成为
D0 门禁；先完成或安全保留已委派批次，在现有证据上区分必要纠错与措辞、压缩等可选优化。
保留原计划、当前绑定、已完成进度及真实未复审范围，核对当前工具支持的定向更新路线；工具允许时可
保留未完成的可选优化 checkpoint，先完成已知缺陷及其依赖范围的受治理修正。不得删改 checkpoint、
伪造已审/no-change、制造源码变化或以缩减受管理范围代替修复。没有取消接口不等于必须继续全量复审；
真实协议阻塞与可选计划未完成分别记录。最终 D0 仍需完成已知缺陷闭环、普通增量对齐及原定交付核验。
全量修复须有广泛失真的具体依据，不能仅由旧条目被替换的数量或空的可选字段推断。

D0 owner 按授权对整个项目
清理不完整分支、明显有问题代码和失效入口，并检查相关调用者、导出、测试与示例。删除或修正须有来源证据，
不能因为索引漏项、语言不支持或当前难以运行而直接删除。依据不足的科学疑点保留明确限制，后续交 D2 判断；
已授权范围内自主处理，不逐项请用户批准，也不为 D0 强行开展无限的科学正确性研究。

在既有项目接续入口引用上游 URL/版本/许可、D0 提交或内容身份、可核对的 diff、剔除/修正理由与证据、
保留范围和未决限制。D0 是独立的派生版本；这些说明使范围透明，不构成另一个审批表或科学认可。
代码稳定后，对齐已有 AOCI 与 CodeGraph 视图，记录实际根、绑定 D0、工具身份、覆盖与缺口，
并验证后续 owner 实际能读取与定位来源。结构索引不能生成 AOCI 语义，也不能裁决科学范围。

交付可分享的固定 D0、上述接续入口、环境定义和可取得的索引/必要证据；凭据、缓存和探针不混入源工件。
新 owner 应能在项目独立容器中接续，不依赖原会话或旧容器存活。冻结后需要改源时另产 D0 successor，
重新绑定受影响索引与证据，不回写旧交付。D1 的完整覆盖分母是接收的 D0，同时保留官方上游到 D0 的差异。

用户明确要求清空旧运行且不备份时，按精确清理范围执行，保留指定来源、工具和凭据；旧运行中的有效经验
写入对应方法，不要求保留已授权删除的旧副本或把旧回执继承为新 D0 资格。

## D1：完整性与源码行为保真

D1 的验收对照是接收的冻结 D0 保留科学范围内的行为，包括影响物理结果的默认值、分支、精度、索引、状态变化、调用顺序和失败。
对照科学输入、输出与状态含义，不要求逐位浮点一致、相同内部实现、绘图、界面、命令壳或错误文案。
求解所需的数据、几何、边界和收敛仍属于核心范围；明确有科学含义的离散字段保持精确比较。
D1 不重新裁决 D0 的剔除/修正，不为通过验收继续缩小 D0 范围；完整 D0 保真不能表述为完整官方上游保真。
忠实复现来源的错误结果或可复现失败可以通过对应的行为对照；这不证明科学正确或适合应用。
源码未定义行为不能臆造稳定期望，无法取得的运行条件仍是明确验证缺口。
原实现可直接抽取或封装，内部允许 Python、C/C++、Fortran 及混合语言，不要求统一改写算法。
`source-free` 指不依赖原 checkout、外部源码环境或在线服务；包内合法保留并绑定来源的实现、
本地二进制和声明依赖可以使用。保存构建配方、许可、ABI/平台限制、状态初始化与隔离约定。
整体封装可以先打通对照，但仍须交付来源支持的可复用局部能力及其组合，不能只包住原入口就称拆解完整。

测试使用原样例和自行构建的来源可接受输入，同时运行原实现与抽取实现，比较输出、状态与异常。
按重要分支、边界和生命周期补案例；复用有效原始结果，不要求额外解析解、物理残差、实验校准、
收敛证明或独立科学 oracle。保留原有比较容差，缺少判据时根据原实现精度和运行条件先定比较规则。
源码已知行为可以作为期望；禁止复制答案到实现中或根据候选误差放宽规则。
每次失败先区分抽取不一致、来源原有失败、比较器错误和运行依赖失败，不把它们合成科学失败。

疑似来源错误在已有注释/证据记录中保存：确切来源位置、触发输入/状态、观察结果、影响范围和
复现证据；区分已复现事实与待确认推测，注明供 D2 判断。无须先推导修正方案或新增正式报告。
本轮需要的科学修正版另存后续候选及其证据，不能覆盖忠实版本；用户授权清空旧运行不因此被阻止。

盘清源项目的科学能力、实现、调用顺序、状态/反馈及边界。交付可执行算子、机器可读图和必要 glue，
来源位置/版本、输入输出映射、源实现对照、数值证据与明确缺口。不能以文件数、字段数或文档数量替代完整性。

局部算子完成只推进本项目的 D1 进度。项目交付汇集全来源覆盖、资产/依赖与处置、有效验证和
剩余缺口；有阻塞时保存可恢复快照与重开条件，不能靠送出一个已完成算子宣告项目完成。
在既有 bundle/证据记录上给出简短接续入口及可取得的工件、依赖和复跑方法，使新 owner 不必
阅读原聊天或恢复原临时环境。科学证据单独封存，callable 包仍保持 source-free；不重复写正式资产文档。

代码、YAML、签名、docstring、测试或已有记录能唯一表达的信息直接引用。
不能可靠恢复的单位、约定、假设、分支选择或证据局限补在一个最小科学记录中。
缺少正式 operator.md、task_graph.md 或根报告不构成科学不合格；缺少科学含义、来源映射、
源对照或真实结果仍是相应科学缺口。D2 结构转换成功不自动确认 D1 科学合格。

断言写错时按当前阶段确认期望和判据：D1 对照原实现，D2 科学修正使用独立科学依据；再重放已有原始输出或最小验证；
不能从输出反推期望、调容差或改科学含义。脚本位置、展示格式、文档路径或包装摘要问题，
能确认原实现、输入、环境和结果归属时修复引用、检查新包装并复用数值证据。
不能证明归属、原始输出不足或科学行为变化时，只补必要证据；不伪造旧 receipt 或回写冻结记录。

## D2：整合后生成正式文档

接收上游→D0→D1 来源关系和 D1 的错误/疑点记录，逐项给出修正、保留明确兼容变体、排除或未决的处置及依据。
D0 预处理不免除 D2 的科学正确性职责；本阶段在派生候选中处理问题，不重开已固定的 D0 范围裁决。
科学和数值正确性验证在本阶段按保留能力的主张开展；来源对照通过不自动关闭这些门槛。
修正先保留失败回归，说明相对来源的有意差异，再验证改变的合同和受影响依赖。

## 最终审核

以**上一可信版本**为基线呈现累积科学增量，不逐开发提交审批。独立 Agent 审查记录真实身份、
模型版本与发现，可走通开发链路，不能冒充人类认可。保留增量完整可评估后送审；
未解决科学缺口补证或明确排除，不强迫人类接手日常调试。送人前完成作者自检、独立 AI 挑战和必要的
修正复核；多轮审核以新增依据及未决问题为驱动，不按固定票数、统一阅读量或无上限轮次运行。
已确认源码错误时，专家审核的正常对象是修正并验证后的实现。对应审查页说明原源码实际表现、
判错依据、具体改动、修正后结果及仍有的限制；原始证据可下钻取得。修复记录不能只写“已修复”，
也不把尚可由 Agent 完成的实现工作转交专家。
所有最终保留的新增/改变项仍需人工决定，按风险/不确定性分配注意力，低风险项可明确批量确认。

待审快照绑定 Git、exact documents、代码/测试、比较处置和有效证据；已有 wheel/catalog 同时绑定。
SciRel 将稳定待审快照登记为统一发布索引中的候选版本；返工另建关联版本。索引是最终发布版本的
选择入口，catalog、wheel 和单次 manifest 只绑定该版本的实际内容，不自行授予发布状态。
review_units 只包括保留新增/改变项；input_dispositions 完整记录无改变的复用、重复或覆盖。
纯无变化批次终结为 no_changes，不产生新 draft、审核项、批准或 release。复用不提升目标信任状态。
上传后不静默覆盖；返工另建 successor，保留原版及审查记录。人工最终可要求返工或排除；
批准只覆盖确切版本及依赖，科学实质变化须重新确认。

## 验证、提交与发行

```powershell
pwsh ./scripts/check.ps1 -Mode affected -ChangedPath src/scirel/<domain>/<asset>.py
pwsh ./scripts/check.ps1 -Mode affected -BaseRef <merge-base-or-release-ref>
pwsh ./scripts/check.ps1 -Mode focused -TestPath tests/<affected-test>.py
pwsh ./scripts/check.ps1 -Mode full
```

内循环按影响选检查并复用有效证据；纯文档验证结构、链接、signature 与相关示例，不重跑源数值。
共享合并前运行适当工作流/科学测试，发行再运行 release 门禁。
交付实际文件、SHA、检查和未验证边界；按 owner 聚焦提交并合并，保护冻结记录及其他贡献者的成果。

安排验证前先定位改变的事实与其影响范围；沿用已有 run 记录，不新增逐项审批表。

| 改变或缺口 | 最小必要动作 |
| --- | --- |
| 路径、包装、报告或文档呈现变化，科学代码/输入/运行条件仍可核对 | 修引用或新绑定；验证结构及受影响文档示例，复用数值结果 |
| 比较器或断言错误，原始输出足够且正确期望有独立依据 | 保留原失败；修比较器并重放原始输出，不调容差或倒推答案 |
| 科学实现、源输入、依赖或数值相关运行条件改变 | 先建立适当回归，再验证受影响科学闭包和反向依赖 |
| 原始结果不足、来源归属不明或独立依据缺失 | 保持该项缺口，补最小缺失证据；不重跑无关项目或整个链路 |
