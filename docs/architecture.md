# SciRel 架构与科学资产合同

本文定义 SciRel 自身的长期边界。SciRel 从保存的 L1 产物开始拥有 candidate、自动检查、标准化、专家审核和 release 的领域流程；CodeFusion 只提供 artifact、job runner、身份、队列和审核 UI 等宿主能力。CodeFusion 的数据库、Rust owner、宿主审核状态和源项目目录都不是 SciRel core 的运行时依赖。

保存的多项目 L1 目录可以使用项目级 inventory 作为结构探针，模型也可以直接检查保存的产物并形成候选。inventory 只保留来源路径、摘要、测试归属和显式依赖缺口；探针本身不复制实现或授予批准。合法来源实现可经 D1 抽取封装和 D2 整合进入包，候选来源记录不表示专家批准。参考探针和不同批次的历史盘点见 [`l1-inventory.md`](design/l1-inventory.md)。

新流程的权威需求和设计分别见 [`scirel-workflow.md`](requirements/scirel-workflow.md) 与 [`scirel-workflow.md`](design/scirel-workflow.md)。本文件中的历史 admitted 记录仍可作为开发期 provenance fixture，但不再是新 workflow 的唯一输入。

## 开发项目与用户科学包

SciRel 项目拥有生产科学库的完整开发与治理过程，用户核心交付为确切版本的 `scirel` 包。
`src/scirel/` 提供科学运行实现；workflow、审核状态、skill、来源工件、开发工具和宿主适配由项目层维护。
普通 wheel 只收集 `scirel` 与其子包，必要本地组件/数据及许可证等分发元数据也须进入实际发行物。
用户文档和可选 Agent catalog 绑定同一兼容 wheel 与能力闭包；文档可在同一 `major.minor` 主线上有独立编辑修订号，但每条 exact document 的实现版本仍精确指向安装的 wheel。运行不加载完整开发材料或审核状态。
wheel 的 patch 或 dev 维护批次也在该主线上产生新的兼容 wheel；文档的 `compatible_wheel` 与
`implementation_version` 必须随之更新。PEP 440 的 `post` 只用于已有版本的打包或元数据修正，
编辑修订号不能替代实现版本。
历史试验不自动成为后续正式主线的公共能力或永久门禁；仍被引用的来源与许可依据保持可取得。
完整目录、构建及多版本分支/worktree 规则见 [开发项目与科学包交付](design/project-and-distribution.md)。

## 科学领域子包与导入边界

公共 API 按科学领域分到子包，例如 `scirel.field`、`scirel.kinetic`、`scirel.equilibrium`、`scirel.geometry` 和 `scirel.diagnostics`。来源项目记录在 provenance 中，不成为公共命名空间。新增能力优先进入已有领域；细分子领域须有明确的科学问题与稳定边界，避免按来源各建一套相同功能。

简单科学关系和复合 TaskGraph 都通过普通函数入口提供。复合入口归属它解决的问题所在领域，显式依赖其他领域的关系；不要把全部复合计算集中进顶层，也不要用顶层反向导入制造循环依赖。共用实现的合并仍需比较科学合同、单位、默认值与失败行为，不能仅凭名称重命名或吸收。

开发包顶层仅导出领域模块；科学函数和异常类型位于各自子包，不再同时复制到 `scirel` 顶层。当前项目尚未发布、没有外部用户，调整 API 时同步更新调用方和文档，不为旧入口保留无实际消费者的别名、弃用包装或回退层。历史冻结工件继续按原字节保存，后续构建采用新的入口边界。

顶层使用 Python 模块 `__getattr__` 按需加载并缓存领域模块。`import scirel` 和 `dir(scirel)` 不导入科学后端；`from scirel import field` 只加载该领域 facade，访问具体 API 时才加载其真实传递依赖。调用使用 `field.solve_multi_coil_vacuum_field` 或正式函数页的完整模块路径。`from scirel import *` 会加载声明的全部领域 facade，不应作为按需加载的使用方式。

子包边界、按需导入与独立分发是不同层次。目前普通开发 wheel 仍包含 `scirel.*`，运行依赖仍由 `pyproject.toml` 声明。仅拆目录或延迟导入不会减小 wheel 或取消 NumPy/SciPy/Matplotlib 依赖。后续若引入可选依赖或独立分发，必须先核对传递依赖、共享实现与安装兼容性，并分别验证所选能力闭包；已资格化的精确发行继续使用自己的导出和验证记录。

文档采用“领域 → 问题 → 函数 / 复合入口”的阅读结构。学习章节可跨多个代码子包；函数详情中的确切模块与签名绑定正式科学文档，不能为配合章节排列擅自修改 API。维护方法见 [科学手册编写](handbook-authoring.md)。

## 核心对象

### 框架图、TaskGraph 与运行实例

SciRel 的公共资产层级与拆解阶段的项目认知层级不同，不能把它们混为同一种资产：

- 框架图 L0 面向人，描述项目级流程和能力边界；L1 面向拆解模型，指导如何把流程分成可验证的局部能力。框架图是拆解和理解的边界，不是运行时公共 callable。
- TaskGraph 是可复用的局部功能编排，节点可以是 Operator 或嵌套 TaskGraph。它必须有明确目标、可描述的输入输出、独立测试和显式依赖。
- Operator 是具有独立科学语义的可调用计算单元，承担一个完整、可验证的定向计算合同。
- 用户请求产生的动态补全图是运行实例或临时组合；除非经过标准文档、验证和准入流程，否则不会自动成为公共 TaskGraph 资产。

拆解阶段可以采用“一个 TaskGraph 不超过一个框架图节点、通常至少包含两个算子”的粒度经验，以避免把整个项目直接当作一张图。该经验只约束拆解过程，不是 catalog 的绝对最小/最大规模规则；单算子复用、嵌套图和经验证的更细粒度图仍须按功能目标和独立测试判断。

### 科学关系与计算粒度

科学关系（scientific relation）描述物理量或状态之间有依据的方程、约束、闭合、诊断定义或演化规律。
它可以是显式映射，也可以是隐式方程、耦合方程组、微分或积分关系；关系本身不是可执行函数。
例如 `V = I R` 是一个关系，给定 `V, R` 求 `I` 与给定 `I, R` 求 `V` 是不同的计算方向，
还各自需要适用域和失败语义。TaskGraph 中的依赖、顺序和反馈关系是另一层概念，不能与该科学关系混用。

不把“最小科学关系”当作存在唯一答案的物理术语。这里的粒度是相对于已声明来源范围、科学合同和
重组用途的工程选择；一条公式、一个函数、一行代码、一个标量输出都不是划分标准。
选择边界时判断：

- 输出或状态变化能否用科学含义命名，且输入、假设、单位、适用域与数值约定完整；
- 来源是否支持把它作为可独立调用、替换或组合的计算，并能在该边界做有意义的验证；
- 内部若还有满足上述条件、需要独立交付的子计算，则保留那些子边界；其必要依赖和顺序由 TaskGraph 表达；
- 若继续拆分只暴露代数碎片、数组操作或迭代细节，且没有独立科学合同，则停止拆分。

一个合同的结果可以是向量、张量、耦合状态或连同诊断返回的结构体。“一个主结果”不表示只能有一个
返回字段。例如同一磁场映射的 `B_R, B_Z` 不因有两个分量就必须拆开。反之，多个互不相关的诊断
不因共享输入或同处一个函数就应合并。已有多种科学等价的划分时，保留能覆盖来源并支持所需重组的
稳定边界，不为寻找全局唯一的“最小”反复拆包；科学含义或源对照未决仍须解决。

### Operator

Operator 实现一个完整的定向科学映射，而不是科学关系本身。它可以包含多条方程和多个数值步骤；
边界按上面的科学合同与独立交付价值判断。其身份由关系方向、模型与假设、几何与坐标、边界或闭合、单位、轴序、shape/dtype、适用域、数值方法以及失败行为共同决定；名称、模块路径、源码相似度或少量相同样例都不能单独证明等价。

Operator 的规范运行入口是普通 Python callable。函数签名是公共接口的一部分，结构化输入输出合同补充参数名无法表达的单位、shape、轴序、适用域和失败语义。REST、CLI 或平台工具可以包装 callable，但只是适配层；源码块属于实现与证据，不是调用协议。

Python callable 不要求内部为纯 Python。可以封装包内来源实现、C/C++/Fortran 扩展或随包的本地程序，
明确数据布局、ABI/支持平台、依赖、状态初始化/重置、并发隔离和失败映射。构建材料与许可随交付可取得；
运行不访问原 checkout、开发机路径、捕获答案或在线源服务。独立进程封装也须保持可复用能力边界，
其科学计算由绑定的来源组件承担，不在适配胶水里重写。

### TaskGraph

TaskGraph 是组合能力，也是普通 Python callable。它的规范定义是有向、类型化的数据流图，而不是顺序函数列表：

- 节点引用精确 Operator、嵌套 TaskGraph、调用方端口或合同允许的 glue。
- 边描述端口、数据含义、必要转换、条件和失败传播。
- 普通数据依赖必须无环，并可拓扑排序。
- 循环只允许作为显式反馈合同；每个受控循环使用一个稳定 ID，其一条或多条 feedback edge 共同对应唯一合同，并声明状态所有者、初始状态、更新顺序、收敛/停止条件、迭代上限和未收敛结果。
- 调度器可以把某次运行投影成顺序步骤；该顺序不是图的科学身份，不能替代节点和边合同。

因此，普通 TaskGraph 是 DAG；Picard 等迭代能力是“无环单步图 + 有界反馈控制”。把迭代按轮次展开后，每次实际执行仍形成有限的有向执行记录。不得用未标注的环、隐藏重试或调用顺序偶然性表达科学反馈。

TaskGraph 定义与运行实例分开：定义绑定公共入口和精确依赖；实例保存本次参数、状态、分支、迭代和结果。任务参数属于实例，不进入可复用资产身份。

### 科学身份、实现与来源

一个科学身份可以有多个来源或工程版本；共享实现也不意味着两个科学身份可以合并。每次整合必须选择并记录下列关系之一：复用同一身份、保留明确变体、新增能力、兼容替换、仅共享内部实现，或因证据不足保持未决。

来源和许可证义务随身份保留。参考项目的行为是证据，不是 SciRel 权威；采用参考行为时保留其成立条件、适用范围和已知反例，并用 SciRel 合同与回归测试确认最终行为。

### 组装错误与验证边界

组装失败按层处理，不能因为 Python 参数已经绑定就认为科学连接正确：

1. 结构错误：签名、端口、类型、shape/dtype 或必需输入不匹配；
2. 连接错误：选错算子、顺序/分支错误或把不兼容的图连接在一起；
3. 语义错误：单位、坐标系、轴序、归一化或变量含义不一致；
4. 科学错误：组合可以运行，但整体模型、边界条件或守恒关系不成立。

签名和端口校验、单位/量纲、shape/dtype、轴序、输入域、守恒量、残差、正定性、对称性、极限情况和 metamorphic tests 都可以作为自动检查。它们只能证明各自声明的局部性质；不能靠穷举规则证明所有输入下的物理翻译或模型选择正确。形式化证明适合量纲保持、守恒量传播、线性性质和反馈上限等明确合同，不能替代科学审核。

### 能力边界与缺口

L3 运行时能力边界包括：没有对应 Operator/TaskGraph，候选模型/几何/边界/适用域不兼容，缺少关键输入或标准科学文档，需要引入新的变量、单位制、坐标约定或数值方法，或者必须改变已有资产的科学语义。遇到这些情况必须返回结构化的 `capability_gap`，不得让模型猜测一个看似相近的替代资产。

能力扩展遵循“发现缺口 -> 搜索/拆解新来源 -> 形成标准资产文档 -> 科学审核与验证 -> 进入 catalog -> 重新组装”的闭环。skill 可以辅助缺口分析和候选构建，但不能替代科学审核，也不能直接产生公共资产。

## 三个边界

### 候选与 provenance

`provenance/admitted-assets.json` 保存旧流程导出的 52 条开发迁移样本。它的来源路径、版本树、内容摘要、依赖绑定和当时决定标签保持冻结，不能因重构或措辞调整而改写；但这些标签不等于新生命周期的专家批准，也不再是 L1 到 release 主链的治理输入。新候选、机器检查通过、旧 admission 标签或 AI 建议都不能单独产生批准。

### 维护源码与公共 API

`src/scirel/` 是独立演进的库源码。公共 API 按科学领域组织，Operator 和 TaskGraph 都通过普通 Python callable 暴露。内部组合、校验和适配代码不得成为第二套科学事实，也不得在 wrapper 中隐藏新公式、插值、闭合、几何重建或离散规则。

科学行为变化包括公式、单位/轴序、默认值、边界、失败行为、数值方法或 TaskGraph 依赖重绑。此类变化先以失败回归明确差异，并按需要形成新的科学候选和审查；行为不变的工程重构仍要保留旧合同和回归证据。

### 发行与目录投影

`scripts/build_admitted_distribution.py` 可以从历史迁移账本复现 admitted-only staging、wheel、内置 manifest 和内容锁，只作为开发证据。新流程由 SciRel 的统一发布索引选择冻结候选及最终发布版本；候选绑定待审快照，最终发布另绑定批准后固化的基线、确切资产文档和实际构建摘要，不从旧账本推断准入。任何构建成功都不单独产生批准或发布事实。

面向大规模发现的 catalog 应是从索引选定的同一发行内容锁重建的投影，而不是发布版本索引或新的科学真值。每条精确记录至少需要：

- 稳定资产 ID、kind、公共 module/symbol 和运行时 signature；
- 结构化输入输出，以及模型、几何、边界、单位、轴序、shape/dtype 和适用域；
- SciRel implementation version 与稳定依赖 asset IDs；
- provenance 摘要、验证范围和证据上限。

不得从函数名或源码猜补缺失的科学元数据。当前准入账本与 wheel manifest 已覆盖入口、准入和依赖绑定，但尚未覆盖上述完整发现合同；在补齐可信元数据前，应把它标记为 metadata gap，而不是生成看似完整的目录。

标准 exact record 使用 `scirel.asset-document.v1`。MCP、Codex、Claude Code、CodeFusion、CLI 和云执行平台只消费同一份 record/catalog/wheel；adapter 负责协议、权限与执行环境，不得成为新的资产身份或科学合同来源。

## 大规模发现

资产规模增长到数万 Operator、数千 TaskGraph 时，不把精确合同一次性放进模型上下文。目录按以下层级提供渐进披露；分片、稳定 ID、反向依赖和增量构建的详细合同见[规模化目录合同](catalog.md)：

```text
领域/关系路由索引
  -> 有界候选摘要
  -> 最终候选的 canonical contract 与 release binding
```

路由优先使用输出、关系方向、模型、几何、边界、生命周期、单位/轴序/shape 和适用域；名称、来源项目、关键词或向量相似度只提高召回率，不能覆盖类型化不兼容。每次检索记录实际加载的 snapshot、范围、候选和未搜索区域；预算耗尽只能得到有边界的 shortlist 或 metadata gap，不能据此声称“没有该能力”。

## 依赖与失败原则

- 科学函数必须在没有 CodeFusion、源项目 checkout、数据库和网络的环境运行。
- TaskGraph 绑定精确依赖闭包；缺失、冲突或未准入依赖 fail closed。
- glue 只做明确且无科学含义的重命名、结构转换、无损单位/dtype/轴序转换或状态传递。
- 每项证据只支持其实际覆盖的模型、输入域、容差和运行环境；测试通过不扩张科学结论。
- 公共 API 的破坏性变化必须说明调用方、版本影响和迁移路径，不能静默删除旧入口。
- 每个资产必须有可机器解析的直接测试归属；TaskGraph 精确依赖和 Python 共享模块 import 形成反向影响图。日常变更从该图选择最小闭包，无法归属时扩大到全套，不能以速度为由跳过不确定影响。
