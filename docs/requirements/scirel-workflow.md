# SciRel 来源预处理到 Release 需求

## 目标

完整链路的输入是来源码及声明依赖，输出是脱离原源码环境可安装运行的 SciRel 包。
D0 从只读官方来源建立可编辑分支/副本，先完成或复用初始 AOCI 索引，再进行有依据的项目整理，
对稳定改动增量维护 AOCI/CodeGraph，最后保存可分享的固定交付；首次索引完成不自动要求全量重审。
D1 忠实复现该冻结 D0 的现有功能与失败行为；D2 承担科学判断、数值正确性验证、必要修正和库整合；
D3 验证确切包在实际任务中的使用。原实现可作为包内 Python/C/C++/Fortran 组件封装调用，
不要求纯 Python 重写。合法来源、依赖、构建和 ABI 限制必须可取得，运行不依赖原 checkout。
完整入口封装不替代局部可复用能力及 TaskGraph 的拆解。

D0 可以按授权清理不完整、明显有问题的代码；必须保留官方上游身份与可核对差异，说明剔除/修正依据、
保留范围和限制。D0 准备不等于科学正确性认可，既有授权不变成逐项审批。D1 不重做 D0 范围裁决，
也不能把完整 D0 保真称为完整官方上游保真。具体方法见 [D0 流程](../development-process.md#d0整理来源并固定交付)。

D1 可以自行构建冻结 D0 可接受的测试输入，以该版本原实现为行为对照，比较输出、状态、顺序和异常。
来源自身的疑似错误保存位置、触发条件、观察、影响和复现材料，供 D2 判断与修正；
它不自动使忠实性失败。抽取引入的不一致必须修复，缺少对照或未定义行为必须明确披露。
独立物理依据、实验准确性和科学修正不作为 D1 默认门槛；D1 完成不等于科学正确性认可。

SciRel 拥有 D0/D1 方法及项目交付；从保存的 L1 产物开始，D2 完成语义理解、与开发/可信基线及当前未发布候选池比较、开发整合与验证、最终待审冻结、专家拍板和 release。CodeFusion 是中性的 Agent 宿主，不拥有 SciRel 的科学状态和资产语义。

语义理解和标准化由加载 `scirel-integration` skill 的模型完成；代码不尝试用固定状态机、脚本或 JSON patch 代替这项工作。模型在隔离开发分支完成代码整合、修正、测试及内部 wheel/catalog；可信版本保持只读。正式文档在 D2 去重和代码稳定后生成，重复吸收项仅保留本阶段的来源和处置依据。人类在最终稳定增量处拍板，不成为日常开发前置条件。阶段职责与条件路由以 [开发流程](../development-process.md) 为准。

## 整项目完成：核心物理能力可独立替代

整项目技术完成意味着：移除来源项目 checkout、开发环境、探针和捕获答案后，仅安装确切 SciRel 包及声明依赖，仍能完成来源项目的全部核心物理任务。绘图、界面和文档生成等非核心功能可明确排除；求解必需的数据读取、几何构造、边界条件、状态演化与收敛控制不能以“辅助功能”为由排除。

项目接收必须保存上游核心物理能力到冻结 D0、D1、最终 Operator/TaskGraph、安装包和 D3 应用证据的逐项对应。普查包含上游到 D0 的剔除项：有核心能力被移除或尚未复现时，原有完整保留范围的阶段资格可以保留，但不能据此宣称整项目可替代。文件数、函数数与测试数量用于定位，不能代替能力覆盖判断。

同等物理能力不要求复制源项目的已知错误，也不要求所有数值逐位相同。D1 保留冻结源码行为；D2 对已证缺陷实施有依据的修正，记录差异与独立物理/数值验证。模型、输入域、边界、单位、状态、精度与失败行为均须有明确合同；未完成的核心能力保持缺口，不能靠缩小声明完成计数。

D3 在无来源 checkout、无捕获答案依赖的干净安装环境中，覆盖全部核心能力及必要组合，核对有效输入、边界/非法输入、失败与不收敛、状态和有依据的参数变化。离线运行用于证明无隐藏在线依赖，不要求删除用于审计的来源档案。逐项证据全部闭合并实际合入 canonical 与精确包、文档保持一致后，才计整项目技术完成；人工科学认可与公开发行仍分别记录。

## 项目交付与异步接续

本 workflow 属于 SciRel 开发项目，管理科学库的生产和发行证据；用户安装的 `scirel` 包不需要
workflow、审核队列、skill 或宿主服务。普通科学构建只包含科学库及必要运行材料；
可选插件/catalog 由平台独立部署并绑定兼容版本。历史试验不定义后续主线的构建范围或永久门禁，
不同整合及发行路线在隔离分支/worktree 进行，见 [项目与科学包边界](../design/project-and-distribution.md)。

D0 交付固定代码、上游到 D0 的差异与范围、环境定义以及绑定该版本的索引/必要证据，供新 owner 独立接续。
每个项目使用独立容器；依赖/工具、探针、缓存、证据、产物分开，不依赖旧容器的隐藏安装。各 worker 复用
同一固定预处理结果；来源和索引身份未变时不逐区域重建。来源选择与准备记录沿用已有入口，不另建 registry。

D1 的默认交接单位是一个冻结 D0 项目：先尽量完成该项目整个保留范围的科学普查、拆解、依赖闭合和源验证，
再保存项目级交付供 D2 接收。算子、TaskGraph 和科学家族是阶段内部的实现、验证和并行单位，
不是每完成一个就自动启动 D2、D3 的流水线单位。未完成能力、外部阻塞和明确排除范围必须留在
项目普查与缺口记录中；保存项目快照不等于完成 D1，不得继续缩小接收的 D0 范围以冒充完整项目。

D1 全项目抽取、源数值/行为对照及自包含交付完成，经独立完整性复核并由接收 owner 核对后，
可以把整个项目产物送入 D2/D3；不按算子、局部家族或 partial 结果逐项触发整链。
人工或调度器可以按项目管理接续；阶段间可有正常空档，这不影响项目内部连续拆解。

D1、D2、D3 可由不同 Agent/团队在不同时间执行。D1 交付后可以结束运行；一个月后新的 D2
仍应能只凭保存材料接续，不依赖原会话、原 Agent、在线源服务或仍存活的临时环境。
项目交付在现有 bundle 与证据目录上提供一个简短接续入口，引用上游与 D0 确切身份/许可、二者差异、D0 全项目覆盖与
逐项处置/缺口、实现/图及依赖、源输入/原始输出/判据/验证证据、运行依赖与复跑方法和工件身份。
引用必须可随交付取得；原始完整源快照和验证材料可独立封存；合法抽取的运行实现可以进入
source-free callable 包，原 checkout、探针、捕获答案和隐藏环境不能成为运行依赖。
这些是已有事实的定位入口，不另造一套重复科学文档。机器结构检查不能替代内容与科学完整性。

D2 接收时固定该项目交付，并对照当时的开发/可信基线和未发布候选池进行比较及整合；
完整记录所有输入的处置和依赖，不把一个月前的库比较结果当作当前事实，也不改写 D1 快照。
时间间隔或换 Agent 本身不使源数值证据失效；只有归属不足或受影响科学事实改变时补验证。
D3 消费稳定的整合版本，按实际有用任务选择资产组合与应用证据，不要求每个算子/图各建一个应用。

明确约定的局部试点或部分接收可使用合格 `bounded_delivery`，但其范围、未完成部分和接续条件
必须明确；有界科学资格只说明该部分可用，不自动触发下游调度，也不改变按项目交付的默认方式。
项目交付粒度与最终审核粒度分开：保留增量仍以唯一资产文档呈现，审核状态和决定仍逐项绑定。

## 生命周期

```text
candidate
  -> automated_checking
  -> automated_ready | automated_rejected
  -> no_changes (全输入已比较且无保留增量)
  | draft
  -> review_pending
  -> review_in_progress
  -> needs_evidence | rework_requested | rejected | approved
  -> approved frozen-version confirmation/build
  -> released
```

候选包可以包含数十或数百个 Operator/TaskGraph；上述审核状态应逐项解释，而不是给整个批次加一把锁。上传前的 `draft` 可以由模型整合、替换或撤回；上传后每项 `review_pending` 都已有确定的初始内容版本，队列中没有模型继续改写。查看某项完整详情只记录该专家看过的版本，不改变同批其它项。领取是另一件事：它记录本轮修改的基点并授予该项的独占写租约；未领取的授权专家仍可只读查看。返工保留先前版本和审核记录。SciRel reviewer body 已实现逐资产投影、只读打开、精确版本决定、完整 successor 和批准子集返回；租约、版本历史与 diff 仍由 CodeFusion 通用工作台实现和验收。

候选生成与候选审核/固化是两个异步流程。模型提交批次后即可结束运行，不等待耗时不可控的人工审核。逐项 `approved` 只使该项有资格被上传者取回并进入独立固化流程，不表示整个批次已批准或已经修改 SciRel。只有批准项及其依赖闭包完成固化且 release 构建成功，才能产生 `released`。未批准内容可以进入明确标识的开发基线、内部 catalog 和 wheel，但不得进入可信/公开发行。D3 可以使用开发版本并披露信任状态；Agent 独立审核记录真实身份和结论，不伪称人类批准。

## 领域对象

- **L1 bundle / payload**：来源项目拆解阶段保存的真实输入。目录或 ZIP 先由 SciRel 的转换入口生成 `scirel.l1-bundle.dev`，逐文件保存安全相对路径、原始内容和摘要；`scirel.import_l1` 再从这个受 source Artifact digest 绑定的 bundle 映射资产。CodeFusion 不得手工构造资产列表或猜测 domain 映射。SciRel 不依赖源项目 checkout、CodeFusion 数据库或网络，也不在转换或导入时执行输入代码。
- **L1 inventory**：`scripts/build_l1_inventory.py` 提供的可选结构探针。它可以帮助定位相对路径、直接测试和显式依赖缺口，但不是模型整合 L1 的必经输入或标准化协议。
- **CandidatePackage**：绑定 `run_id`、来源 artifact、source digest、单一 `project_id`、候选资产和自动检查结果。多项目 inventory 必须先拆成 `to_project_l1_payloads()` 的独立 payload，不能在一个 candidate 中混合推进。
- **Candidate comparison view**：冻结 SciRel 基线、全部当前未发布候选和本次 L1 输入的联合检索视图。它用于提前发现重复、可合并项和冲突；未发布候选可以在隔离开发包中运行，但不改变可信基线或自动获得认可。
- **StandardizationSubmission**：模型完成语义工作后的正式交接，绑定 exact candidate/source、SciRel Git base、未发布候选池快照、harness/model/skill 身份，以及保留增量的逐项文档、代码或无代码理由、测试、处置、依赖、证据和 gaps；无变化输入使用可选 input_dispositions 绑定目标版本和比较证据。它不携带或覆盖自动检查结果。
- **StandardizedDraft**：确定性门禁接受 submission 后形成的开发期对象。资产文档作为专家主入口，逐项三件套和模型运行身份保存在其 evidence 中；批次只承载来源和比较上下文，不应成为审核锁粒度。
- **Item revision / review event**：每项 `scirel.review-item.dev` 关联资产文档、代码/测试证据、依赖和 gap；review action 绑定 exact predecessor Artifact，successor Artifact 成为下一 current version。观测、领取、保存、清空修改、放回和提交事件及 diff 由 CodeFusion 保存，同内容可复用快照。
- **ReviewDecision**：仅由显式 `plugin.review.action` 提交产生，绑定 item ref、最终 Artifact ref/digest、host 认证的 reviewer actor、outcome 和说明；同一批次可独立形成多项结论。旧 `ReviewDecision`/`record_review()` 仍只服务单 draft release fixture，不作为工作台逐项事实。
- **ReleaseManifest**：绑定 candidate ID/digest、draft digest、approved asset IDs、catalog ref/digest、wheel ref/digest 和实现版本。
- **Workflow state snapshot**：由 SciRel 序列化当前 candidate、自动检查结果、draft/review 历史和 release，供工作台查询或进程重启后恢复。它不承载宿主平台字段。

SciRel 可以通过宿主 artifact store 保存 `scirel.workflow-state.dev` 快照；这只是状态恢复记录，不是第二套科学资产真值，也不要求 SciRel 引入数据库。

## 自动检查

自动检查按阶段选择：D1 必须保持全来源范围、源实现/数值对照及可运行重组；入库转换只检查路径安全、实现/直接测试、来源映射和图依赖，不执行输入代码，也不以正式 Markdown 缺失拒收。D2 负责比较后代码、受影响测试和开发包；标准文档完整性在保留资产稳定后、catalog 投影/最终待审冻结前检查。检查结果只能说明机器门禁范围内的事实，不能替代专家对科学适用性的判断。

检查失败必须保留结构化原因。存在失败或缺口时，workflow 不得创建可审核 draft。

第一阶段产物不要求完美。`AutomatedCheckResult` 只回传确定性检查事实和证据引用，不能携带
源码、合同、测试映射或依赖的补丁，也不能修改 candidate。模型按照 skill 在隔离的 SciRel
工作树中理解并修复问题，然后对实际变更重新运行适合该问题的检查。未解决的问题继续阻断，
并可按 `next_action` 暴露为 `retry`、`rework_requested`、`needs_evidence` 或 `rejected`。
即使 checks 全部通过，只要结果明确要求 `needs_evidence` 或 `rework_requested`，candidate
仍保持相应阻断状态，不能被自动标记为 `automated_ready`。
对 L1 inventory 形状的结果还要由 SciRel 重新检查直接测试映射、TaskGraph 依赖引用，
并确认 TaskGraph 依赖保持 DAG，不能仅凭执行器声明的 `passed` 清除这些缺口。

## 标准化与审核

工作目录和模型推理过程不固定，但上传边界必须形成
`scirel.standardization-submission.dev`。`SciRelWorkflow.submit_standardization()` 重新校验
candidate/source digest、SciRel Git base、候选池与 skill digest、L1 资产记账和每项三件套内容摘要，
有保留增量时产生 `review_pending` workflow；全部输入均由有证据的复用/重复/覆盖处置解释时产生 `no_changes`，不创建 draft、审核项、批准或 release。每个输入在 review_units 与 input_dispositions 中必须恰好归属一次。该门禁只验证绑定和结构，不把模型自报的命令结果
解释为科学正确或平台执行事实，也不运行模型。

上传者将一个批量候选交给独立工作台，并在项目权限内选择对全部获准审核员可见或指定审核员可见。列表、详情、三件套 Artifact 和动作的权限都必须在服务端复核；可见不等于可写或已领取。专家按单个 Operator/TaskGraph 自行领取，工作台按 item ref 签发带代次的写租约；同一项只允许一个有效持有者，不同项可并行。领取事件绑定当时的内容版本，作为本轮清空修改的返回点。过期或旧代次提交不得覆盖当前版本。

上传时确定的逐项初始快照已经可追溯；首次只读打开完整详情记录所见内容版本，不需要为了冻结内容改变它。持有租约的专家可以保存修改，形成关联前一版本的新提案，不能覆写已有版本；工作台需按文档、代码和测试展示版本间差异。清空本轮修改应恢复到领取时绑定的版本，不删除已有历史。放回队列时保存当前内容版本（未变化则复用已有版本）、记录放回事件并释放租约，该项仍未完成审核，供其他专家领取；放回不是提交，也不能隐式批准。只有显式提交审核动作才记录完成结论及其最终确切版本（未变化也可复用版本），并释放租约。即使内容相同，领取、放回和提交事件仍分别保留；不必为每个事件复制内容快照。TaskGraph 依赖的 Operator 尚未获批准或已返工时，可以继续只读分析该图，但不能绕过依赖闭包固化。

工作台把每项已提交的结论、版本关系和差异集中交还上传者；放回但未提交的修改留在待审核队列。上传者是收集与固化协调者，不因上传而自动成为科学批准者。逐项最终批准必须由有权限的专家明确作出；意见冲突需要有权裁决者处理，不以数量或平台 action receipt 自动投票通过。允许取回已完成的子集，不要求数百项全部审核完毕才开始独立固化。

模型在上传前准备候选时必须同时检索冻结基线、当前未发布候选池和本次 L1；发现重复或可合并时，优先整合上传前草稿以减少重复审核。已上传批次的内容不能由模型静默改写，不以专家是否已经打开或领取为条件。需要模型重新准备时另起短任务，产生可追溯的新候选，并由上传者明确决定后续上传和关联方式。

上传前草稿的撤回只是候选存储取消引用，不新增科学审核状态。已经上传的候选不能以“专家未打开”为理由静默替换或消除其初始版本和平台事件；需要撤回时由有权限的上传者显式操作并保留可追溯记录。

候选文档是专家审核的主入口。新增或改变公共资产时，其中拟议的 canonical asset document 必须使用现有 `scirel.asset-document.v1` 合同；候选代码和候选测试用于核对其主张。缺少科学关系、单位、坐标、适用域、失败语义或证据时登记 gap，不从名称、源码相似度或项目经验猜补。

审核工作台只展示 SciRel 的 draft、证据、依赖和候选差异。CodeFusion 提供 UI、身份和动作投递；审核结论写入 SciRel workflow 记录。

批准只授权候选中明确列出的内容。实施时发现需要改变科学合同、API、依赖或测试主张，必须形成新候选或回到专家审核，不能静默扩大批准范围。

## 批准后固化与候选冲突

批准后由新的短任务确认冻结开发版本与批准内容一致并准备发行，不从头重做已完成的开发整合；原 Claude Code、CodeFusion 或 Codex 运行不需要等待专家。第一版按串行队列处理已批准候选；只有受影响科学身份和依赖闭包明确不相交时，才允许并行固化。

每次固化先把候选审核时的 Git base 与当前 SciRel 基线比较：

1. 相关资产、公共合同、依赖、TaskGraph 和 patch hunk 均未变化时，原样应用批准的候选代码和测试；
2. 基线有无关变化但批准 patch 仍能原样应用时，应用后运行 affected tests 和候选声明的直接测试；
3. 同一科学身份、公共合同、依赖闭包、TaskGraph 或 patch hunk 已变化时，停止固化，不采用 last-write-wins；
4. 冲突候选基于最新基线重新比较并形成关联的新候选。若它因此成为无变化的重复/复用，保留本阶段目标绑定与科学处置证据，可结束为 no_changes；若公共合同改变仍形成新的待审增量；
5. 旧批准记录保持冻结，只证明旧候选曾获批准，不能自动批准新代码。

这里不新增复杂的长期状态机。当前 `approved` 即“已批准、等待固化”；固化成功后才能调用 `release`。冲突时保留原 workflow 和固化失败证据，另起一个候选 workflow。工作台把“已批准待固化、固化冲突、已发布”作为现有记录的投影视图即可。

允许在隔离开发分支整合、提交并构建可运行开发版本，避免长期未提交候选堆积。冻结待审版本相对上一可信版本呈现累积科学差异；不要求每次开发提交先审核。可信/公开发行仍只包括最终批准的确切内容。

## Release 门禁

目标批量流程的 release 前必须满足（reviewer body 已能返回逐项批准子集；批准后固化器仍需消费该子集）：

1. 每个拟发行 item 的最终确切版本已逐项 `approved`，且其候选代码/测试已按批准文档应用到 SciRel；未批准项不随同批次进入发行；
2. 拟发行项没有未解决 gaps，且 TaskGraph 的必需依赖已在维护基线或同一批准固化闭包内；
3. 每个拟发行资产都有稳定 `asset_id`；
4. 实际 diff、资产文档和测试与逐项批准版本可核对，catalog、wheel 和 release manifest 来自同一构建结果；
5. manifest 中的 candidate/batch、逐项审核版本与批准记录的 digest 均与实际 artifact 一致；
6. release version 与 catalog/document implementation version 一致。

最终固化逐项核对获批 revision 所附的代码、测试材料和重新执行的测试结果，与拟发行 Git 内容及
wheel 逐字节或按可验证摘要对应。开发期 finalizer 已接收逐项批准投影与原始 artifact，要求批准
successor 与提交前 revision 一致；它信任审核宿主对 actor 的认证和导出来源，本地摘要不能单独
证明人工身份或发行授权。当前没有可据此晋级的真实批准输入。

SciRel 维护一个统一的发布索引，作为发布候选和最终发布版本的版本入口。冻结待审增量进入候选条目时，
索引绑定确切 Git 版本、拟发行资产及依赖闭包、exact documents、审核版本和证据引用；候选状态不代表批准。
只有逐项批准内容完成固化，并通过许可、依赖、catalog/wheel 绑定和发行门禁后，才可从该候选形成
最终发布条目。条目和决定保留历史及 successor 关系，不回写已审版本；公开消费者只能选择已发布条目。
开发 wheel、catalog 快照、旧 admission 标签及 Agent 审查结论均不能自行创建发布事实。

索引的开发期存储和字段可随首条真实闭环调整；正式发布前须将 SciRel 自有的相关版本与 `.dev` 合同
统一收敛并冻结为 `v1`，核对索引、workflow、文档、catalog、wheel 和公共 API 的绑定，不保留旧
`.dev` 流程兼容分支。旧 52 项历史开发候选不作为本轮索引设计或开发整合的盘点门禁；实际拟发行内容
仍须满足上述发行门禁。

## 测试要求

每个 workflow 变更必须覆盖直接状态转换测试。逐项审核实现需另外覆盖：同批两项并行领取互不阻塞、同项只能有一个有效写租约、未领取只读、上传后无后台改写、首次打开记录该项所见版本而不修改内容、领取版本作为清空修改的基点、保存后 diff、放回保存修改并释放租约但不产生审核结论、提交绑定最终版本、相同内容复用版本但保留事件、过期代次与旧快照不能提交、批准子集不能带入未批准依赖。科学资产测试仍由 `scripts/check.ps1 -Mode affected` 根据资产和 TaskGraph 反向依赖选择；无法归属的 workflow、plugin 或公共合同变化 fail closed 到全套测试。

生命周期 fixture 可以在没有 CodeFusion、数据库、网络和源项目 checkout 的环境中验证 draft/review/release artifact 关联；它不声称能替代模型从真实 L1 完成科学整合。
