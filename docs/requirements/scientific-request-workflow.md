# SciRel 科学请求工作流需求

## 状态与目标

- 状态：开发期需求
- 领域 owner：SciRel
- 可用宿主：CodeFusion、Claude Code、Codex 或其他能够加载 SciRel skill 并调用发布运行时的 harness
- 运行输入：用户请求、用户提供的数据和一个对当前运行环境可见的 SciRel release

本工作流把用户的自然语言科学需求转化为一次有边界、可执行、可解释的 SciRel 运行。它属于
SciRel 对外提供的科学能力，而不是某个 harness 的内置领域知识。宿主负责会话、权限、工具、执行环境、
artifact 和结果交付；SciRel skill 负责科学问题规范化、资产适用性、TaskGraph 语义和科学检查方法。

运行环境只向用户和求解模型暴露已发布资产。资产是否通过专家审核由 SciRel 发布流程保证；求解工作流
不得为每次请求重复证明批准状态。环境可以自动记录实际 release 以便复现，但该记录不是一次科学推理
步骤，也不是面向用户的审核声明。

上段是正式用户运行环境的边界。用户授权的隔离 D3 开发评估可以固定未批准 wheel 与匹配 catalog，
按同样的适用性、调用和结果解释规则验证；所得结论明确为开发证据，不冒充可信发行。
这种评估不等待最终人工认可，不扫描或改写上游未交付资产，也不把开发数据暴露为已发布能力。

## 必须完成的工作

### 1. 规范化科学问题

系统必须先理解问题，再搜索 callable。规范化结果应按实际问题覆盖下列事实：

- 用户目标和请求输出；
- 科学模型、关系方向和需要求解的未知量；
- 几何、坐标、单位、归一化和轴约定；
- 初始条件、边界条件、闭合关系和给定剖面；
- 输入数据及其来源、shape、精度和有效范围；
- 容差、终止条件和期望交付形式；
- 系统引入的假设或默认值；
- 仍未解决且会实质改变模型、适用域或结果的问题。

规范化结果还应把每个关键条件标明来源：用户明确给出的事实、用户文件中读到的事实、exact document
允许的默认值，或系统提出但尚未获确认的假设。用户的目标应对应到预期输出和本次可执行的结果检查；
不能把文件中的数值、合同默认值或系统推测说成用户的要求。

缺失事实会实质改变科学问题时，系统必须请求澄清。允许补充非关键默认值，但必须在结果解释中
明确它们，不能把模型选择或边界条件作为隐藏默认值。

### 2. 发现和匹配能力

系统应从可见 release 的分片 catalog 逐步检索候选，读取入围资产的 exact document，并按模型、
关系方向、几何、坐标、单位、边界、适用域和失败语义判断是否可用。名称、关键词和向量相似度
只能用于召回，不能覆盖科学不兼容。

后续请求新增科学关系、输出位置或结果形式时，系统必须先重新规范化该增量，再围绕新增关系
重新检索可见 catalog。早期 shortlist 只证明当时目标下的候选范围，不能证明新关系不存在，也
不能替代新增关系的 exact document 匹配。

当 catalog 声明为 partial 或检索尚未穷尽时，系统只能说明“当前已检索范围内没有合适能力”。
当完整的可见 release 已被检索且没有合适资产时，返回该 release 的能力缺口。两种情况都不得
用近似名称或更弱模型猜测替代能力。

### 3. 形成和校验求解计划

求解计划可以直接调用一个 Operator、复用一个已发布 TaskGraph，或形成由已发布资产组成的本次
运行实例。运行实例不是公共资产，执行成功不会使它自动进入 catalog。

计划执行前必须检查与本次请求有关的边界：

- 每个资产的适用域覆盖其实际输入；
- 端口、单位、shape、dtype、坐标、轴序和归一化可以正确连接；
- 普通数据依赖构成 DAG；反馈或迭代具有显式状态、更新顺序、停止条件和上限；
- 表示转换是无损且可说明的；新的插值、闭合、离散、几何重建或科学换算不能藏在 glue 中；
- 所需输入、边界和终止条件均已解析。

动态组合时，每个节点输入须能追到用户输入、文件、已声明默认值或上游节点的具体输出端口；边须
说明连接的科学含义。计划在执行前固定本次实际使用的输入、资产和连接。之后若用户纠正关键条件，
应重新规范化并校验新计划，不得把旧计划的执行证据挪作新请求的结果。

校验失败必须停止执行并指出具体不兼容，不能靠 Python 参数能够绑定来推断科学连接正确。

### 4. 执行和结果级检查

系统使用可见 release 中的 SciRel callable 执行已校验计划。科学异常必须保留原始原因；不得在
失败后静默切换模型、资产或单位约定。

可被后续请求复用的中间产物必须携带继续使用所需的科学绑定，或强绑定到携带这些事实的输入文件。
至少应覆盖实际坐标轴、coordinate basis、support mask、关键输入来源摘要和本次生成关系。若历史产物
只保存了值数组而缺少这些元数据，后续请求只能在检查当前配置形状和来源摘要一致后有界复用，并必须说明
不能证明原始运行的坐标字节一致；不得把这种结果解释成强于产物本身支持的来源证明。

当追加需求需要对照或继续使用先前交付的图表、文件时，旧结果必须保持可区分且可访问，新结果不得
静默覆盖它们；交付说明应能指出各结果对应的输入和请求。若用户明确要求替换且旧结果不再用于本次
任务，可按宿主的 artifact 更新约定处理，不要求一律为每个文件创建新版本。

每次请求应根据问题选择有意义的结果级检查，例如量纲、有限性、输入域、边界条件、守恒量、
残差、收敛、正定性、对称性、极限情况或问题特有的不变量。检查必须区分：

- 已检查且通过；
- 已检查且失败；
- 对该问题不适用；
- 本次未检查或现有能力无法检查。

测试通过、函数正常返回或某个局部不变量成立，都不得扩张 exact document 声明的证据上限。
数值结果中的有限值、零点、趋势或图形结构只是计算观察；除非本次计划已经包含相应的科学关系、
场量和检查，否则不得解释为共振、吸收、沉积、稳定性或其他物理机制。

运行异常、输入或端口错误、能力不适用、以及结果级科学检查失败应分别说明。修复文件路径、容器
格式等不改变科学问题的执行错误后，可以重跑受影响步骤和检查；改变模型、资产、单位、边界、
容差或连接时，必须重新校验计划。科学检查失败不得被静默重试或解释成通过；无法定位或修复时
停止并交付失败证据与限制。

### 5. 交付结果和可审计解释

用户应得到请求的数值、图表或文件，以及能够核对本次计算的简明说明。说明至少回答：

- 系统把用户需求理解成了什么；
- 使用了哪些假设、默认值和用户输入；
- 选择了哪些科学能力，以及为什么适用于本次问题；
- 本次运行实例如何连接这些能力；
- 执行了哪些结果级检查，结果如何；
- 仍有哪些限制、未检查性质或能力缺口。

审计记录保存可观察的输入、决定、调用、检查和结果，不保存或要求模型的隐藏思维链。

## 逻辑产物

首版只要求四类逻辑产物，不冻结统一文件名、JSON schema 或数据库表：

1. `Normalized Problem`：规范化问题、假设和未决问题；
2. `Solution Plan`：能力匹配、运行实例和执行前校验；
3. `Execution Evidence`：实际输入、调用、结果和结果级检查；
4. `Result Explanation`：面向用户的结果、依据、限制和缺口。

同一份文档可以承载多个逻辑产物，harness 也可以把它们存为独立 artifact。只有观察到稳定的跨框架
消费需求后，才把其中的必要字段提升为机器合同。

为了便于用户和专家复核，这四类产物至少应能投影出三个关联视图：需求、事实来源、假设与缺口；
选用的能力节点及其输入输出连接；实际调用、结果和检查证据。这些是同一次请求的可读视图，
不要求额外的持久图数据库或统一报告格式，也不包含模型隐藏思维链。

## 完成结果

一次请求至少应明确落入以下结果之一，不要求为它们建立持久状态机：

- 需要用户澄清；
- 当前检索范围不足；
- 可见 release 存在能力缺口；
- 求解计划不合法；
- 执行失败；
- 结果级检查失败；
- 结果完成，但带有明确限制或未检查项；
- 结果完成且通过本次声明的检查。

## 文档与机器读取

SciRel exact asset document 是科学事实来源。发布流程从同一批 exact documents 生成：

- 面向模型的 route、summary 和 exact-record catalog；
- 面向人的可检索文档站页面；
- 指向同一 callable 和 evidence ceiling 的版本化链接。

skill 只教授检索和判断方法，不嵌入不断增长的资产清单。运行时优先读取与已安装 release 一致的本地
catalog snapshot 或 connector；公开文档站是同源投影，不成为执行时的网络依赖，也不通过 HTML 抓取
替代机器合同。

## 非目标

- 不训练或引入 PINN、XNet 等替代求解器；
- 不让求解模型访问未发布候选或审核队列；
- 不在每次请求中重新审核资产；
- 不把自然语言请求自动发布为新的 TaskGraph；
- 不用一个通用脚本硬编码语义理解、模型选择或科学验证；
- 不声称有限检查构成对所有输入和所有物理性质的形式化证明。

## 首轮验收

以轴对称平衡相关请求作为首轮样例：

1. 对“求解一个完整平衡”的请求，若可见 catalog 只有网格映射或材料支撑能力，必须准确报告缺少
   平衡求解能力，不能把预处理 TaskGraph 冒充求解器；
2. 对“把给定轴对称平衡映射到 Cartesian 求解网格并分类材料支撑”的请求，应能选中现有
   TaskGraph、完成输入规范化、执行并报告覆盖、clamping、mask 和有限性检查；
3. 两条路径都应产生用户可读的说明，并清楚区分事实、假设、检查结果和证据上限。
