# Tests that only the release stage runs, one entry per line:
#
#     <path or nodeid> | <what it proves and why the development stage skips it>
#
# The rule for this list: a test belongs here when a failure means the packaged or published
# product is wrong, and NOT when it means this change is wrong. Every test that is responsible
# for the correctness of the change itself stays in the development stage, and anything unclear
# stays there too. The development stage deselects exactly these entries and fails if one of them
# deselects nothing (a renamed or deleted test cannot silently return to the fast path), and the
# release stage runs the whole suite with zero deselections.
#
#
# Two rules keep this list honest. FIRST, prefer a nodeid over a file: a file entry takes every
# test in that file out of the development stage, including any correctness test someone adds to
# it later, and nothing fails when that happens. A file entry is only right when *every* test in
# the file needs the artifact. SECOND, never add a correctness test to a file that already appears
# here without narrowing the entry to nodeids in the same commit: the stale-entry check covers
# renamed and deleted tests, not added ones, so an added test would silently become release-only.
#
# `tests/tooling/test_validate_extraction_package.py` is deliberately absent even though it
# validates an admission artifact: it also holds the test that refuses a development-stage
# receipt, which is the guard for this very split, and a guard that only runs in the stage it
# guards is not a guard.
#
# Manifest reader: skills/development/scirel-acceptance/scripts/check_all.py

tests/delivery/test_real_delivery.py | Builds the wheel from the candidate commit, installs it into a separate virtual environment and consumes the exported catalog, index and three skills. It proves the artifact is installable and complete, which is release evidence; the development stage has not produced an artifact to consume yet.
