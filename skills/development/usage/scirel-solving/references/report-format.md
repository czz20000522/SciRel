# 报告格式

报告写成一篇简短的技术报告。读者先要知道答案，再决定是否看方法和细节。报告语言跟随用户。

## 结构

二级标题按以下顺序：

| 章节 | 内容 |
| --- | --- |
| 答案 | 几句话回答用户原来的问题，带主要数字和最重要的限制 |
| 问题与理解 | 用户问了什么，我怎样理解，关键口径 |
| 物理模型与方法 | 从物理判断到公式到求解思路，见[物理方法](method-design.md) |
| 结果 | 核心指标的小表、图和对图的说明 |
| 讨论 | 为什么是这个结果，物理解释，适用范围和没有覆盖的内容 |
| 结论 | 用一小段收尾，说明用户可以怎样使用这个结果 |
| 附录 | 验证结果、完整数值表、复现方法 |

英文报告使用 `Answer`、`Problem and understanding`、`Physical model and method`、`Results`、`Discussion`、`Conclusion`、`Appendix`。

## 写法

- **有效数字：** 正文通常 2 到 3 位，够表达差异即可。原始精度留在数据文件，附录的表最多 4 位。
- **用物理语言说影响：** 比如“不均匀度约增加一倍，从 0.29% 到 0.54%”。不要只堆数字。
- **不越权：** 用户没有给判据时不判定“可用”或“合格”，但要讲清楚影响，并说明用户可以怎样对照自己的要求。
- **数字可追溯：** 正文数字从保存的结果读回，最好由脚本填入。
- **图：** 每张图有图注。正文说明从图上能看出什么。
- **失败如实写：** 未通过和未运行的内容必须写明。
- **大表放附录：** 正文的表控制在 10 行以内。
- **图随报告交付：** 即使平台另有可视化流程，报告本身也要带图。环境里没有 matplotlib 就安装；确实无法安装时，写明原因并按下面的方式声明。

## 校验

校验器是本 skill 的 [scripts/validate_report.py](../scripts/validate_report.py)：

```sh
python <本 skill 目录>/scripts/validate_report.py <path>/REPORT.md
```

它只用标准库，检查章节顺序、图和图注、方法章节里没有代码块和实现细节、正文有效数字、失败检查已写入报告。它不判断物理是否正确，物理内容要靠人读。

确实不需要图或公式时，在报告里声明，校验器会接受：

```markdown
<!-- report: figures=none; reason=这是一个概念问题，答案是一句定性判断 -->
<!-- report: math=none; reason=只比较定义，没有用到公式 -->
```

## 目录约定

```text
<case>/
  request.md        阶段 1：用户原话和已确认口径
  method.md         阶段 2：物理方法
  solve.py          计算和检查
  make_figures.py   画图
  make_report.py    从保存的结果生成报告（数字不手抄）
  data/             原始精度结果和 checks.json
  figures/          报告中的图
  REPORT.md         最终报告
```

文件名不强制，但产物要齐。写法示范见[示例](example-report.md)。
