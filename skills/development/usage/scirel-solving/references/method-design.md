# 写物理方法

方法章节写给物理专业的读者。读者应该能从问题出发，一步步跟到结果，并判断每一步的物理假设对不对。

无论宿主平台用什么计划模板，开始计算前都要有这一段。模板里没有对应栏目时，自己加上。

## 要写什么

按下面的顺序写，让每一步都从上一步自然得出：

1. **物理判断：** 问题的物理核心是什么，什么效应决定答案。能先给一个定性或量级判断就先给。
2. **模型与假设：** 保留什么，忽略什么，为什么可以忽略。
3. **定律与公式：** 用什么定律，得到什么方程或解。关键公式要写出来。
4. **求解思路：** 怎样从公式走到要求的量，解析还是数值，为什么这样选。
5. **怎样确认算得对：** 计划用哪些检查，每个检查能抓住哪类错误。至少有一个检查对符号、归一化或单位敏感，例如解析极限、已知特例、独立的第二种算法或远场/近场渐近式。只写对称性是不够的，见[结果检查](result-checks.md)。

## 不写什么

数组形状、轴序、函数调用次序、文件名和数据流都不属于方法。这些放在代码和附录的复现说明里。

口径定义、点集清单、约束条件和交付清单也不是方法。它们写在 `request.md`，方法里引用即可。

## 怎样提到工具

某一步恰好用到 SciRel，就顺带注明一句，比如"单环的场这一步用了 SciRel 的现成函数"。用 NumPy、SciPy 或自己写的代码同样正常，不需要标注。不要每步都对应算子，也不要为了展示而改用某个算子。

## 模板

```markdown
# 物理建模与方法设计

## 物理判断
（问题的核心物理，什么决定答案；可先给定性或量级估计）

## 模型与假设
（保留的物理、忽略的物理和理由）

## 从定律到求解
1. （定律和公式）
2. （如何得到要求的量）

## 如何判断算得对
（每个检查及它能发现的错误类型；容差及其依据）

## 图
（每张图打算回答什么问题）

## 确认状态
（如实写：用户在对话中确认了什么 / 哪些口径由题目给定 / 哪些是未经确认的假设）
```
