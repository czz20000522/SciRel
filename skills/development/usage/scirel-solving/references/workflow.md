# 求解流程

用户的问题无法枚举，所以这里约束的是过程，不是题型。每个任务都走同样五个阶段，每个阶段有产物和进入下一阶段的条件。分支在阶段内部处理。

```text
需求澄清 → 物理建模与方法设计 → 用户确认 → 计算与验证 → 带图的报告
   ↑                               │
   └───── 物理前提变了就退回 ──────┘
```

| 阶段 | 产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1 需求澄清 | `request.md`：用户原话、口径及其来源、仍未知的量 | 剩下的未知量不再改变计算结果 |
| 2 物理建模与方法设计 | `method.md`：[物理方法](method-design.md) | 物理链条从问题到结果没有断点 |
| 3 用户确认 | 用户对方法的确认或修改 | 用户确认，或用户明确说可以跳过 |
| 4 计算与验证 | 程序、`data/`、`data/checks.json` | [结果检查](result-checks.md)已运行，失败已查明并解决，解决不了的已写明 |
| 5 报告 | `REPORT.md`、`figures/`，见[报告格式](report-format.md) | 报告校验通过，图已逐张看过 |

## 宿主平台的计划模板

很多平台会先让 agent 填一份自己的计划或任务模板（数据说明、目标、约束、交付清单等）。这些模板可以照常填写，但不能代替上面的五个阶段：

- 模板里没有物理方法这一段时，自己补一段，内容按[物理方法](method-design.md)的五步写。口径定义、点集、约束条件和交付清单都不是方法。
- 模板要求写"澄清结论"或"用户答复"时，只写真实发生过的对话。题目预先给定的口径写成"题目已给定"；没有问过用户的，不能写成"已向用户确认"。
- 模板自带的简报、摘要、交互可视化等格式是附加产物。用户没要求就不做；要做也只能附在七节报告之外，不能替代它。

## 阶段 1：需求澄清

重述问题，判断它属于哪类问题。只追问会改变计算或结论的内容，一次一到三个问题，先问影响最大的。详见[澄清方法](clarification.md)。

**何时结束：** 模型、几何、输入、输出量的定义和符号约定都已确定，同一份口径交给另一个人会算出同样的数。不影响计算的未知量（例如用户的容许指标）记下来即可，不必继续追问。用户给不出的量保留为未知，并给出条件结果。

在 `request.md` 里给每条口径注明来源：用户在对话中说的、题目或附件里写明的、还是你的假设。

## 阶段 2：物理建模与方法设计

先写物理，再想代码。方法要让懂物理、不一定懂代码的读者能跟下来。

需要现成算子时再用 `scirel-capability-discovery` skill 检索。检索是为了省事和复用经过验证的实现，不是流程目标。

## 阶段 3：用户确认

用几句话把物理假设和方法给用户看。确认的重点是模型是否符合用户的物理情况，不要把实现细节交给用户确认。

- 用户已明确说不用确认，或已经确认了全部物理口径：直接继续，在 `method.md` 里写明是哪种情况。
- 平台不支持中途提问：把假设写清楚后继续，并在报告的"问题与理解"里标明哪些假设未经用户确认。
- 不论哪种情况，都不能把没发生的确认写成已确认。

## 一次性任务

任务一次给出、中途不能提问，或题目声明已经完成澄清和确认时，跳过提问和等待，但阶段产物照写：

- `request.md` 照写，逐条标明口径来源：题目给定、附件给定、或你的假设。
- `method.md` 照写，并在末尾写一段"确认状态"：哪些口径由题目给定，哪些是未经确认的假设，以及假设不成立时结果会怎样变。题目声明已确认的内容写成"题目声明已确认"，不写成"用户已确认"。
- 不需要另写计划文件。宿主要求计划时，计划可以引用这两个文件。

## 阶段 4：计算与验证

按方法实现。原始精度的数字写入 `data/`，之后的步骤只从保存的文件读回。

检查要能分辨符号、归一化、单位这类看似合理的错误，只做对称性检查是不够的。容差在看结果之前定好；事后发现容差的依据错了，按修正检查处理（见[结果检查](result-checks.md)）。期望值要由独立途径得出，按定义恒等的关系不算检查。检查失败时先查原因：物理错了就修正计算，检查错了就修正检查，都要重跑，以最新结果为准。查清后仍解决不了的失败才如实写进报告，未运行的内容也要写明。详见[结果检查](result-checks.md)。

## 阶段 5：报告

报告是一篇短论文：答案 → 问题与理解 → 物理模型与方法 → 结果与图 → 讨论 → 结论 → 附录。格式和校验见[报告格式](report-format.md)。

## 分支

| 情况 | 怎么处理 |
| --- | --- |
| 不需要数值计算（定义、公式推导、量级估计、概念问题） | 仍要澄清和写出物理推理；可用解析结果或估算回答，跳过阶段 4 的程序，报告可以很短。不要为了走流程硬写程序 |
| SciRel 有合适的算子 | 读完整合同，确认单位、符号和适用范围后使用，在方法里顺带注明一句 |
| SciRel 没有，或不完全匹配 | 用 NumPy、SciPy 或自己写的代码，这很常见。写清楚公式和假设并加以验证，见[补充计算](glue-gap.md)。在报告里用一句话说明哪一步是自己实现的 |
| 物理假设在计算中被推翻 | 退回阶段 2，告诉用户变化，不要静默修改模型 |
| 澄清不能收敛（用户给不出关键量） | 用明确的条件分支计算，或说明缺什么；不要自己编一个值 |
| 涉及参数扫描 | 在方法里说明扫描的物理目的和范围，输出用曲线或等值线图；区间外不外推 |
| 涉及优化或设计 | 目标函数和约束必须来自用户，写进 `request.md`；用户没给就先澄清，不要自创目标或权重 |
| 需要用户数据 | 先检查单位、覆盖范围和坏点；对数据的处理写进方法 |
| 需要判定是否合格 | 只有用户给了判据才判定；没有判据时讲清楚变化，并说明用户可以怎样对照自己的要求 |
| 用户要一个可重复运行的程序，或要修改已有应用 | 交付可运行的入口、你为任务写的回归测试及其运行结果；保留用户原有的输入和基线 |
| 计算失败或不收敛 | 先查原因并尝试解决。解决不了的如实报告，说明已完成的部分和下一步需要什么 |

## 可视化

凡是结果涉及空间分布、函数关系或多个工况比较的，都要画图。标量答案或概念问题可以不画，并写明原因。

每张图只回答一个物理问题，只画物理量，不画代码流程或工具使用情况。坐标范围要让关键差异看得见。图生成后必须实际打开查看，像素统计不算。绘图通常用 matplotlib，它只用于报告，不是 SciRel 的依赖，环境里没有就单独安装（`python -m pip install matplotlib`）。稠密网格的图只用于观察，指标仍按用户定义的点计算，并在图注中说明。检查文字重叠、图例遮挡和坐标范围。
