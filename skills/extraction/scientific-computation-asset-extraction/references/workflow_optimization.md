# Extraction Workflow Optimization

Use this reference to reduce repeated D0 preparation, governed semantic-batch work and D1 extraction cost without changing the selected scope or freeze meaning.
It describes run methodology, not candidate-bundle content. Keep indexes, telemetry, experiments, and comparison
receipts in the run-owned evidence area; do not export them as L1 assets.

## Preserve the quality boundary

Use the completed D0 preparation as the shared starting point. Its upstream delta explains authorized scope changes;
D1 covers the frozen D0 and does not re-decide that cleanup to optimize its own cost. Bind source, indexes and
environment once at handoff, then give workers the relevant views and anchors. Rebuild or revalidate only when
the corresponding source/tool/environment binding changes or evidence is missing. Do not reinstall dependencies,
rehash an unchanged archive or repeat project-wide indexing for each region. Keep probes and cache separate from
scientific evidence and deliverables so tool experiments cannot become hidden runtime dependencies.

Freeze the source/evidence universe, declared scope, target paths, runtime conditions, skill bundle digest, and
current `full_freeze` contract before comparing workflows. The candidate workflow must still account for the same
source scope and pass the selected source-fidelity, dependency, source-free, comparison and completion
gates. Canonical/sealed-holdout requirements apply only when the caller selected that evidence protocol; do not
reintroduce scientific-correctness qualification into ordinary D1 through an optimization checklist. Do not trade an unresolved scientific relation, material branch, state lifecycle, or terminal output for a
lower cost metric.

Efficiency measures are diagnostic only. Select the smallest useful set for the suspected mechanism, such as wall
time, model turns, tool calls, repeated source bytes inspected, failed queries, retries, candidate reopenings, or
manual handoffs. No universal score or fixed improvement threshold is required.

## Select the smallest necessary rerun

Classify the failed boundary before scheduling work. Reuse observations only when executable science, source/input,
dependencies, runtime-relevant conditions and claim still correspond to the retained raw results. A prose, path,
packaging or comparator defect may require a new binding or comparison, not another scientific run. Derive repaired
expectations independently; never calibrate a tolerance or expected answer against the candidate output. If provenance
or raw results cannot support reuse, rerun only the affected slice. A new stage, new Agent or stronger receipt shape
alone is not a reason to repeat unchanged calculations.

Use existing run notes and receipts to distinguish reused evidence, cheap rechecks and fresh execution; this is not
a new mandatory report or gate. Keep operator/dependency tests, source comparison, independent fidelity/completeness review,
application replay and packaging checks attached to their owning claims. Validation-script optimization may reduce
duplicate byte reads but cannot replace those claims with a faster structural check.

## Governed semantic-batch critical path

First identify whether the work is initial index creation, maintenance after stable source changes, or repair of
an evidenced semantic defect. Follow [D0 phase order](material_access_and_preprocessing.md#d0-source-preparation):
complete the initial view before cleanup, then maintain changes without automatically launching a second full
semantic review. Existing valid indexes and already reviewed unchanged evidence are reusable. Keep repair scope
proportional to the demonstrated problem; widespread untrusted entries can justify a full repair, but a completed
first build alone cannot. Preserve active-plan progress and finish known corrections through a legal route.
Do not confuse preserving an optional review checkpoint with an obligation to exhaust it. At a normal boundary,
reuse existing findings to choose the necessary correction scope; use a supported targeted update path while
keeping elective unreviewed work explicit when the tool permits it. Do not conduct another whole semantic pass
to justify narrowing, infer defects from replacement counts, invent no-change results, or reset governance state.

The batch workflow below is conditional on the selected delegation/review contract, not a requirement to add
multiple agents to AOCI. Prefer its native Guide loop and existing responses/checkpoints over a second scheduler
or report chain. Retain any required independent stage reception and delegated-final submission gates. Report
initial build, cleanup, maintenance and repair costs separately so a full repair is not presented as initial scan cost.
Role count follows the actual dependency and independent-challenge requirement, not a fixed role set per batch.
Reuse unchanged gates and source-bound reviews; retain required final/digest/semantic checks at the real submission
boundary. Avoid regenerating ancestor receipts for every small increment. Validate a simplification with an actual
necessary correction and formal readback: separate work legitimately avoided from speed on comparable work,
include quality failures and integration time, and retain uncertainty when scope or complexity differs.

Use this route when repeated context recovery, worker collection or request repair dominates a sequence of D0
semantic batches. Follow the live indexing contract and retain one owner of formal writes. Before changing the
workflow, reconstruct a bounded sample from issued packet, dispatch, worker final, owner review, each rejected
attempt and actual Apply timestamps. Include child work and context compaction. Compute overlapping intervals
rather than summing nested tool timers or waits that overlap useful review. Time outside observed spans remains
unattributed; it is not automatically model reasoning, provider latency or idle time. Compare time to a valid
reviewed submission: an Apply before a required worker final is a completion defect, not a speedup.

At the next valid batch boundary, change the decision that causes the repeated work:

1. **Recover the current work first.** Read a compact view of owner/session and source identities, the current
   packet path and digest, applicable contract/Meta references, candidate coverage, worker readiness and unresolved
   correction/recovery/conflict pointers. Retain access to the authoritative records. Do not first print the whole
   checkpoint, historical receipts or help ladder merely to find those fields. Expand changed, missing or ambiguous
   clauses and evidence as needed; a compact projection does not restore lost source understanding or prove full
   index cognition. Follow any required live governance or recovery operation independently of this read choice.
2. **Reuse within a review; preserve independent challenge.** Bind the packet and necessary source/relation anchors
   once for each reviewer. Reuse that reviewer's valid readings while their bindings and claim remain unchanged.
   Changed source, new dependencies, conflicting proposals or missing evidence require the affected reads again.
   An author's conclusion or hash alone cannot stand in for the owner's independent source-based review.
3. **Consume ready work without premature submission.** Review completed subsets while other workers continue.
   Use native completion notifications or an appropriate supported blocking wait when nothing independent remains;
   repeated short waits or file-existence polling are not a completion test. Accept a result only when its required
   critique is finished and its final signal identifies the exact artifact bytes. Preserve that original and digest;
   later revisions are successors. Submit only the complete current machine-issued batch after all required results
   and owner review are ready. Do not serially delay ready reviews until every worker finishes.
4. **Stabilize the mechanical interface.** Inspect the actual final artifact shape and reuse one exact object/field
   mapping while that schema remains valid. Before Apply, check complete candidate coverage, source/candidate
   bindings, serialization and the current tool's deterministic field/budget constraints. A collector may move
   reviewed literals, not invent semantics, infer completion, truncate text or fill missing results with old entries.
   Repair only a named rejected scope, retain original-versus-owner-revision identities and compare meaning before
   resubmitting the full batch. Numeric/schema success cannot approve a lost condition or failure behavior.
5. **Enforce required evidence at the submission boundary.** When the selected contract requires final results and
   reviewed revisions, a file label, author-supplied completion boolean or optional collector is insufficient.
   Connect the checks to the actual submit path: resolve the native final event to its author/session/turn and exact
   artifact digest; bind source/candidate/batch identities and the complete outgoing request; bind any changed
   literals to a source-based semantic review of both immutable versions. A later final, changed artifact, new
   request or changed source invalidates an older pass. Mechanical checks verify these bindings, not the scientific
   judgment; the responsible model must still compare conditions, relations and failure behavior against evidence.
   Bind the actual authored review item, not a generic assurance copied into every row. Resolve index-keyed review
   items through the exact issued candidate mapping; never replace missing identity with the object being checked.
   Reject absent or empty judgments even when their hashes agree. Reuse unchanged, attributable source reviews;
   require a new comparison only for changed meaning or invalidated evidence.
   Exercise the real path with missing or late final, changed digest, missing or mismatched difference review and
   stale-pass cases, plus a valid case. An alternate direct submission that bypasses the check remains an open gap;
   distinguish a workflow check from a tool-enforced rejection rather than claiming either from a successful script.

Exercise the changed path on a real subsequent batch using existing execution records. Check final-before-Apply
ordering, preserved proposals, submitted revisions and formal readback as well as reduced reads, waits or repairs.
Retain original tool responses separately from compact projections so timing and acceptance can be independently checked.
Keep targeted semantic corrections in the current stage's completion contract. Distinguish instruction delivery,
observed adoption, outcome quality and measured speed; different batch contents or unfinished corrections prevent
a blanket speedup claim. This route adds no per-batch report family, extra reviewer, polling controller or universal
batch-size/timeout default. Apply portable guidance to later tasks; steering an authorized live owner does not
require replacing its frozen skill bundle.

## Structural evidence index

D0 preprocessing may emit a digest-bound, shareable structural index with:

- source files, languages, parse status, and excluded paths;
- symbols and source spans with stable anchors;
- static references, call edges, imports/includes, and explicit state reads/writes;
- candidate entry points, tests, examples, fixtures, and documents;
- tool/version/query provenance, unresolved dynamic edges, failures, and confidence limits.

This layer automates navigation and inventory only. It must not label a relation as scientifically public, decide an
operator or TaskGraph boundary, resolve Fortran common state or dynamic callbacks without evidence, determine a
document's scientific authority, or claim coverage. The extraction agent must be able to open the indexed source,
challenge the index, and run a bounded source/runtime probe. Prefer a tool-neutral intermediate shape so CodeGraph,
Joern, tree-sitter, language servers, compiler indexes, or repository-native tools can be compared without changing
the scientific method or making any one dependency mandatory.

## Bounded comparison

Record a baseline and one selected candidate workflow using comparable inputs and environments. Account for
differences in model/provider, cache state, concurrency, available dependencies, prior artifacts, and source runtime.
When practical, verify that the evaluation distinguishes an intentionally incomplete or stale index from a valid one;
otherwise a cheaper run may only demonstrate a blind evaluator.

Compare quality first: source census and dispositions, target-path and branch coverage, port/state completeness,
candidate claim ceilings, source-comparison reassembly under the selected evidence protocol, provenance, and unresolved gaps. Then compare the
selected efficiency observations. Inspect whether apparent savings came from scope shrinkage, unrecorded reuse,
evidence leakage, deferred work, or reduced oracle independence.

Choose the best currently supported workflow and stop the optimization pass. A single project is a bounded pilot,
not proof of universal improvement. Record the conditions, result, regressions, confounders, and next evidence that
would justify another revision; do not keep iterating in search of an absolute optimum.
